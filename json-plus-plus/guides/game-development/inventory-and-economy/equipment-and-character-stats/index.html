Equipment and Character Stats

A. Overview​

Ari fights with an iron sword and wears a leather armour. Both pieces change the numbers of the hero, and both are described by data instead of by code. The document says what an item is and what it adds; the events of Fusion add the numbers together, refuse the combinations that would break the hero, and write the result back to the document.

DifficultyIntermediate
ComplexityMedium — one document, a catalog of four pieces, two slots and five derived attributes
Fusion skillsFrame events, Active objects, Counter objects, global variables, comparison expressions
JSON++ skillsAbsolute paths, searches, writing values, reading typed values, file work, error handling

Gameplay scenario​

The hero finds an ember axe in the forest. The axe is stronger than the iron sword and it is also slower and less protective. Equipping it removes the sword from the hand and puts the axe there, so the derived attributes change in one step. The chain armour is better than the leather one in every way except its weight, but it cannot be worn by a hero of level three.

Learning objectives​

By the end of this guide you will be able to:

  • describe every piece of equipment with a stable identifier, a slot and a set of modifiers;
  • read the equipped items of the hero from the document;
  • add the modifiers of the equipment to the base attributes of the hero;
  • refuse an invalid combination, such as an item the hero does not carry, an item above the level of the hero, or an item that would make an attribute negative;
  • equip and unequip an item without losing the contents of the pack;
  • keep the equipped items between two sessions.

What you will build​

An equipment panel with two slots, a catalog of four pieces of Emberfall, the events that equip and unequip them, the calculation of the derived attributes, and the file inventory.json.

B. Prerequisites​

Fusion knowledge you need

  • Frame events such as Start of Frame.
  • Active objects and the is clicked condition.
  • The Counter object and the Set counter action.
  • The String object and the Set alterable string action.
  • Global variables on the Special object, written in this manual as Special : Set <name> to <value>.
  • Comparison conditions, written as value1 < value2, value1 >= value2 and value1 <> value2, and string comparison written as value1 = value2.

JSON++ concepts you need

  • JSON paths, because the modifiers of a piece of equipment are read with a path built from the identifier of the item.
  • JSON instance state, because the events copy values out of the document and into the counters of the game.
  • Missing, null and empty, because an empty slot and a slot that holds an item are different states.
  • Search results and their lifetime, because the check of the pack uses a search whose result list is replaced by the next search.
  • Conditions and triggers, in particular the difference between On Results Found and On Not Results Found.

Runtime limitations to keep in mind

  • A string comparison in the Compare to String condition accepts an empty text, so an empty slot can be tested directly. A comparison between two Fusion values uses the ordinary comparison condition of Fusion.
  • The extension does not add numbers. Every sum of this guide is a Fusion counter that receives two values in two steps.
  • File paths follow the host. Apppath$ + "inventory.json" works on Windows. HTML5 needs a browser reference such as storage://inventory, and the mobile targets write inside the sandbox of the application. See platform-specific file operations.

Standard objects used here

JSON++ Object, Counter, String, Special, Active and Timer. Nothing else is required.

C. Gameplay Scenario​

The equipment of the hero is made of two slots. The weapon slot holds the sword or the axe. The armour slot holds the leather or the chain armour. The document records which item occupies each slot and describes what that item does.

Every piece of equipment belongs to a catalog. The catalog is an object whose members are the identifiers of the items, so the definition of the ember axe is always at /equipment/axe_ember. Its definition names the slot it belongs to, the attributes it changes, and the level the hero needs before he may carry it.

The attributes of the hero come in two families. The base attributes belong to the hero and never change: they are in /player/base_stats. The derived attributes are the result of the base attributes and of the equipment, and they are calculated by the events of Fusion every time the equipment changes. The document stores the two families side by side, and the difference between them is the subject of this guide.

When the player chooses an item, the events do not trust the click. They check that the hero carries the item, that the hero is strong enough, and that the item belongs to a slot that exists. Only then does the document change, and only then are the derived attributes calculated again.

Three kinds of data meet in this system, and each one has a different origin. The base attributes and the catalog are written by a designer. The equipped items are written by the player, through the events of the panel. The derived attributes are written by the events of the calculation, from the other two. The table in the next section makes that separation explicit, because it is the point that most often goes wrong when a game grows.

D. Final Result​

The finished system behaves like this:

  • The panel shows the iron sword in the weapon slot and the leather armour in the armour slot.
  • Choosing the ember axe moves it to the weapon slot, and the derived attack rises from 20 to 26 while the derived speed falls from 11 to 7.
  • The sword is still in the pack: equipping replaces the slot, it does not consume the item.
  • Choosing an item that the hero does not carry is refused with a message, and the equipment does not change.
  • Choosing the ember axe with a hero of level three is refused with a message about the level.
  • Choosing an item whose slot the hero does not have is refused, and the equipment does not change.
  • A piece of equipment that would make an attribute negative never produces a negative attribute.
  • Unequipping the armour empties the slot and lowers the derived defense.
  • The name of every piece in the panel is read from the catalog, and an empty slot reads Empty.
  • The derived attributes are stored in the document, so a saved run keeps them.
  • A file that cannot be read or written produces a readable message instead of an empty panel.

E. JSON Data Structure​

The complete document​

The equipment of the hero lives in the document of the hero, the same file that holds the pack. The catalog of the pieces sits next to the catalog of the items, under /equipment.

{
  "schema_version": 1,
  "player": {
    "name": "Ari",
    "level": 3,
    "hp": 80,
    "max_hp": 100,
    "gold": 250,
    "base_stats": {"attack": 12, "defense": 6, "speed": 10, "magic": 4},
    "equipment": {"weapon": "sword_iron", "armor": "armor_leather"},
    "derived_stats": {"attack": 20, "defense": 10, "speed": 11, "magic": 4, "max_hp": 110},
    "inventory": [
      {"id": "sword_iron", "quantity": 1},
      {"id": "axe_ember", "quantity": 1},
      {"id": "armor_leather", "quantity": 1},
      {"id": "armor_chain", "quantity": 1},
      {"id": "potion_health", "quantity": 2}
    ]
  },
  "equipment": {
    "sword_iron": {"name": "Iron Sword", "slot": "weapon", "attack": 8, "defense": 0, "speed": 1, "magic": 0, "hp": 0, "requires_level": 1, "value": 120},
    "axe_ember": {"name": "Ember Axe", "slot": "weapon", "attack": 14, "defense": -2, "speed": -1, "magic": 3, "hp": 0, "requires_level": 4, "value": 150},
    "armor_leather": {"name": "Leather Armor", "slot": "armor", "attack": 0, "defense": 4, "speed": 0, "magic": 0, "hp": 10, "requires_level": 1, "value": 90},
    "armor_chain": {"name": "Chain Armor", "slot": "armor", "attack": 0, "defense": 9, "speed": -2, "magic": 0, "hp": 20, "requires_level": 5, "value": 180}
  }
}

The root holds the version of the shape, the record of the hero and the catalog of the equipment.

The catalog of the equipment​

The catalog is an object whose members are the identifiers of the pieces. The path of a definition is built from the identifier alone, so the modifiers of the ember axe are at /equipment/axe_ember/attack and /equipment/axe_ember/defense.

MemberTypeMeaning
namestringThe name shown in the panel, such as Ember Axe.
slotstringThe slot the piece belongs to: weapon or armor. The events read this member and refuse a piece whose slot the hero does not have.
attacknumberThe points added to the derived attack. A negative value is allowed.
defensenumberThe points added to the derived defense. The ember axe removes two of them.
speednumberThe points added to the derived speed. The chain armour removes two of them.
magicnumberThe points added to the derived magic.
hpnumberThe points added to the maximum health.
requires_levelnumberThe level the hero needs before he may carry the piece.
valuenumberThe base price of the piece. The shop guide uses it.

Every member is a number, except the name and the slot. Numbers are the rule of this document, because every one of them is added to a counter.

The record of the hero​

MemberTypeMeaning
namestringThe name of the hero.
levelnumberThe level of the hero. It is compared with requires_level of a piece.
hpnumberThe current health of the hero.
max_hpnumberThe maximum health of the hero before any armour.
base_statsobjectThe attributes that belong to the hero: attack, defense, speed and magic.
equipmentobjectThe two slots: weapon and armor. Each one holds the identifier of the piece, or an empty text when the slot is empty.
derived_statsobjectThe attributes after the equipment is added: attack, defense, speed, magic and max_hp. The events of Fusion write this object.
inventoryarrayThe pack of the hero, in the shape built by the stackable inventory guide.

The empty slot​

An empty slot holds an empty text, not null and not a missing member:

{
  "equipment": {"weapon": "", "armor": ""}
}

This choice matters on the runtimes. The native runtime accepts a member whose value is null when the exists condition is used, while the HTML5 runtime reports such a member as absent. An empty text behaves the same way on every target, and it can be compared with a string condition without ambiguity.

The attributes of the hero​

The base attributes are the numbers that the hero brings to the fight, before any piece.

AttributeMeaningWhere the combat events use it
attackThe damage of a hit of the hero.The damage of the attack of the hero.
defenseThe protection of the hero.The damage that the hero takes from a hit.
speedThe speed of the hero.The delay between two moves and the order of the turns in a fight.
magicThe power of the magic of the hero.The damage of the spells of the hero.

The maximum health is not an attribute of the base_stats object, because it belongs to the hero itself: it is the member max_hp of the record of the hero, and the armour adds to it. The derived maximum health is written in /player/derived_stats/max_hp.

The four attributes and the maximum health are the only numbers of the hero that a piece of equipment may change. A new piece that changes something else, such as the reach of the weapon or the resistance to a kind of damage, needs a new member in the catalog and a new action in the calculation of Step 5.

The slots of the hero​

The hero has two slots, and the object /player/equipment holds one member for each of them.

SlotMemberHoldsExample
WeaponweaponThe identifier of the piece in the hand, or an empty text.sword_iron
ArmourarmorThe identifier of the piece on the body, or an empty text.armor_leather

The name of the slot is also the name of the slot member of a definition in the catalog, and the events of Step 15 write the piece to the slot that its own definition names. A piece therefore never reaches a slot that it does not belong to.

The slots are the only place where the equipment of the hero is recorded. The pack holds the pieces, the slots hold the ones that are in use, and the two never describe the same piece in two different states: a piece in a slot is also in the pack, because equipping does not consume it.

The levels of the pieces​

The requirement of a piece is a number in the catalog, and it is compared with the level of the hero.

PieceSlotRequired levelWhat the hero gainsWhat the hero loses
sword_ironweapon18 attack, 1 speedNothing.
axe_emberweapon414 attack, 3 magic2 defense, 1 speed.
armor_leatherarmor14 defense, 10 maximum healthNothing.
armor_chainarmor59 defense, 20 maximum health2 speed.

Two of the four pieces are above the level of Ari, who is level three. The comparison of Step 13 refuses them, and the level of the hero is the only thing that decides whether a piece may be worn.

The pieces that lower an attribute are as interesting as the ones that raise it. The ember axe is the strongest weapon of Emberfall and the slowest one, and the chain armour protects the hero better than any other piece while it makes the hero slower. The design of the set lives in the catalog, and the events of this guide only add the numbers.

What the document stores and what Fusion calculates​

This is the heart of the guide. Two families of numbers live in the document, and they are not written the same way.

ValueWritten byRead byChanges when
base_statsThe designer, in the fileThe events of the calculationThe hero levels up.
The catalog of the equipmentThe designer, in the fileThe events of the calculationThe designer adds a piece.
equipmentThe events of the equippingThe events of the calculationThe player equips or unequips.
derived_statsThe events of the calculationThe combat events and the interfaceThe equipment or the level changes.
The counters of the gameThe events of the calculationThe combat eventsThe events run.

The document never calculates anything by itself. Changing base_stats in the file changes the derived attributes the next time the calculation runs, and until then the counters keep the values of the last run. The multiple save slots guide writes the document of the hero to the disk, and the derived attributes travel with it.

G. Step-by-Step Implementation​

Step 1 — Create the frame and the objects​

  1. Create a frame named Camp.
  2. Add the objects of the previous section, with the names the table lists.
  3. On the Special object, create the global variables Chosen Id (string), Slot Value (string), Weapon Id (string), Armor Id (string), Needed Level (number), Equip Refused (number), Stats Dirty (number) and Write Dirty (number). Leave them at 0, except the three text ones, which start empty.

Step 2 — Load the document at the start of the frame​

Add a Start of Frame event with one action:

  • Action: Equipment Data : Load JSON from file at Apppath$ + "inventory.json".

The document is read and parsed. A file that is missing or invalid reaches the On Error event of Step 17.

Step 3 — Read the equipped items into global variables​

Add an event with the condition Equipment Data: On JSON Loaded:

  • Action: Special : Set Weapon Id to GetString( "Equipment Data", "/player/equipment/weapon" ).
  • Action: Special : Set Armor Id to GetString( "Equipment Data", "/player/equipment/armor" ).
  • Action: Special : Set Stats Dirty to 1.

The two identifiers are copied into global variables, because the calculation of Step 4 needs them in a form that Fusion can compare and concatenate. The flag Stats Dirty asks for the calculation of the attributes.

Step 4 — Reset the derived counters from the base attributes​

Add an event with the condition Stats Dirty = 1. The events of this guide are placed after the search events, so the flag that they set is seen in the same frame.

  • Action: Attack Counter : Set counter to GetNumber( "Equipment Data", "/player/base_stats/attack" ).
  • Action: Defense Counter : Set counter to GetNumber( "Equipment Data", "/player/base_stats/defense" ).
  • Action: Speed Counter : Set counter to GetNumber( "Equipment Data", "/player/base_stats/speed" ).
  • Action: Magic Counter : Set counter to GetNumber( "Equipment Data", "/player/base_stats/magic" ).
  • Action: Max HP Counter : Set counter to GetNumber( "Equipment Data", "/player/max_hp" ).
  • Action: Special : Set Write Dirty to 1.
  • Action: Special : Set Stats Dirty to 0.

The counters start from the base attributes. The equipment is added on top of them by the next steps, so the calculation never adds twice. The flag Write Dirty asks the event of Step 8 to store the result in the document.

Step 5 — Add the modifiers of the weapon​

Under the same event, add a group:

  • Condition of the group: Weapon Id <> "".
  • Action: Attack Counter : Set counter to value("Attack Counter") + GetNumber( "Equipment Data", "/equipment/" + Weapon Id + "/attack" ).
  • Action: Defense Counter : Set counter to value("Defense Counter") + GetNumber( "Equipment Data", "/equipment/" + Weapon Id + "/defense" ).
  • Action: Speed Counter : Set counter to value("Speed Counter") + GetNumber( "Equipment Data", "/equipment/" + Weapon Id + "/speed" ).
  • Action: Magic Counter : Set counter to value("Magic Counter") + GetNumber( "Equipment Data", "/equipment/" + Weapon Id + "/magic" ).
  • Action: Max HP Counter : Set counter to value("Max HP Counter") + GetNumber( "Equipment Data", "/equipment/" + Weapon Id + "/hp" ).

The path of the definition is built with the identifier of the piece, so the same five actions work for every weapon. The group is skipped when the slot is empty.

Step 6 — Add the modifiers of the armour​

Add a second group under the same event:

  • Condition of the group: Armor Id <> "".
  • Action: Attack Counter : Set counter to value("Attack Counter") + GetNumber( "Equipment Data", "/equipment/" + Armor Id + "/attack" ).
  • Action: Defense Counter : Set counter to value("Defense Counter") + GetNumber( "Equipment Data", "/equipment/" + Armor Id + "/defense" ).
  • Action: Speed Counter : Set counter to value("Speed Counter") + GetNumber( "Equipment Data", "/equipment/" + Armor Id + "/speed" ).
  • Action: Magic Counter : Set counter to value("Magic Counter") + GetNumber( "Equipment Data", "/equipment/" + Armor Id + "/magic" ).
  • Action: Max HP Counter : Set counter to value("Max HP Counter") + GetNumber( "Equipment Data", "/equipment/" + Armor Id + "/hp" ).

Step 7 — Keep the derived attributes positive​

Add a third group under the same event, after the two groups of Steps 5 and 6:

  • Condition of the group: value("Defense Counter") < 0.
  • Action: Defense Counter : Set counter to 0.

The ember axe removes two points of defense. A hero with a low base defense would otherwise end up with a negative value, and a negative defense in the combat events would add damage instead of removing it. The same group can be added for the speed when the design allows a piece to slow the hero below zero.

Step 8 — Write the derived attributes into the document​

Add a second event with the condition Write Dirty = 1, placed after the event of Step 4 in the event list:

  • Action: Equipment Data : Set number value("Attack Counter") at "/player/derived_stats" with key "attack".
  • Action: Equipment Data : Set number value("Defense Counter") at "/player/derived_stats" with key "defense".
  • Action: Equipment Data : Set number value("Speed Counter") at "/player/derived_stats" with key "speed".
  • Action: Equipment Data : Set number value("Magic Counter") at "/player/derived_stats" with key "magic".
  • Action: Equipment Data : Set number value("Max HP Counter") at "/player/derived_stats" with key "max_hp".
  • Action: Special : Set Write Dirty to 0.

The derived attributes now exist twice: in the counters, which the game reads, and in the document, which the game saves. Writing them is optional; a designer who prefers a smaller file can leave the object out and let the counters be the only copy.

Step 9 — Apply the derived attributes to the hero​

Add two more actions to the event of Step 8:

  • Action: Player : Set alterable value to value("Max HP Counter").
  • Action: Stats Label : Set alterable string to "ATK " + Str$(value("Attack Counter")) + " DEF " + Str$(value("Defense Counter")) + " SPD " + Str$(value("Speed Counter")).

The first action hands the maximum health to the hero. The second draws the line of attributes. The combat events of the game read the same counters, so the numbers that the player sees and the numbers that the fight uses are always the same.

Step 10 — Choose a piece in the interface​

Add an event with the condition Equip Button is clicked:

  • Action: Special : Set Chosen Id to "axe_ember".
  • Action: Special : Set Equip Refused to 0.
  • Action: Equipment Data : Search for value """" + Chosen Id + """" at "/player/inventory" (Exact: 1).

The click only records the choice and asks the document whether the hero carries that identifier. The search looks for the value in the pack of the hero, where every entry holds the identifier of its item.

Step 11 — Refuse a piece that the hero does not carry​

Add an event with the condition Equipment Data: On Not Results Found:

  • Action: Status Text : Set alterable string to "The hero does not carry this item".
  • Action: Special : Set Equip Refused to 1.

Nothing else runs. The equipment of the hero keeps the items it had.

Step 12 — Read the definition of the chosen piece​

Add an event with the condition Equipment Data: On Results Found:

  • Action: Special : Set Slot Value to GetString( "Equipment Data", "/equipment/" + Chosen Id + "/slot" ).
  • Action: Special : Set Needed Level to GetNumber( "Equipment Data", "/equipment/" + Chosen Id + "/requires_level" ).

Both values come from the catalog, with the identifier as the last part of the path. The slot tells the events where the piece goes, and the level requirement tells them whether the hero may carry it.

Step 13 — Check the level of the hero​

Under the event of Step 12, add a group:

  • Condition of the group: GetNumber( "Equipment Data", "/player/level" ) < Needed Level.
  • Action: Status Text : Set alterable string to "The hero is not strong enough".
  • Action: Special : Set Equip Refused to 1.

The group runs when the hero is below the requirement of the piece. The flag Equip Refused tells the group of Step 15 not to equip anything.

Step 14 — Check the slot of the piece​

Under the event of Step 12, add a group with the condition Slot Value <> "weapon", and inside it a group with the condition Slot Value <> "armor":

  • Action: Status Text : Set alterable string to "That piece cannot be equipped".
  • Action: Special : Set Equip Refused to 1.

The two groups together refuse every slot that the hero does not have. A piece whose definition names a slot that does not exist is a mistake in the data, and the hero must not wear it.

Step 15 — Equip the piece and refresh the attributes​

Under the event of Step 12, add a last group:

  • Condition of the group: Equip Refused = 0.
  • Action: Equipment Data : Set string Chosen Id at "/player/equipment" with key Slot Value.
  • Action: Special : Set Weapon Id to GetString( "Equipment Data", "/player/equipment/weapon" ).
  • Action: Special : Set Armor Id to GetString( "Equipment Data", "/player/equipment/armor" ).
  • Action: Special : Set Stats Dirty to 1.
  • Action: Status Text : Set alterable string to "The piece was equipped".

The key of the write is the slot of the piece, so the same action fills the weapon slot or the armour slot. The group runs last, after the refusal groups of Steps 13 and 14, so it sees the flag they may have set.

The document keeps the piece in the pack. Equipping fills a slot, it does not consume an item.

Step 16 — Unequip a piece​

Add an event with the condition Unequip Button is clicked:

  • Action: Special : Set Slot Value to "armor".
  • Action: Equipment Data : Set string "" at "/player/equipment" with key Slot Value.
  • Action: Special : Set Armor Id to GetString( "Equipment Data", "/player/equipment/armor" ).
  • Action: Special : Set Stats Dirty to 1.
  • Action: Status Text : Set alterable string to "The slot is empty".

An empty text empties the slot on every runtime. The piece itself stays in the pack, so the player can equip it again.

Step 17 — Save the equipment and handle the errors​

Add an event with the condition Save Button is clicked:

  • Action: Equipment Data : Save JSON to file at Apppath$ + "inventory.json".

Add a second event with the condition Equipment Data: On JSON Saved:

  • Action: Status Text : Set alterable string to "The equipment was saved".

And a third one with the condition Equipment Data: On Error:

  • Action: Status Text : Set alterable string to GetError( "Equipment Data" ).

J. Edge Cases & Error Handling​

SituationWhat happensHandling
inventory.json does not existThe load fails and On Error runsWrite the file with the game on the first run and show a message that the equipment is unavailable.
The document has no player memberThe counters are reset to zero and the panel shows zerosCheck /player with the exists condition and write a default record before the calculation.
The document has no equipment memberThe definition of the piece cannot be read and the slot is emptyKeep the catalog in the same file and validate the file against a JSON schema.
The chosen identifier is not in the catalogThe slot reads empty and the level reads zeroRefuse any identifier that is not in the catalog, and validate the file when it is written.
The chosen identifier is not in the packThe search finds nothing and the On Not Results Found event runsKeep the search before every write; the refusal leaves the equipment untouched.
The hero is below the required levelThe refusal group of Step 13 sets the flag and the piece is not equippedCompare the level of the hero with requires_level of the piece, and raise the requirement only in the data.
The piece names a slot the hero does not haveThe two groups of Step 14 refuse itKeep the list of slots small and validate the slot member of every definition.
A modifier would make an attribute negativeThe group of Step 7 sets the attribute back to zeroClamp every attribute that the combat events use as a subtraction.
The hero levels upThe base attributes change and the calculation must run againSet Stats Dirty when the level changes, so the derived attributes follow.
A piece is equipped twiceThe slot is written twice with the same identifierThe slot holds one identifier, so the second write replaces the first.
The pack is empty because the level was reloadedThe search finds nothing and every piece is refusedLoad the pack before the equipment, in the same order as the level events.
The catalog has no slot member for a pieceThe slot reads empty and the piece is refusedKeep the slot member in every definition and validate the file against a JSON schema.
The catalog has no requires_level memberThe requirement reads zero and every hero may carry the pieceKeep the member in every definition, and give it a value of 1 for the pieces that any hero may carry.
A piece is equipped while another piece of the same slot is equippedThe slot is overwritten and the first piece stays in the packWrite the identifier to the slot of the piece, so the slot always holds exactly one piece.
The save file cannot be writtenThe save fails and On Error runsKeep the confirmation in On JSON Saved to File, so the player is never told that a save happened when it did not.
The game runs on HTML5Apppath$ has no meaningUse a browser reference such as storage://inventory and read the platform-specific file guide.
The game runs on Android or iOSThe file lands in the sandbox of the applicationUse the path documented for that target and test the export.

One rule deserves emphasis: the refusal groups run before the group that writes. The order of the groups is what keeps the equipment of the hero consistent, and it is why the flag Equip Refused exists.

K. Runtime Compatibility​

The system relies on three groups of features: file operations, searches, and reading and writing values.

TargetFile workSearches and valuesNotes
WindowsImplemented and testedImplemented and testedApppath$ resolves to the folder of the exported application.
AndroidImplemented, not verified by an automated checkImplemented, not verified by an automated checkWrites inside the sandbox of the application. Test the export.
HTML5Implemented and testedImplemented and testedUse a browser reference. storage:// uses the origin storage, download:// dispatches a download, embedded:// is read-only.
macOSUnknownUnknownNo separate build was verified.
iOSImplemented, not verified by an automated checkImplemented, not verified by an automated checkWrites inside the sandbox of the application. Test the export.

A second difference matters for the empty slot. On the native runtime the exists condition accepts a member whose value is null, while the HTML5 runtime reports such a member as absent. This guide stores an empty text instead of null, so both targets agree and the string comparison works everywhere. The full matrix is on the runtime compatibility page.

M. Next Steps​

  • Add more slots. A ring or a trinket needs one more member in /player/equipment and one more group in the calculation. The crafting guide uses the same structure to produce the pieces that fill those slots.
  • Show the piece that the player chose. The name of a piece is read from the catalog with the identifier of the piece, and the panel draws it next to the button, as the block of the section H shows.
  • Show the requirements in the interface. Read requires_level and the name of the piece and draw them next to the button of the piece, so the player knows why a piece is refused.
  • Compare the pieces. A comparison panel reads the catalog of the equipment and shows the difference of two definitions, using a loop over the catalog.
  • Balance the pieces without touching the events. Every number of the catalog is in the file, so a designer rebalances the axe by changing one line of JSON.
  • Protect the document. The extension can validate a file against a JSON schema before it is read, and encrypt the file it writes. See Enable JSON Schema Validation and Enable Encryption.
