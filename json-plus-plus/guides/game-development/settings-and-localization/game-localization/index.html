Game Localization

A. Overview​

Emberfall ships in two languages. The player picks one in the options menu, and every interface element, item name and line of dialogue follows that choice without the gameplay logic changing.

DifficultyIntermediate
ComplexityMedium — two JSON documents, one dictionary per language and a small index
Fusion skillsFrame events, Active objects, String objects, global variables, expressions
JSON++ skillsLoading files, reading members with a computed path, checking the existence of a member, writing preferences

Gameplay scenario​

The options menu of Emberfall lists two languages, English and Portuguese. The player chooses Portuguese, and the title of the menu becomes Iniciar jogo, the health label becomes Vida and Elder Rook greets the hero in Portuguese. The player quits the game, starts it again and finds the choice preserved: the menu is in Portuguese from the first frame.

Learning objectives​

By the end of this guide you will be able to:

  • separate the text of the game from the logic of the game, so that a language is a document and not a copy of the events;
  • read a translation with a key built at runtime, which is what makes one event serve every label;
  • keep a fallback dictionary in a second JSON++ Object and use it when a key is missing;
  • localise a dialogue that stores keys instead of sentences;
  • save the chosen language and apply it again at the next start.

What you will build​

A dictionary document per language, a small index that lists the available languages, a language selector in the options menu, a refresh event that rewrites every visible label after a change, and a preference file that keeps the choice.

B. Prerequisites​

Fusion knowledge you need

  • Frame events and the condition Start of Frame.
  • The String object and the action Set alterable string.
  • The Special object and its global variables, including a global that holds text.
  • The Active object and the condition is clicked.
  • Reading the alterable string of an object, for example item_id("Potion").

JSON++ concepts you need

  • JSON paths, and the fact that a path may be built from an expression.
  • Missing, null and empty, because a key that is absent and a key that holds an empty text are two different situations.
  • JSON instance state: two JSON++ Object instances hold two documents at the same time.
  • Conditions and triggers, for On JSON Loaded and On Error.

Runtime limitations to keep in mind

  • A file path that names the language is built at runtime, for example Apppath$ + "locale_" + Locale Id + ".json". The expression must produce a complete reference on every target, so the identifier of the language has to be the same in the index and in the file name.
  • On HTML5 the language file is a browser reference such as storage://locale_pt-BR, and a file that is not there produces an error rather than an empty dictionary.
  • The exists condition accepts a member whose value is null on the native runtime and reports it as absent on the HTML5 runtime. The dictionaries of this guide never store null, so both targets behave the same.

Standard objects used here

String, Special, Active, Timer, JSON++ Object.

C. Gameplay Scenario​

Emberfall is written once. The events that move the hero, open a chest or apply the damage of a sword do not know which language is active. They do not even know the words on screen.

What they know is a key. The label of the health bar does not contain the word Health; it contains the key hud.hp. A small event asks the dictionary for the text of that key and writes the answer in the label. Change the dictionary and the screen changes with it.

The options menu is the only place where the player chooses. The choice is stored in a global variable, applied by reloading the dictionary and rewriting every label, and written to the settings file so the next start begins in the same language.

The dictionary has one entry per language, and each entry has the same keys. When a new line of dialogue is added and the translation is forgotten, the game must not show an empty label: a second dictionary in English stands by, and the label takes the English text when the key is absent from the chosen language.

D. Final Result​

The finished system behaves like this:

  • The game starts in the language that was chosen in the previous session.
  • Choosing another language in the options menu rewrites the menu, the interface labels, the item names and the current dialogue line at once.
  • The choice survives closing the game.
  • A key that has no translation falls back to the English text instead of leaving the label empty.
  • The gameplay code is identical in both languages: no event changes, no duplicated branch.

E. JSON Data Structure​

The index of the available languages​

{
  "locales": ["en", "pt-BR"],
  "current": "en",
  "fallback": "en"
}

The root is an object with three members. locales is an array of the identifiers of the languages that ship with the game. current is the language the player chose. fallback is the language used for a key that has no translation.

The identifier is the same string that names the file and that appears in the dictionary. Keeping one identifier for the three uses removes an entire class of mistakes.

The dictionary of one language​

  "locale": "en",
  "language_name": "English",
  "strings": {
    "menu.start": "Start Game",
    "menu.options": "Options",
    "menu.quit": "Quit",
    "hud.hp": "HP",
    "hud.gold": "Gold",
    "inventory.title": "Inventory",
    "inventory.empty": "Your bag is empty.",
    "shop.buy": "Buy",
    "shop.sell": "Sell",
    "shop.not_enough_gold": "Not enough gold.",
    "shop.bag_full": "Your bag is full.",
    "dialogue.rook.greeting": "Welcome to Emberfall, traveller.",
    "dialogue.rook.quest": "The forest is full of slimes. Cull three of them for me.",
    "dialogue.rook.complete": "The village is safe again. Take this, and welcome.",
    "item.potion_health": "Health Potion",
    "item.sword_iron": "Iron Sword",
    "item.herb_lotus": "Lotus Herb",
    "quest.accept": "Quest accepted.",
    "quest.complete": "Quest complete."

}

The root holds the identifier of the language, the name of the language in that language, and the dictionary itself. strings is an object whose members are the translation keys.

The keys follow a dotted convention: the area, then the subject, then the variant. menu.start is the start button of the menu, shop.not_enough_gold is the message of the shop when the player cannot pay. The convention is not a rule of the extension; it is a convention of the game, and it keeps two dictionaries compatible.

F. Clickteam Fusion Object Setup​

Item Name LabelStringThe name of the item being described, read from the key item.item_id.
Dialogue TextStringThe line of dialogue, read from the key dialogue.npc_id.line_id.

Translation KeySpecialA global variable that holds the key whose text is being requested.

Four JSON++ Object instances are used. Each one keeps its own document, so the index, the dictionary, the fallback and the preferences never mix.

G. Step-by-Step Implementation​

Step 1 — Create the frame and the objects​

  1. Create the frame Options and add the objects listed above.
  2. Create the global variables Locale Id, Translation Key and Item Id on the Special object. Locale Id starts with the text en.
  3. Give the rows of the Language Selector an alterable string named LocaleId with the identifier of their language, such as en and pt-BR.

Step 2 — Load the index of the languages​

Add a Start of Frame event:

  • Condition: Start of Frame.
  • Action: Locale Index : Load JSON from file at Apppath$ + "locales.json".

Step 3 — Load the preferences and apply the stored language​

Add an event with the condition Locale Index: On JSON Loaded:

  • Action: Settings Data : Load JSON from file at Apppath$ + "settings.json".

Then add an event with the condition Settings Data: On JSON Loaded:

  • Action: Special : Set Locale Id to GetString( "Settings Data", "/locale" ).

If the preferences file does not exist yet, the error branch runs instead and the language of the index is used. The order matters: the preferences override the default, and never the other way around.

Step 4 — Load the dictionary of the chosen language​

Add an event with the condition Settings Data: On JSON Loaded and, in the same event, the condition of the index:

  • Condition of the group: Locale Index: Is "/current" equal to "en".

When the stored language is English, the file of the fallback is the same file, so it is loaded once. In the other branch, the language of the index is loaded:

  • Condition of the group: Locale Index: Is "/current" equal to "pt-BR".
  • Action: Locale Data : Load JSON from file at Apppath$ + "locale_pt-BR.json".

A cleaner version of the same idea builds the name from the global variable, so that a new language does not need a new event:

  • Action: Locale Data : Load JSON from file at Apppath$ + "locale_" + Locale Id + ".json".

Use that version in a game with more languages. The two versions are shown here because the group form makes the decision visible.

Step 5 — Load the fallback dictionary​

Add an event with the condition Locale Index: On JSON Loaded:

  • Action: Fallback Data : Load JSON from file at Apppath$ + "locale_en.json".

The fallback dictionary is always English in this game. It is loaded even when the chosen language is English, which keeps the lookup logic in the game identical for every language.

Step 6 — Write a label from a key​

Add an event with the condition Locale Data: On JSON Loaded:

  • Condition: Locale Data: On JSON Loaded.
  • Action: Special : Set Translation Key to "menu.start".
  • Action: Menu Title : Set alterable string to GetString( "Locale Data", "/strings/" + Translation Key ).

The path is built at runtime from the global variable, so one event serves every label. The next steps show the same event with a different key.

Step 7 — Refresh every label after a change​

Add an event with the condition Refresh Timer: On timer:

  • Action: Menu Title : Set alterable string to GetString( "Locale Data", "/strings/menu.start" ).
  • Action: Health Label : Set alterable string to GetString( "Locale Data", "/strings/hud.hp" ).

The timer fires a few frames after the dictionary is loaded. The delay gives the load time to finish, because the dictionary arrives through On JSON Loaded and not at the moment the action is issued.

Add one action per label. The list is short in this game and long in a real one, which is a good reason to keep the keys in one place.

Step 8 — Fall back to English for a missing key​

Add an event with the condition Locale Data: On JSON Loaded:

  • Condition: Locale Data: On JSON Loaded.
  • Condition: Locale Data: "/strings/dialogue.rook.greeting" exists.
  • Action: Dialogue Text : Set alterable string to GetString( "Locale Data", "/strings/dialogue.rook.greeting" ).

And a second event for the case in which the key is absent:

  • Condition: Locale Data: On JSON Loaded.
  • Condition: Locale Data: NOT "/strings/dialogue.rook.greeting" exists.
  • Action: Dialogue Text : Set alterable string to GetString( "Fallback Data", "/strings/dialogue.rook.greeting" ).

The two events are the same line of the game seen from two sides. When a translation is forgotten, the player reads the English sentence instead of an empty box.

Step 9 — Localise a dialogue​

The dialogue of an NPC stores keys, not sentences:

{
  "npc_id": "npc_elder_rook",
  "lines": [
    {"line_id": "greeting", "next": "quest"},
    {"line_id": "quest", "next": "end"}
  ]
}

The event that shows a line builds the key from the NPC and the line:

  • Condition: Dialogue Line is clicked.
  • Action: Special : Set Translation Key to "dialogue." + npc_id("Dialogue Line") + "." + line_id("Dialogue Line").
  • Action: Dialogue Text : Set alterable string to GetString( "Locale Data", "/strings/" + Translation Key ).

The dialogue document never changes when a language changes, because it never contained the text.

Step 10 — Let the player choose a language​

Add an event with the condition Language Selector is clicked:

  • Action: Special : Set Locale Id to LocaleId("Language Selector").
  • Action: Locale Data : Load JSON from file at Apppath$ + "locale_" + Locale Id + ".json".

The second action reloads the dictionary. When it finishes, the event of Step 7 rewrites the labels.

Step 11 — Store the choice​

Add an event with the condition Save Settings is clicked:

  • Action: Settings Data : Set string Locale Id at "/" with key "locale".
  • Action: Settings Data : Save JSON to file at Apppath$ + "settings.json".

The value of the global variable is written, not a literal, so the event works for every language.

I. Expected Behavior​

Before the player chooses a language​

The index keeps the default:

{
  "locales": ["en", "pt-BR"],
  "current": "en",
  "fallback": "en"
}

The menu shows Start Game, the health readout shows HP and the file settings.json does not exist yet.

After the player chooses Portuguese​

The menu shows Iniciar jogo, the health readout shows Vida, and the settings file holds the choice:

{
  "locale": "pt-BR",
  "music_volume": 80,
  "show_hints": 1
}

The dictionary file of the language is a separate document and does not change:

{
  "locale": "pt-BR",
  "language_name": "Português",
  "strings": {
    "menu.start": "Iniciar jogo",
    "menu.options": "Opções",
    "hud.hp": "Vida",
    "dialogue.rook.greeting": "Bem-vindo a Emberfall, viajante."
  }
}

After a key is added to the game and not to the dictionary​

The English dictionary holds the new key and the Portuguese dictionary does not:

{
  "locale": "en",
  "strings": {
    "shop.new_stock": "New stock has arrived."
  }
}

The label shows New stock has arrived. in Portuguese, because the fallback dictionary answered. No event changes and no dictionary is edited at runtime.

J. Edge Cases & Error Handling​

SituationWhat happensHandling
The preferences file does not existThe load fails and the error branch runsTake the language from the index and write the preferences on the first save.
The dictionary of the chosen language is missingThe load fails and On Error runsShow the menu in the fallback language, and report the missing file in the log.
The dictionary has a key with an empty textThe label is emptyCheck the existence of the key and, when it exists but is empty, compare the text with an empty string in Fusion.
A key is absent from the dictionaryThe fallback dictionary answersUse the group of Step 8 for every label that comes from a dictionary.
The identifier of the language contains a character that breaks the file nameThe file is not foundKeep the identifiers short, without spaces and with the same characters used in the file names.
The game runs on HTML5Apppath$ has no meaningUse a browser reference per language, such as storage://locale_pt-BR, and read the platform-specific file guide.
The index lists a language whose file does not existThe load of that dictionary failsCompare the list of the index with the files that ship with the game before a release.
Two dictionaries disagree on a keyThe player sees one of themCompare the keys of the dictionaries during the tests of the localization.
The player changes the language while a dialogue is openThe current line keeps the old text until the next lineRewrite the open dialogue in the refresh event of Step 7.
The chosen language is written with a different caseThe file is not foundUse the identifier exactly as it appears in the index.

K. Runtime Compatibility​

The system depends on the file operations and on the insertion and change of values of the extension.

TargetFile workValue changesNotes
WindowsImplemented and testedImplemented and testedApppath$ resolves to the folder of the exported application.
AndroidImplemented, not verified by an automated checkImplemented, not verified by an automated checkWrites inside the sandbox of the application. Test the export.
HTML5Implemented and testedImplemented and testedUse one browser reference per language. The origin storage holds the dictionaries and the preferences.
macOSUnknownUnknownNo separate build was verified.
iOSImplemented, not verified by an automated checkImplemented, not verified by an automated checkWrites inside the sandbox of the application. Test the export.

One difference changes the fallback logic. On the native runtime the exists condition accepts a member whose value is null, and on the HTML5 runtime that member is reported as absent. The dictionaries of this guide never store null, so a key that holds null in a hand-edited file falls back to English on both targets. The full matrix is on the runtime compatibility page.

M. Next Steps​

  • Load the fallback only when it is needed. A condition that checks the existence of the key in the chosen dictionary can decide which file to read.
  • Translate the item names from the item database. A single event reads /items/" + Item Id + "/name" and one dictionary entry per item replaces the key of every item.
  • Keep the language of the numbers. The guide writes the digits of the price, the level and the quantity separately, so a dictionary of the formatting rules can follow later.
  • Add a language to the game. Write a new dictionary with the same keys, add its identifier to the index and ship the file. No event changes.
  • Protect the preferences. The extension can validate the file against a JSON schema, which rejects a preferences file that lost a member. See Enable JSON Schema Validation.
