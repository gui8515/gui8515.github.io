Remote Game Configuration

A. Overview​

The balance of Emberfall lives in a document that the studio can replace without shipping a new build. The game reads the remote document when it starts, compares it with the version it understands, applies the values it accepts and falls back to the local copy when anything is wrong.

DifficultyAdvanced
ComplexityHigh — one remote document, one local copy, a validation step and a fallback path
Fusion skillsFrame events, Active objects, String objects, global variables, timers
JSON++ skillsLoading a file over HTTP, reading members with a computed path, comparing versions, writing the values that were applied

Gameplay scenario​

The studio of Emberfall notices that the second boss of the forest is too easy for the players of the last week. A designer edits a document on the server that holds the new health of the boss, the new reward of the festival event and the date the change expires. The next time a player starts the game, the new numbers are in place. The player is offline, or the server is down: the game still starts, with the numbers that ship with the build.

Learning objectives​

By the end of this guide you will be able to:

  • load a configuration from a remote resource with the file Actions of the extension;
  • tell the player whether the configuration arrived, without blocking the start of the game;
  • compare the version of the remote document with the version the build understands;
  • apply the values that were accepted and keep the local values for the rest;
  • describe honestly what the extension does and what belongs to the server.

What you will build​

A remote configuration document, a local copy of the same document, the events that load the remote resource, the events that check its version and its expiry, the events that apply the values, and the fallback that keeps the game playable when the remote copy does not arrive.

B. Prerequisites​

Fusion knowledge you need

  • Frame events and the condition Start of Frame.
  • Timers, to give the remote load a moment before the game decides that it failed.
  • The Active object and the conditions is visible and is invisible.
  • The String object and the action Set alterable string.
  • Global variables on the Special object.

JSON++ concepts you need

  • JSON paths and the reading of a member with a computed path.
  • Missing, null and empty, because a remote document can lack a member that the local copy holds.
  • Conditions and triggers: On JSON Loaded is the continuation of a successful load, On Error is the continuation of a failed one.
  • JSON instance state: the remote copy and the local copy live in two different objects.

Runtime limitations to keep in mind

  • JSON++ Object does not provide a server. It reads a resource that another system publishes. The hosting, the address, the caching and the availability belong to the game or to the service it uses.
  • The browser runtime reaches an HTTP address with a request from the page. The answer must allow the request with the headers of the origin, and the server must answer with status 200. A request that is not allowed fails like a request that never arrived.
  • The browser runtime refuses two file operations at the same time. A load that overlaps another load reports an error.
  • A request that times out leaves the remote state uncertain: the game cannot tell whether the answer was lost or never left the device.
  • The embedded:// reference reads a resource of the exporter and cannot be written. The download:// reference writes a file and cannot be read.

Standard objects used here

String, Counter, Special, Timer, Active, JSON++ Object.

C. Gameplay Scenario​

Emberfall ships with two copies of the same configuration document. One is inside the build, at config.json. The other is published on the address https://config.emberfall.game/config.json.

At the start of the frame the game loads the local copy, which is always present, and then asks for the remote copy. The local copy is the working configuration: the game applies it at once, so the player never waits.

When the remote copy arrives, the game checks three things: the version of the schema, the minimum version of the game that accepts it, and the date it expires. When the three checks pass, the remote values replace the local ones and the game applies them again. When any check fails, the game keeps the local values and writes a line in the log.

The result is that a mistake in the remote document is never worse than not having published it.

D. Final Result​

The finished system behaves like this:

  • The game starts with the configuration that ships with the build and never waits for the network.
  • The remote configuration replaces the local one when it arrives and passes the checks.
  • The player sees a small notice when the balance of the game changed.
  • A remote document that is too old, that is too new or that expired is ignored.
  • A server that is down, an address that does not answer or a request that is not allowed change nothing in the game.

E. JSON Data Structure​

The remote configuration​

{
  "schema_version": 2,
  "issued_at": "2026-02-14T18:32:00Z",
  "expires_at": "2026-03-14T18:32:00Z",
  "min_game_version": "1.2.0",
  "balance": {
    "enemy_health_multiplier": 1.1,
    "damage_taken_multiplier": 1,
    "reward_multiplier": 1.2
  },
  "events": {
    "festival_2026": {"active": 1, "reward_gold": 500}
  }
}

The root object holds six members:

MemberTypeMeaning
schema_versionnumberThe version of the structure of this document. The game knows how to read the versions it was built for.
issued_atstringThe moment the document was published, in the ISO 8601 format.
expires_atstringThe moment the document stops being valid.
min_game_versionstringThe oldest version of the game that understands this document, as major.minor.patch.
balanceobjectThe multipliers that the game applies to the balance of the enemies, the damage and the rewards.
eventsobjectThe temporary events of the game, each one named by its identifier.

The structure of balance is the structure of the presets of the difficulty guide, and the structure of events is a small object per event with a flag and a reward. The game reads both with the same kind of path.

The local copy​

The local copy has the same members, with the values that ship with the build:

{
  "schema_version": 2,
  "issued_at": "2026-01-01T00:00:00Z",
  "expires_at": "2026-12-31T00:00:00Z",
  "min_game_version": "1.0.0",
  "balance": {
    "enemy_health_multiplier": 1,
    "damage_taken_multiplier": 1,
    "reward_multiplier": 1
  },
  "events": {
    "festival_2026": {"active": 0, "reward_gold": 0}
  }
}

Keeping the two documents identical in shape is what makes the fallback a single decision instead of a second set of events.

G. Step-by-Step Implementation​

Step 1 — Create the objects​

  1. Add the objects listed above to the frame that starts the game.
  2. Set the global variable Game Version to the version of the build.
  3. Place the Network Label invisible in the frame editor.

Step 2 — Load the local copy first​

Add a Start of Frame event:

  • Condition: Start of Frame.
  • Action: Local Config : Load JSON from file at Apppath$ + "config.json".

The local copy is loaded first and applied at once, so the game never waits for the network.

Step 3 — Apply the local values​

Add an event with the condition Local Config: On JSON Loaded:

  • Action: Balance Data : Set number GetNumber( "Local Config", "/balance/enemy_health_multiplier" ) at "/balance" with key "enemy_health_multiplier".
  • Action: Balance Data : Set number GetNumber( "Local Config", "/balance/damage_taken_multiplier" ) at "/balance" with key "damage_taken_multiplier".
  • Action: Balance Data : Set number GetNumber( "Local Config", "/balance/reward_multiplier" ) at "/balance" with key "reward_multiplier".
  • Action: Status Text : Set alterable string to "Using the configuration of the build".

The Balance Data object holds the values the game really uses. The presets of the difficulty guide read from it, so a change of the remote document changes the game without touching another event.

Step 4 — Ask for the remote copy​

In the same event, after the local copy is applied:

  • Action: Remote Config : Load JSON from file at "https://config.emberfall.game/config.json".
  • Action: Load Timer : Start timer 120.

The timer is the safety net. When the remote copy never arrives, the game has already started with the local values, and the timer only writes a line in the log.

Step 5 — Check the version of the schema​

Add an event with the condition Remote Config: On JSON Loaded:

  • Condition of the group: Remote Config: Is "/schema_version" equal to 2?.
  • Action: Balance Data : Set number 1 at "/" with key "remote_valid".

A document that does not carry the version the build understands is refused. The check is a comparison of a number, and the version the build accepts is written in the event, next to the code that reads it.

Step 6 — Check the minimum version of the game​

Add a group under the same event:

  • Condition of the group: Remote Config: Is "/min_game_version" equal to Game Version?.
  • Action: Balance Data : Set number 1 at "/" with key "remote_valid".

A configuration published for a newer build carries a higher min_game_version, and this group refuses it. In a game with many versions, compare the three numbers of the version separately.

Step 7 — Apply the remote values​

Add an event with the condition Balance Data: Is "/remote_valid" equal to 1?:

  • Action: Balance Data : Set number GetNumber( "Remote Config", "/balance/enemy_health_multiplier" ) at "/balance" with key "enemy_health_multiplier".
  • Action: Balance Data : Set number GetNumber( "Remote Config", "/balance/damage_taken_multiplier" ) at "/balance" with key "damage_taken_multiplier".
  • Action: Balance Data : Set number GetNumber( "Remote Config", "/balance/reward_multiplier" ) at "/balance" with key "reward_multiplier".
  • Action: Network Label : Set visible.
  • Action: Status Text : Set alterable string to "Balance updated".

The remote values replace the local ones in the same object, and the events that read the balance read them again.

Step 8 — Handle a failed load​

Add an event with the condition Remote Config: On Error:

  • Action: Status Text : Set alterable string to "Using the configuration of the build".
  • Action: Status Text : Set alterable string to GetError( "Remote Config" ).

The second action overwrites the first, and the detailed message of the extension replaces the friendly one. When the message is meant for the player, keep the friendly text and send the technical one to the log of the game.

Step 9 — Handle a load that never answers​

Add an event with the condition Load Timer: On timer:

  • Action: Status Text : Set alterable string to "The remote configuration did not arrive".

The game keeps the local values, because the local values were applied before the request was made.

Step 10 — Read a temporary event​

Add an event with the condition Remote Config: On JSON Loaded:

  • Action: Festival Flag : Set counter to GetNumber( "Remote Config", "/events/festival_2026/active" ).

The events of the configuration are read the same way as the balance. A game with many events walks them with a loop over /events.

I. Expected Behavior​

The local copy, applied at the start of the frame​

{
  "schema_version": 2,
  "balance": {
    "enemy_health_multiplier": 1,
    "damage_taken_multiplier": 1,
    "reward_multiplier": 1
  }
}

The Balance Data object holds the same values, and the status line reads Using the configuration of the build.

The remote copy arrives and passes the checks​

{
  "schema_version": 2,
  "issued_at": "2026-02-14T18:32:00Z",
  "expires_at": "2026-03-14T18:32:00Z",
  "min_game_version": "1.2.0",
  "balance": {
    "enemy_health_multiplier": 1.1,
    "damage_taken_multiplier": 1,
    "reward_multiplier": 1.2
  },
  "events": {
    "festival_2026": {"active": 1, "reward_gold": 500}
  }
}

The Balance Data object now holds the remote values, the notice appears and the status line reads Balance updated. A wolf with forty health now starts with Floor(40 * 1.1), which is 44.

The remote copy is refused​

The document is the same, but min_game_version is 2.0.0 and the build is 1.2.0. The Balance Data object keeps the local values:

{
  "remote_valid": 0,
  "balance": {
    "enemy_health_multiplier": 1,
    "damage_taken_multiplier": 1,
    "reward_multiplier": 1
  }
}

The status line reads Using the configuration of the build and the game plays exactly as it did before.

J. Edge Cases & Error Handling​

SituationWhat happensHandling
The server is downThe load fails and On Error runsThe local values are already applied. Show the friendly message and log the detail.
The request times outThe state of the remote copy is uncertainThe timer ends the wait and the local values stay in place.
The answer is not allowed by the browserThe load fails like any other failureThe service must allow the origin of the game. Test it from a page served by the same origin.
The answer is not JSONThe document is not replacedKeep the local values and report the failure.
The remote document has a newer schema_versionThe check of Step 5 refuses itPublish the document with the version the build understands, or ship a build that understands the new one.
The remote document is for a newer buildThe check of Step 6 refuses itCompare the version before applying anything.
The remote document expiredThe game applies it anyway unless it checks the dateCompare expires_at with the clock of the game before applying the values.
A member is missing in the remote documentThe expression returns a fallback of 0 and a multiplier of 0 breaks the balanceCheck the existence of each member before applying it, and keep the local value when it is absent.
A multiplier is out of rangeThe balance becomes impossibleClamp the values in the game, and validate them on the server that publishes them.
The remote document holds a value the game does not understandThe document is loaded and the member is ignoredThe game reads the members it knows and ignores the rest.
The game runs on HTML5The request comes from the pageUse an address that allows the origin, and remember that the file operations of the browser runtime cannot overlap.

K. Runtime Compatibility​

The system depends on the file operations of the runtime.

TargetFile workNotes
WindowsImplemented and testedA native build reaches the address with the network stack of the system.
AndroidImplemented, not verified by an automated checkThe application needs the permission of the network, and the export must declare it.
HTML5Implemented and testedThe request comes from the page, so the answer must allow the origin. A concurrent file operation is refused.
macOSUnknownNo separate build was verified.
iOSImplemented, not verified by an automated checkThe application needs the permission of the network. Test the export.

The extension reads and parses the answer; it does not host it, does not sign it and does not check it. The full matrix is on the runtime compatibility page.

M. Next Steps​

  • Check the expiry. Compare expires_at with the clock of the game and refuse a document that expired.
  • Publish the events in a loop. A loop over /events reads every event of the configuration and opens the ones that are active.
  • Cache the last good copy. Write the accepted document in the preferences file, so a game that starts offline uses the last configuration the studio published.
  • Validate on the server. The extension can validate a document against a JSON schema, which rejects a malformed configuration before it reaches the players. See Enable JSON Schema Validation.
  • Protect the address. Serve the configuration over HTTPS and keep the publishing key out of the document: anything the document holds can be read by the players.
