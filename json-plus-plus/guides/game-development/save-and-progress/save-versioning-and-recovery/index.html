Save Versioning and Recovery

A. Overview​

Every change to the format of the run file breaks the saves that were written before it. A new member appears, a member is renamed, a section is split in two. The player who returns to the updated build finds a file the game does not understand, and the run is lost unless the game knows how to read it.

This guide makes that situation impossible to lose a run over. Every document the game writes to disk carries the number of the format it follows as its first member. On load, the game compares that number with the version it expects, applies the migrations that lead from the old format to the current one, and writes the result back. A file that the game cannot read at all falls back on a copy of the last save that worked, and a copy that cannot be read either leaves the player with a new run instead of a broken application.

The guide also states plainly what the recovery cannot do. A file that was damaged on the disk is not rebuilt, and the minutes the player lost are lost.

DifficultyAdvanced
ComplexityHigh — three versions of the format, a migration chain, a backup file and three levels of recovery
Fusion skillsFrame events, the order in which Fusion runs the events of a frame, Active and Counter objects, expressions
JSON++ skillsAbsolute paths, comparing a member with a value, inserting and moving members, copying a document into another instance, searching for a key, error handling

Gameplay scenario​

Emberfall shipped its first version in January. The run file of that version holds the hero and nothing else. In February the game added the progression, and in March it recorded the checkpoint as a complete record instead of a single identifier. The player who bought the game in January and comes back in March has a file from January.

The game reads the number at the top of the file, sees 1, and knows exactly what to do: it creates the sections that the February build added, it renames the member that March renamed, and it builds the checkpoint record from the identifier that January wrote. The run continues in the village square with the same gold and the same inventory. When the game closes, the file carries the number 3, and the next launch reads it without touching it.

A file can also be damaged. A player copies the file to another machine, edits it by mistake, or the disk fails. The file no longer holds valid JSON, and the game cannot parse it. It reads the copy of the last save that worked, which is one or two minutes old, and the player loses those minutes rather than the run.

If the copy is missing too, the game starts a new run and says so. It never pretends that a run was restored when it was not.

Learning objectives​

By the end of this guide you will be able to:

  • store the version of the format as the first member of every document that reaches the disk;
  • detect a file written by an older build and apply the migrations that lead to the current format;
  • add a new member to the format without losing the value that a missing member would have held;
  • rename or move a member while the game migrates a file;
  • find out whether a member is missing and give it its default value;
  • check the type of the loaded values and repair them when they are wrong;
  • handle a file that cannot be parsed, and a file that comes from a build the game does not know;
  • define a recovery with more than one level, and explain what it cannot repair.

What you will build​

A version number in the run file, a migration chain from version 1 to version 3, a backup file written after every successful save, and the events that detect an old file, repair a broken one and fall back on a new run.

B. Prerequisites​

Fusion knowledge you need

  • Frame events such as Start of Frame and the order in which Fusion runs the events of a frame.
  • The difference between a frame condition and a group condition, and the fact that a group runs after the actions of its event.
  • Active objects, the is clicked condition and the Collision between Active and Active condition.
  • The Counter and String objects with their Set counter and Set alterable string actions.
  • Reading an object's position with X("Player") and Y("Player"), and the value of a Counter with value("HP Counter").
  • The fact that a group with several conditions runs only when every one of them is true.

JSON++ concepts you need

  • JSON paths: every path is absolute, so a migration reads and writes the same node whatever the navigation position is.
  • Missing, null and empty: a member that an old file does not have is absent, and giving it a default is a different action from changing it.
  • Conditions and triggers: On JSON Loaded, On JSON Saved to File and On Error are triggers of one instance.
  • Conditions, Missing Values and Numeric Types: the type conditions of the extension tell a number from a text.
  • JSON instance state: two instances keep two documents, so the run and its backup never overwrite each other.

Runtime limitations to keep in mind

  • JSON++ Object has no action that deletes a file. A file that must be abandoned is overwritten with a fresh template.
  • A failed action can leave the document partly changed. A migration that fails half way can leave a document that is neither the old format nor the new one, so the migration writes the file only after every step succeeded.
  • File paths follow the host. Apppath$ + "emberfall_save.json" works on Windows, HTML5 needs a browser reference such as storage://emberfall_save, and the mobile targets write inside the sandbox of the application. See platform-specific file operations.
  • A save emits On JSON Saved to File when the file work completes. On some targets the completion is asynchronous.

Standard objects used here

Active, String, Counter, Special and JSON++ Object. Nothing else is required.

C. Gameplay Scenario​

The run file of Emberfall is a document that the game writes and reads back. While the format of that document stays the same, everything is simple: the game loads it, reads a few members and moves on. The moment the format changes, the simple path stops working.

The first version of the game kept a very short file. It held the version number, the moment of the save and the record of the hero. The second version added two sections: one for the progression of the story and one for the world. The third version added the record of the last checkpoint, the working state of the game and the section that describes the last recovery.

A player who started in January has a file of the first version. The game cannot read the sections that do not exist, and it cannot ignore them either, because they hold the story. So the game migrates the file: it creates the two missing sections with their default values, it renames the member that was renamed in the third version, it builds the checkpoint record from the identifier the first version wrote, and it saves the result with the number 3 at the top. The migration happens in memory, and the file on the disk is written once, at the end. A migration that is interrupted in the middle leaves the old file untouched, and the next launch tries again.

A file can also be unreadable for a different reason. The player edited it, or the disk failed. The game reads the file, the parse fails, and the extension reports the error. There is nothing to migrate in that case, because there is no document. The game reads the backup instead: the copy it writes after every successful save. The backup holds a complete document of the current format, so it needs no migration, and the player is back in the game within a minute or two of the last save.

The last level of the recovery is the new run. When neither the file nor the backup can be read, the game loads an empty template into the run instance and starts again. The message on the screen says exactly that, because a player who loses a run deserves to know it was lost.

D. Final Result​

The completed system behaves like this:

  • Every file the game writes starts with the number of the format it follows.
  • A file written by the January build is opened, migrated and saved again in the March format. The hero keeps the gold, the items and the position of January.
  • A file written by a build the game does not know is not applied to the game. The game reads the backup instead and tells the player what happened.
  • A file that is not valid JSON is reported as unreadable, and the backup is used.
  • A member that a member of the file does not have is given its default value instead of being read as zero.
  • A value of the wrong type is repaired with the default value of the field.
  • When neither the file nor the backup can be read, the game starts a new run and says so.
  • The file is never written in a state that is neither the old format nor the new one.

The root holds six sections:

SectionPurpose
schema_versionThe number of the format. It is the first member because the game reads it before anything else.
saved_atThe moment of the write, produced by the game.
stateThe working state of the game: what is waiting to be saved and how many times the file was written.
recoveryThe result of the last check: whether the file was understood, whether the values were valid, and what the game did about it.
playerThe hero, with the shape shared by every guide of this manual.
last_checkpointThe record of the last checkpoint, with the identifier, the level, the position and the health.
progressionHow far the story has come.
worldThe state of the objects of the world.

Two instances carry the permanent state and one carries the catalogue. The run and the backup live in different instances, so copying the run into the backup never overwrites the run.

G. Step-by-Step Implementation​

Step 1 — Give every document a version​

Add schema_version as the first member of the run file, of the backup file and of the catalogue. The number is a plain number, and it counts the versions of the format, not the versions of the game: the first format is 1, and every change of the shape of the file raises the number.

Write the number of the current build in one place of the project, and read it from there in every event that compares a version. The guide writes the literals 1, 2 and 3 in the events so that they can be read one by one.

Step 2 — Load the file and prepare the recovery section​

Add a Start of Frame event with two actions:

  • Action: Level Catalogue : Load JSON from file at Apppath$ + "checkpoints.json".
  • Action: Save Data : Load JSON from file at Apppath$ + "emberfall_save.json".

The catalogue is loaded first because the migration reads it. The catalogue never changes, so it can also be pasted into the Initial JSON property of the instance; that removes the doubt of reading a catalogue that has not finished loading.

Then add an event with the condition Save Data: On JSON Loaded and a first action:

  • Action: Save Data : Insert object "{""compatible"":0,""values_valid"":0,""status"":""pending""}" at "/" with key "recovery".

This action creates the section of the recovery if the file does not have it, and resets it if it does. The section is working state of the game: the two numbers are the answers of the checks that follow, and the text describes the outcome. Replacing the whole section with the same values keeps the check honest, because every load starts from zero.

Every event of this guide that answers Save Data: On JSON Loaded must be created in the order of the steps that follow. Fusion runs the events of a frame in the order of the event list, and the checks of this guide depend on that order: the migration runs before the validation, the validation before the repair, and the repair before the restore.

Step 3 — Detect the version of the file​

Under the same event, add one group per known version. The first group reads:

  • Condition of the group: Save Data: Is "/schema_version" equal to 1?.
  • Action: Save Data : Insert object "{""chapter"":1,""bosses"":{},""quests_completed"":{}}" at "/" with key "progression".
  • Action: Save Data : Insert object "{""objects"":{},""npc_states"":{}}" at "/" with key "world".
  • Action: Save Data : Set number 2 at "/" with key "schema_version".
  • Action: Save Data : Set number 1 at "/recovery" with key "compatible".
  • Action: Save Data : Set string "migrated" at "/recovery" with key "status".

The second group reads:

  • Condition of the group: Save Data: Is "/schema_version" equal to 2?.
  • Action: Save Data : Insert object "{""id"":"""",""level"":""level_village"",""position"":{""x"":0,""y"":0},""hp"":100,""activated_at"":""""}" at "/" with key "last_checkpoint".
  • Action: Save Data : Copy from "/player/checkpoint" to "/last_checkpoint/id".
  • Action: Save Data : Copy from "/player/position" to "/last_checkpoint/position".
  • Action: Save Data : Set string GetString( "Level Catalogue", "/checkpoints/" + GetString( "Save Data", "/last_checkpoint/id" ) + "/level" ) at "/last_checkpoint" with key "level".
  • Action: Save Data : Set number 100 at "/last_checkpoint" with key "hp".
  • Action: Save Data : Rename key "bosses" to "bosses_defeated" at "/progression".
  • Action: Save Data : Insert object "{""autosave_pending"":0,""pending_checkpoint"":"""",""pending_object"":"""",""save_busy"":0}" at "/" with key "state".
  • Action: Save Data : Set number 3 at "/" with key "schema_version".
  • Action: Save Data : Set number 1 at "/recovery" with key "compatible".
  • Action: Save Data : Set string "migrated" at "/recovery" with key "status".
  • Action: Save Data : Save JSON to file at Apppath$ + "emberfall_save.json".

And the third group reads:

  • Condition of the group: Save Data: Is "/schema_version" equal to 3?.
  • Action: Save Data : Set number 1 at "/recovery" with key "compatible".

The chain works because of the order in which Fusion runs the groups. The first group reads the version 1, raises it to 2 and creates the two missing sections. The second group then reads the version 2, migrates it to 3 and writes the file. The third group reads the version 3 and does nothing but confirm that the file is understood. A file of version 1 passes through the first two groups and reaches the third one, which finds the version 3 that the second group just wrote.

A file whose version is 4, or a file with no version at all, passes through none of the groups. The number in /recovery/compatible stays 0, and Step 8 reads it.

Step 4 — Add a new member with a default value​

The first action of the first group is the whole answer for a member that did not exist. The Insert object action parses a text and writes the result at the path, creating the branch it needs:

Save Data : Insert object "{""chapter"":1,""bosses"":{},""quests_completed"":{}}" at "/" with key "progression"

The action replaces an existing member of that name, so it is only used where the old file is known not to have the member, or where the member may be replaced on purpose. To keep the value of a member that already exists, the game checks it first with the exists condition, or with the search of Step 5.

Step 5 — Migrate a structure that changed​

Three actions of the second group change the shape of the document rather than filling it:

  • Copy from /player/checkpoint to /last_checkpoint/id moves the value of the old member into the new record. The copy keeps the source, so the identifier stays where the rest of the game reads it.
  • Copy from /player/position to /last_checkpoint/position copies the whole position object at once, with its two members.
  • Rename key "bosses" to "bosses_defeated" at "/progression" renames a member inside a section, which is cheaper than copying the value and deleting the old member.

The Move action does the same thing in one step and removes the source, and the Delete item action removes a member the new format does not use. Both report an error when the path does not exist, so they belong to the places where the old file is known to have the member.

Step 6 — Handle a missing property​

A member can be missing from a file that is otherwise correct, for instance when the file was edited by hand. The exists condition answers the question when the member is there:

  • Condition of the group: Save Data: "/progression" exists.
  • Action of the group: Save Data : Set number 1 at "/recovery" with key "progression_present".

The extension has no condition for the opposite case, so the answer for a member that is absent comes from a marker. A second event reads it:

  • Condition of the group: Save Data: Is "/recovery/progression_present" equal to 0?.
  • Action of the group: Save Data : Insert object "{""chapter"":1,""bosses_defeated"":{},""quests_completed"":{}}" at "/" with key "progression".

The marker is a member of the document that the good case sets to 1. It starts at 0 because the action of Step 2 replaces the whole section of the recovery on every load, so a file that is read twice cannot keep the answer of the first read.

The extension offers a second way to ask the same question. The search for a key gives two events, and On Not Results Found is the branch that says the member is not there. It is the right tool when the game asks about several members in the same frame, because a search replaces the collection of results of the previous one. The marker is enough for a single member, and it keeps the whole check inside the document.

Step 7 — Validate the loaded values​

A member can also exist with the wrong type, for instance when a file was edited by hand. Add an event with the condition Save Data: On JSON Loaded and a group with three conditions:

  • Condition of the group: Save Data: Is "/player/hp" a number?.
  • Condition of the group: Save Data: Is "/player/level" a number?.
  • Condition of the group: Save Data: Is "/player/name" a string?.
  • Action of the group: Save Data : Set number 1 at "/recovery" with key "values_valid".

A group with several conditions runs only when every one of them is true, so the number in /recovery/values_valid becomes 1 only when the three values have the right type.

The extension offers no condition for the opposite case, so the repair is a second event that reads the marker:

  • Condition of the group: Save Data: Is "/recovery/values_valid" equal to 0?.
  • Action of the group: Save Data : Set number 100 at "/player" with key "hp".
  • Action of the group: Save Data : Set number 100 at "/player" with key "max_hp".
  • Action of the group: Save Data : Set string "Ari" at "/player" with key "name".
  • Action of the group: Save Data : Set string "recovered" at "/recovery" with key "status".

The repaired values are written into the document, so the repair is saved with the next write of the file and the game reads a consistent document.

Step 8 — Handle a file the game does not know​

Add an event with the condition Save Data: On JSON Loaded:

  • Condition of the group: Save Data: Is "/recovery/compatible" equal to 0?.
  • Action of the group: Migration Report : Set alterable string to "This save came from another version of the game".
  • Action of the group: Backup Data : Load JSON from file at Apppath$ + "emberfall_backup.json".

And the two branches of the backup:

  • Condition: Backup Data: On JSON Loaded.

  • Action: Save Data : Load JSON from string GetJsonText( "Backup Data", 0 ).

  • Condition: Backup Data: On Error.

  • Action: Migration Report : Set alterable string to "No usable save, starting a new run".

  • Action: Save Data : Load JSON from string "{""schema_version"":3,""saved_at"":"""",""state"":{""autosave_pending"":0,""pending_checkpoint"":"""",""pending_object"":"""",""save_busy"":0},""recovery"":{""compatible"":1,""values_valid"":1,""status"":""ok""},""player"":{""name"":""Ari"",""level"":1,""hp"":100,""max_hp"":100,""gold"":0,""checkpoint"":""cp_village_square"",""position"":{""x"":320,""y"":640},""inventory"":[],""equipment"":{""weapon"":""sword_iron"",""armor"":""armor_leather""}},""last_checkpoint"":{""id"":""cp_village_square"",""level"":""level_village"",""position"":{""x"":320,""y"":640},""hp"":100,""activated_at"":""""},""progression"":{""chapter"":1,""bosses_defeated"":{},""quests_completed"":{}},""world"":{""objects"":{},""npc_states"":{}}}".

The copy of the backup goes into the run instance, so the same migration events and the same restore event work on it. The backup is always in the current format, so its migration does nothing.

The last action loads a complete empty document into the run instance. That is the last level of the recovery: a new run with the default hero, in the village square.

Step 9 — Restore the hero​

Add one more event with the condition Save Data: On JSON Loaded, placed after the event of Step 2 and the events of Steps 7 and 8:

  • Condition of the group: Save Data: Is "/recovery/compatible" equal to 1?.
  • Action of the group: Player : Set X Position to GetNumber( "Save Data", "/player/position/x" ).
  • Action of the group: Player : Set Y Position to GetNumber( "Save Data", "/player/position/y" ).
  • Action of the group: HP Counter : Set counter to GetNumber( "Save Data", "/player/hp" ).
  • Action of the group: Gold Counter : Set counter to GetNumber( "Save Data", "/player/gold" ).
  • Action of the group: Status Text : Set alterable string to "Run restored".

The order of the events in the frame is what makes this work. The migration runs first, the validation second, the repair third, and the restore last. The restore therefore always reads a document that has already been migrated and repaired.

The group is skipped when the file was not understood, so the hero is not restored from a file the game cannot interpret. It is restored a moment later from the backup, when the copy has been loaded into the run instance.

Step 10 — Write the backup after a successful save​

Add an event with the condition Save Data: On JSON Saved to File:

  • Action: Backup Data : Load JSON from string GetJsonText( "Save Data", 0 ).
  • Action: Backup Data : Save JSON to file at Apppath$ + "emberfall_backup.json".

The backup is a copy of the document, written by the running build, so it always has the current version and needs no migration of its own.

Writing the backup doubles the number of file operations of a save. A game that saves often can write the backup only on milestones, such as a checkpoint or the defeat of a boss, and accept that a crash between two milestones costs more.

Step 11 — Handle a file that cannot be parsed​

Add an event with the condition Save Data: On Error:

  • Action: Migration Report : Set alterable string to "The save file could not be read".
  • Action: Backup Data : Load JSON from file at Apppath$ + "emberfall_backup.json".

The branch is the same as the one of Step 8, and it reaches the same two outcomes: the backup is used, or a new run starts. The difference is the reason: the file is not valid JSON, or the file cannot be opened.

The On Error trigger reports every error of the instance, and a failed action of the migration reports one as well. A migration that keeps failing therefore repeats the recovery. Test the migration against every old file before the build is published, and give the game a flag of its own if the recovery must happen only once.

After a file that cannot be parsed​

The status line reads The save file could not be read, and then one of two things happens. The backup is loaded, and the hero returns with the state of the last successful save. Or the backup is missing too, the report line reads No usable save, starting a new run, and the hero starts in the village square with 100 health, no gold and an empty inventory.

After a file from a build the game does not know​

The report line reads This save came from another version of the game. The document of the file is not applied to the game: the hero is not restored from it, and its members are not read. The backup takes its place.

J. Edge Cases & Error Handling​

SituationWhat happensHandling
The file has no schema_versionNo version group matches and /recovery/compatible stays 0Treat the file as a file from an unknown build and use the backup.
The file has a version the game does not knowThe sameThe game never applies a document it cannot interpret.
The file is not valid JSONThe load fails and On Error runsLoad the backup, and start a new run if the backup fails too.
The file cannot be openedThe sameThe same. The message of the error says which of the two happened.
The migration fails half wayThe document is partly changed and the file is not writtenThe version stays old, so the next launch retries the migration. Do not write the file before the migration is complete.
The migration keeps failingThe recovery repeats itselfTest the migration against every old file. If the recovery must run only once, guard it with a flag of the game.
A member of the old file has no equivalent in the new oneThe value cannot be carried overGive the new member its default value and accept that the old value is lost.
A member exists with the wrong typeThe type check fails and the value is repairedThe repair writes the default of the field into the document.
The file has no player record at allThe repair writes fail and the hero is not restoredLoad the backup, and start a new run if there is none.
The catalogue is not loaded when the migration reads itThe level of the checkpoint falls back to the default of the migrationThe catalogue never changes; paste it into the Initial JSON property of the instance to remove the doubt.
The backup is older than the current formatThe copy is migrated like a run fileThe backup is written by the running build, so it is always current. A backup from an older build is migrated by the same events.
The disk is full during the migration writeThe write fails and On Error runsThe old file is still on the disk, because the migration writes only at the end. The next launch tries again.
The file was deleted by the playerThe load fails and the backup is usedThe backup becomes the run. It is written over the missing file at the next save.
The application was closed during a writeThe file may be truncatedThe truncated file cannot be parsed, so the backup is used. The minutes since the last successful save are lost.
A path contains a slash in a keyThe path is split at the slashEncode the slash as ~1 and the tilde as ~0 inside a path.
The game runs on HTML5Apppath$ has no meaningUse a browser reference such as storage://emberfall_save and read the platform-specific file guide.
The game runs on Android or iOSThe files land in the sandbox of the applicationUse the path documented for that target and test the export, because a sandbox path differs from the one of a desktop export.

One rule deserves emphasis. The migration writes the file once, at the end, and never in the middle. A migration that writes twice leaves a file that is half old and half new when the second write is interrupted, and that file is the worst case of all, because it parses and its values are wrong.

K. Runtime Compatibility​

The system relies on four groups of features: file operations, comparisons, changes of the structure and error reporting.

TargetFile workComparisons and structureError reportingNotes
WindowsImplemented and testedImplemented and testedImplemented and testedApppath$ resolves to the folder of the exported application.
AndroidImplemented, not verified by an automated checkImplemented, not verified by an automated checkImplemented, not verified by an automated checkWrites inside the sandbox of the application. Test the export.
HTML5Implemented and testedImplemented and testedImplemented and testedUse a browser reference for the file. Concurrent file work is rejected, so the run and the backup are written one after the other.
macOSUnknownUnknownUnknownNo separate build was verified.
iOSImplemented, not verified by an automated checkImplemented, not verified by an automated checkImplemented, not verified by an automated checkWrites inside the sandbox of the application. Test the export.

One difference matters for the version comparison. On the native runtime the exists condition accepts a member whose value is null, while the browser runtime reports such a member as absent. A file that holds null in schema_version is therefore treated as a file without a version on the native runtime, and as a file without a version on the browser runtime as well, because the comparison of a missing member yields no match. The full matrix is on the runtime compatibility page.

A second difference matters for the timing of the write. On the browser runtime the completion of a file operation can arrive after the action returns, so the message that reports a migration belongs in the On JSON Saved to File event and not directly under the save action.

M. Next Steps​

  • Keep a list of the versions. A document that names every version of the format and the step that leads to the next one would let the game migrate a file that is several versions behind without one group per version.
  • Write the migration into the file as a script. The extension can write a list of changes and apply it, which turns the migration into data instead of events.
  • Give the player a choice. When the file is from a newer build, the game could keep it and let the player start a new run instead of replacing it with the backup.
  • Number the format of the world too. The catalogue of the world objects changes between versions as well, and the same migration pattern applies to it.
  • Validate the file against a schema. The Enable JSON Schema Validation property checks a document that is loaded, including one loaded from a text, and tells the game at once that a file does not follow the format it expects.
  • Protect the file. The Enable Encryption property encrypts the file the extension writes, and a file that a player cannot read cannot be edited by mistake.
