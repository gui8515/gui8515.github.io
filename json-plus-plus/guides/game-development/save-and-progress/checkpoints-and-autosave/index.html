Checkpoints and Autosave

A. Overview​

Emberfall is a long action RPG. The hero crosses a village square, a forest bridge and a cavern entrance, and the walk back to the village is tedious. A checkpoint is a brazier that remembers where the hero stood when it was lit, and an autosave is the habit of writing the run to disk before the player can lose anything.

This guide builds both halves. The run file holds the hero, the last checkpoint and the progression. A second file keeps a copy of the state captured at the last checkpoint, so a damaged run file costs the player minutes instead of a whole evening. A third file describes the checkpoints themselves — which level each one belongs to, where the hero appears, and how much health it restores — so the level data, not the event code, decides where the hero comes back to.

DifficultyAdvanced
ComplexityMedium — three JSON documents, one timer and one search
Fusion skillsFrame events, Active objects and collisions, Counter and String objects, the Timer object, global variables, expressions
JSON++ skillsLoading and saving files, absolute paths, searching for a value, writing nested members, copying a document into another instance, error handling

Gameplay scenario​

The hero walks into the forest and lights the brazier at the bridge. A short message confirms it, and the game writes the run to disk. Twenty minutes later the hero dies to a wolf. The defeat screen appears, and choosing to continue brings the hero back to the bridge with the health the brazier restores and the gold and items the hero carried at that moment.

The player never presses a save button. The game saves when the hero lights a brazier, and it saves on a timer while the run has changed since the last write. Walking back and forth over the same brazier does not produce one file write per frame. If the run file cannot be read at the next launch, the game opens the copy written at the last brazier instead of throwing the player back to the title screen.

Learning objectives​

By the end of this guide you will be able to:

  • give a checkpoint object a stable identifier and let the level data decide what that identifier means;
  • record the identifier, the level, the position and the health of a checkpoint in one JSON document;
  • write a run to disk from a timer without filling the disk with identical files;
  • use a search to ask the document whether a checkpoint has already been recorded, and act on the answer;
  • restore the hero at the last checkpoint after a defeat;
  • recover from a run file that is missing, unreadable or damaged, by falling back to the checkpoint copy.

What you will build​

A run file (emberfall_save.json), a checkpoint copy (emberfall_checkpoint.json), a checkpoint catalogue (checkpoints.json), the checkpoint objects of the three levels, and the events that light a brazier, write the run, restore the hero and repair a broken save.

B. Prerequisites​

Fusion knowledge you need

  • Frame events such as Start of Frame and how an event with a condition runs only when that condition is true.
  • The difference between a frame condition and a group condition under an event, and the order in which Fusion runs an event, its groups and the next event.
  • Active objects, the Collision between Active and Active condition and the is clicked condition.
  • The Counter and String objects, with their Set counter and Set alterable string actions.
  • The Timer object and its On timer event, used here as the heartbeat of the autosave.
  • Reading an alterable of an Active by its name, for example hp("Player") for a number and CheckpointID("Village Square Checkpoint") for a text.
  • Reading an object's position with X("Player") and Y("Player"), and the value of a Counter with value("HP Counter").

JSON++ concepts you need

  • JSON paths: every path in this guide is absolute and begins with /, so it selects the same node whatever the navigation position is.
  • Missing, null and empty: an absent member, a member holding null and an empty value are three different states, and a run file can hold all three.
  • Conditions and triggers: On JSON Loaded, On JSON Saved to File and On Error are triggers of one instance, not state checks of the whole application.
  • JSON instance state: each JSON++ Object keeps its own document, its own navigation position and its own search results, which is why this guide uses three instances.
  • Search results and their lifetime: a search stores a result collection that belongs to the instance that ran it, and the next search replaces it.

Runtime limitations to keep in mind

  • JSON++ Object has no action that deletes a file. A run file that must be abandoned is overwritten with a fresh template, and the index or the slot entry is marked as free.
  • File paths follow the host. Apppath$ + "emberfall_save.json" works on Windows, HTML5 needs a browser reference such as storage://emberfall_save, and the mobile targets write inside the sandbox of the application. See platform-specific file operations.
  • A save emits On JSON Saved to File when the file work completes. On some targets the completion is asynchronous, so the follow-up work belongs in that event and not directly under the save action.
  • Concurrent file work is rejected on the browser runtime. The three documents of this guide are written one after the other, never in the same frame.

Standard objects used here

Active, String, Counter, Timer, Special and JSON++ Object. Nothing else is required.

C. Gameplay Scenario​

Emberfall opens in the village. The hero walks out of the square, follows the forest path, and crosses the bridge. At the bridge a brazier burns with a cold light. When the hero touches it, the brazier takes fire and a line of text says Checkpoint reached.

From that moment the game knows two things: the hero stands at the bridge, and the hero has the health that the bridge restores. Both facts are written into the run file, together with the gold, the items and the progression, so that the file always describes a complete run.

The forest is long, and the hero may fight for twenty minutes without touching another brazier. The game therefore keeps a timer running. Every two minutes the timer asks a single question: has anything changed since the last write? If nothing changed, nothing is written. If the hero picked up the cavern key, fought the warden or opened a chest, the run is written to disk at the next tick of the timer. The hero never sees a save message for those writes, because they are routine.

The braziers are also the points where the hero can fall back. When the health reaches zero, the game shows a defeat screen. Choosing to continue reads the last checkpoint from the run file, asks the catalogue which level that checkpoint belongs to, opens that level, places the hero at the position the catalogue gives and restores the health the brazier offers. Everything the hero collected after the brazier stays collected; the hero simply starts again from the brazier.

One failure case remains. A write can fail: the disk can be full, the browser can refuse the storage, the application can be closed in the middle of the write. That is why the guide writes a second file whenever a brazier is lit. The copy holds the whole run as it was at the brazier. When the next launch finds a run file that cannot be read, the game opens the copy instead, and the player is back at the brazier rather than at the title screen.

D. Final Result​

The completed system behaves like this:

  • Touching a brazier lights it, restores the health the brazier offers and writes the run to disk. The message Checkpoint reached confirms it.
  • Walking over the same brazier again while it is already lit does not write the file again.
  • The hero collects the cavern key, and the next tick of the timer writes the run. Nothing is written while the run has not changed.
  • A defeat followed by Continue brings the hero back to the last brazier, in the level the catalogue names, with the health the brazier restores.
  • A run file that cannot be read at launch is replaced by the copy written at the last brazier. If that copy is unreadable too, the game starts a new run and says so.
  • The game never claims that a run was saved when the file work did not finish.

E. JSON Data Structure​

The run file​

emberfall_save.json is the file the game writes and reads back:

{
  "schema_version": 3,
  "saved_at": "2026-03-08T21:04:11Z",
  "state": {
    "autosave_pending": 0,
    "pending_checkpoint": "",
    "save_busy": 0,
    "save_count": 12
  },
  "player": {
    "name": "Ari",
    "level": 3,
    "hp": 80,
    "max_hp": 100,
    "gold": 250,
    "checkpoint": "cp_forest_bridge",
    "position": {"x": 1280, "y": 512},
    "inventory": [
      {"id": "potion_health", "quantity": 3},
      {"id": "herb_lotus", "quantity": 4}
    ],
    "equipment": {"weapon": "sword_iron", "armor": "armor_leather"}
  },
  "last_checkpoint": {
    "id": "cp_forest_bridge",
    "level": "level_forest",
    "position": {"x": 1280, "y": 512},
    "hp": 100,
    "activated_at": "2026-03-08T21:03:40Z"
  },
  "progression": {
    "chapter": 2,
    "bosses_defeated": {"boss_warden": 1},
    "quests_completed": {"quest_slime_cull": 1}
  },
  "world": {
    "objects": {"chest_forest_01": 1},
    "npc_states": {"npc_elder_rook": "quest_given"}
  }
}

The root object holds the version, the moment of the save and five sections. schema_version is the first member because every document this extension writes to disk carries its version first; Save Versioning and Recovery shows what happens when that number does not match the build.

state is the working section of the game:

MemberTypeMeaning
autosave_pendingnumber1 when the live run differs from the file on disk. The game clears it before a write and sets it again when something changes.
pending_checkpointstringThe identifier of the checkpoint the hero is touching right now. It carries a value from one event to the next.
save_busynumber1 while a file operation is in flight. The timer waits for it, and a file written while it was 1 shows that the application stopped during a write.
save_countnumberHow many times the game has written the run file. It is useful while tuning the autosave and harmless afterwards.

player keeps the shape shared by every guide of this manual: the name, the level, the health, the maximum health, the gold, the identifier of the last checkpoint, the position, the inventory and the equipment.

last_checkpoint is the record that the defeat screen reads. It holds the identifier of the brazier, the level that brazier belongs to, the position the hero appears at, the health the brazier restores and the moment it was lit.

progression and world describe how far the run has come. The map form used in bosses_defeated, quests_completed and objects answers the question "is this identifier recorded?" with a single path; Persistent World State develops that choice.

Two rules keep this document consistent with the rest of the manual:

  • Stable identifiers. A checkpoint, a boss and a chest are named by identifiers such as cp_forest_bridge, never by their position in an array. The maps may be reordered or extended without breaking a save.
  • The file owns the truth. The live game state lives in the counters and the Active objects, and the file is the copy that survives a crash.

The checkpoint copy​

emberfall_checkpoint.json is written when a brazier is lit. It has the same shape as the run file, because the recovery path reads it with the same events:

{
  "schema_version": 3,
  "saved_at": "2026-03-08T21:03:40Z",
  "state": {
    "autosave_pending": 0,
    "pending_checkpoint": "cp_forest_bridge",
    "save_busy": 0,
    "save_count": 9
  },
  "player": {
    "name": "Ari",
    "level": 3,
    "hp": 100,
    "max_hp": 100,
    "gold": 250,
    "checkpoint": "cp_forest_bridge",
    "position": {"x": 1280, "y": 512},
    "inventory": [
      {"id": "potion_health", "quantity": 3},
      {"id": "herb_lotus", "quantity": 4}
    ],
    "equipment": {"weapon": "sword_iron", "armor": "armor_leather"}
  },
  "last_checkpoint": {
    "id": "cp_forest_bridge",
    "level": "level_forest",
    "position": {"x": 1280, "y": 512},
    "hp": 100,
    "activated_at": "2026-03-08T21:03:40Z"
  }
}

The copy is written first, and the run file is written when the copy reports success. A failure of the run file therefore leaves a copy that holds the state of the brazier, and a failure of the copy leaves the run file alone.

The checkpoint catalogue​

checkpoints.json describes the checkpoints of the three levels. It never changes during a session:

{
  "schema_version": 1,
  "checkpoints": {
    "cp_village_square": {
      "level": "level_village",
      "position": {"x": 320, "y": 640},
      "hp": 100
    },
    "cp_forest_bridge": {
      "level": "level_forest",
      "position": {"x": 1280, "y": 512},
      "hp": 100
    },
    "cp_cavern_entrance": {
      "level": "level_cavern",
      "position": {"x": 240, "y": 96},
      "hp": 60
    }
  }
}

checkpoints is an object whose member names are the checkpoint identifiers. Each entry holds the level the checkpoint belongs to, the position where the hero appears, and the health the checkpoint restores. The cavern entrance restores less health, because the cavern is dangerous and the checkpoint sits outside it.

Because the identifiers are the member names, the path to an entry is built from the identifier alone: /checkpoints/cp_forest_bridge/position/x. No search and no array index are involved.

F. Clickteam Fusion Object Setup​

ObjectTypeRole in the system
Save DataJSON++ ObjectHolds the run document. Reads the hero back at the start of the frame and writes emberfall_save.json.
Checkpoint DataJSON++ ObjectHolds the copy written at a brazier. Receives a copy of the run document and writes emberfall_checkpoint.json.
Checkpoint Level DataJSON++ ObjectHolds the checkpoint catalogue. Answers which level a checkpoint belongs to, where the hero appears and how much health it restores.
Village Square Checkpoint, Forest Bridge Checkpoint, Cavern Entrance CheckpointActiveThe braziers. Each carries its identifier in the alterable string CheckpointID.
PlayerActiveThe hero. Receives the restored position and the health of the checkpoint.
HP CounterCounterThe live health. Written into the run file and read back from it.
Gold CounterCounterThe live gold. Written into the run file and read back from it.
Level CounterCounterThe level of the hero. Written into the run file and read back from it.
Autosave TimerTimerThe heartbeat of the autosave. Its On timer event asks whether the run changed.
Cavern KeyActiveA pickup. Clicking it marks the run as changed.
Continue ButtonActiveThe button of the defeat screen. Clicking it returns the hero to the last checkpoint.
Target LevelStringHolds the identifier of the level the last checkpoint belongs to. The game opens that level.
Status TextStringThe message line. Reports a checkpoint, a save and a recovery.
SpecialSpecialHolds the global variables of the game.

Three JSON++ Object instances are used on purpose. Each one keeps its own document, its own navigation position and its own search results, so the run, the copy and the catalogue never interfere with each other.

The Special object holds one global variable, Save Busy, that the game sets to 1 while a write is in flight. It is a convenience for the game's own events; every decision that the guide depends on is taken with the document itself.

G. Step-by-Step Implementation​

Step 1 — Create the objects and the level data​

  1. Create a frame named Village, a frame named Forest and a frame named Cavern.
  2. Add the objects listed in the previous section to each frame that needs them. The Save Data and Checkpoint Level Data objects are needed in every frame.
  3. Place one brazier Active in each level and name it after its level: Village Square Checkpoint, Forest Bridge Checkpoint, Cavern Entrance Checkpoint.
  4. On each brazier, create an alterable string named CheckpointID and type the identifier of that brazier: cp_village_square, cp_forest_bridge or cp_cavern_entrance.
  5. Create checkpoints.json next to the exported application and fill it with the catalogue shown in the previous section.
  6. Set the Default JSON Path property of Checkpoint Level Data to the file if you want the game to load the catalogue without an event. The guide loads it explicitly so the file can be edited without rebuilding the application.

Step 2 — Load the catalogue and the run at the start of the frame​

Add a Start of Frame event with two actions:

  • Action: Checkpoint Level Data : Load JSON from file at Apppath$ + "checkpoints.json".
  • Action: Save Data : Load JSON from file at Apppath$ + "emberfall_save.json".

The catalogue is loaded first because the events that light a brazier read it. If the run file is missing or damaged, the On Error branch of Step 10 runs instead.

Step 3 — Restore the hero from the run file​

Add an event with the condition Save Data: On JSON Loaded:

  • Action: Player : Set X Position to GetNumber( "Save Data", "/player/position/x" ).
  • Action: Player : Set Y Position to GetNumber( "Save Data", "/player/position/y" ).
  • Action: HP Counter : Set counter to GetNumber( "Save Data", "/player/hp" ).
  • Action: Gold Counter : Set counter to GetNumber( "Save Data", "/player/gold" ).
  • Action: Level Counter : Set counter to GetNumber( "Save Data", "/player/level" ).
  • Action: Save Data : Set number 0 at "/state" with key "autosave_pending".
  • Action: Status Text : Set alterable string to "Run restored".

This is the event that applies the data to the game world. JSON++ Object reads; the Fusion actions move. Changing a number in the document does not move the hero by itself.

The last two actions deserve a word. The file on disk was written while the run was complete, so autosave_pending is already 0 there. Writing it again makes the rule explicit and protects the case of a file written by an older build that still carried the flag.

Step 4 — Light a brazier​

Add one event per brazier. The first one reads:

  • Condition: Player collides with Village Square Checkpoint.
  • Action: Save Data : Set string CheckpointID("Village Square Checkpoint") at "/state" with key "pending_checkpoint".
  • Action: Save Data : Search for value CheckpointID("Village Square Checkpoint") at "/player" (Exact: 1).

The first action records which checkpoint the hero is touching. The second asks the document whether that identifier is already the one in /player/checkpoint.

The search is the guard of this guide, so it is worth being precise about it. The search collects a result for every member of /player whose value is exactly cp_village_square. While the hero stands on the brazier, the value in /player/checkpoint is that identifier, so the search finds it and the game does nothing. The moment the hero lights a brazier that is not the current one, the search finds nothing, and the On Not Results Found branch of Step 5 does the work.

A Fusion collision is true on every frame while the two objects overlap. The search runs on each of those frames, and it is cheap; the write that follows is not repeated, because the branch only runs when the identifier is new.

Step 5 — Record the checkpoint and write the copy​

Add an event with the condition Save Data: On Not Results Found. The branch reads the identifier that Step 4 recorded, so one event serves the three braziers:

  • Action: Save Data : Set string GetString( "Save Data", "/state/pending_checkpoint" ) at "/last_checkpoint" with key "id".
  • Action: Save Data : Set string GetString( "Checkpoint Level Data", "/checkpoints/" + GetString( "Save Data", "/state/pending_checkpoint" ) + "/level" ) at "/last_checkpoint" with key "level".
  • Action: Save Data : Set number GetNumber( "Checkpoint Level Data", "/checkpoints/" + GetString( "Save Data", "/state/pending_checkpoint" ) + "/position/x" ) at "/last_checkpoint/position" with key "x".
  • Action: Save Data : Set number GetNumber( "Checkpoint Level Data", "/checkpoints/" + GetString( "Save Data", "/state/pending_checkpoint" ) + "/position/y" ) at "/last_checkpoint/position" with key "y".
  • Action: Save Data : Set number GetNumber( "Checkpoint Level Data", "/checkpoints/" + GetString( "Save Data", "/state/pending_checkpoint" ) + "/hp" ) at "/last_checkpoint" with key "hp".
  • Action: Save Data : Set string GetString( "Save Data", "/state/pending_checkpoint" ) at "/player" with key "checkpoint".
  • Action: HP Counter : Set counter to GetNumber( "Checkpoint Level Data", "/checkpoints/" + GetString( "Save Data", "/state/pending_checkpoint" ) + "/hp" ).
  • Action: Save Data : Set number 1 at "/state" with key "save_busy".
  • Action: Checkpoint Data : Load JSON from string GetJsonText( "Save Data", 0 ).
  • Action: Checkpoint Data : Save JSON to file at Apppath$ + "emberfall_checkpoint.json".

Five of the actions read the catalogue with a path built from the identifier: /checkpoints/ followed by the identifier followed by the member name. The identifier is a stable string, so the path always selects the same node.

The ninth action copies the whole run document into the second instance. GetJsonText serializes the document of Save Data, and the load action parses that text into Checkpoint Data. The tenth action writes that copy to its own file.

The run file is not written here. The browser runtime rejects two file operations at the same time, so the run file is written from the completion of the copy. Add the event that does it:

  • Condition: Checkpoint Data: On JSON Saved to File.
  • Action: Save Data : Set number 0 at "/state" with key "save_busy".
  • Action: Save Data : Save JSON to file at Apppath$ + "emberfall_save.json".
  • Action: Status Text : Set alterable string to "Checkpoint reached".

And the event that handles a copy that could not be written:

  • Condition: Checkpoint Data: On Error.
  • Action: Save Data : Set number 0 at "/state" with key "save_busy".
  • Action: Save Data : Save JSON to file at Apppath$ + "emberfall_save.json".
  • Action: Status Text : Set alterable string to "Checkpoint reached, copy failed".

The run file is written even when the copy fails. The run holds more than the copy, and the copy exists only for the recovery, so a missing copy must not cost the player a run.

The game also writes the moment the brazier was lit into /last_checkpoint/activated_at, and the moment of the write into /saved_at. Both are date and time strings produced by the game itself; the extension stores the text it is given.

Step 6 — Mark the run as changed​

The autosave writes the file when something worth writing happened. The game marks that moment with one member:

  • Action of the pickup event: Save Data : Set number 1 at "/state" with key "autosave_pending".

The same action belongs to the event of the warden, to the event of the chest and to the event that opens a new level. A milestone is not saved on the spot; it is saved at the next tick of the timer, so a busy minute does not produce a dozen files.

Step 7 — Write the run on the timer​

Add an event with the condition Autosave Timer: On timer, and give it a group:

  • Condition of the group: Save Data: Is "/state/autosave_pending" equal to 1?.
  • Condition of the group: Save Data: Is "/state/save_busy" equal to 0?.
  • Action: Save Data : Set number 0 at "/state" with key "autosave_pending".
  • Action: Save Data : Set number value("HP Counter") at "/player" with key "hp".
  • Action: Save Data : Set number value("Gold Counter") at "/player" with key "gold".
  • Action: Save Data : Set number X("Player") at "/player/position" with key "x".
  • Action: Save Data : Set number Y("Player") at "/player/position" with key "y".
  • Action: Save Data : Add number 1 at "/state" with key "save_count".
  • Action: Save Data : Save JSON to file at Apppath$ + "emberfall_save.json".

The group is the whole reason the timer exists. When nothing changed, the flag is 0, the group does not run and no file is written. When something changed, the flag is cleared first, so a second tick during a write finds nothing to do. The second condition keeps the timer away from a write that a brazier has already started, because the browser runtime refuses two file operations at the same time.

The timer interval is the second half of the rule. A timer of two minutes gives the player at most two minutes of progress to lose, and gives the disk one write every two minutes of active play at the worst.

Step 8 — Report the result of the write​

The autosave is a routine operation and the hero never sees it happen. A design that wants a confirmation anyway adds an event with the condition Save Data: On JSON Saved to File:

  • Action: Status Text : Set alterable string to "Progress saved".

This event only runs when the file work completed. A write that failed never reaches it, so the message never claims a save that did not happen. On the browser runtime the completion can arrive after the action returns, which is exactly why the message lives here.

The message of a checkpoint is written in the event of Step 5, which runs before the write of the run file. A game that uses one line for both messages must choose which of the two the player sees last.

Step 9 — Return the hero to the last checkpoint​

Add an event with the condition Continue Button is clicked:

  • Action: Save Data : Set number GetNumber( "Save Data", "/last_checkpoint/hp" ) at "/player" with key "hp".
  • Action: HP Counter : Set counter to GetNumber( "Save Data", "/player/hp" ).
  • Action: Player : Set X Position to GetNumber( "Save Data", "/last_checkpoint/position/x" ).
  • Action: Player : Set Y Position to GetNumber( "Save Data", "/last_checkpoint/position/y" ).
  • Action: Target Level : Set alterable string to GetString( "Checkpoint Level Data", "/checkpoints/" + GetString( "Save Data", "/last_checkpoint/id" ) + "/level" ).
  • Action: Status Text : Set alterable string to "Back to the last checkpoint".

The first action copies the health of the checkpoint into the run document and the second reads it back into the counter. That order matters: the document is the place where the restored value is recorded, and the counter only follows it.

The last action puts the identifier of the level in a String object. The game reads that identifier and opens the matching frame; choosing the frame is the work of the game, not of the extension. Opening the level moves the hero to the coordinates of that level, and the actions that set the position put the hero on the brazier itself.

Step 10 — Recover from a run file that cannot be read​

Add an event with the condition Save Data: On Error:

  • Action: Status Text : Set alterable string to "Run file unavailable, trying the checkpoint".
  • Action: Checkpoint Data : Load JSON from file at Apppath$ + "emberfall_checkpoint.json".

And an event with the condition Checkpoint Data: On JSON Loaded:

  • Action: Save Data : Load JSON from string GetJsonText( "Checkpoint Data", 0 ).

That action copies the copy back into the run instance, so the events of Step 3 restore the hero from it. The On JSON Loaded event of Step 3 runs again at that point, and the hero appears where the hero stood at the last brazier.

Finally, add an event with the condition Checkpoint Data: On Error:

  • Action: Status Text : Set alterable string to "Starting a new run".

When neither file can be read, the game has nothing to restore. It starts a new run and says so, instead of leaving the player in front of an empty screen.

Step 11 — Write the run at the moment of a defeat​

The defeat screen itself does not need to write anything: the state of the run is already on disk, because the autosave ran at the last tick and the brazier wrote a copy when it was lit. If the design asks for a save exactly at the defeat, add the actions of the group of Step 7 to the event of the defeat screen, without the conditions of the group.

  • +Save Data: Is "/state/save_busy" equal to 0?

Read the group from the top. The first flag is the whole decision: 1 means there is something to write, 0 means there is nothing to do. The second flag keeps the timer away from a write that is still running.

The status line reads Checkpoint reached, and the health counter reads 100.

After the hero collects the cavern key and the timer ticks​

The flag /state/autosave_pending was set to 1 by the pickup. The timer clears it, copies the live values into the document and writes the file. The number in /state/save_count grows by one, and the run file now holds the key in the inventory. No message appears on the screen: this write is routine.

After the hero dies and chooses to continue​

The hero is back at 1280, 512 in the forest, the health counter reads the health the bridge restores, and the file on disk is unchanged. The gold, the items and the progression are the ones of the last checkpoint, plus whatever the hero carried out of the forest.

After the run file is damaged​

At the next launch the load of emberfall_save.json fails. The game loads emberfall_checkpoint.json, copies it into the run instance and restores the hero from it. The status line reads Run file unavailable, trying the checkpoint, and the player is back at the bridge.

J. Edge Cases & Error Handling​

SituationWhat happensHandling
The run file does not existThe load fails and On Error runsLoad the checkpoint copy, and if that fails too, start a new run. Never treat a missing file as an empty run.
The run file holds invalid JSONThe document is not replaced and the error text describes the problemFall back to the copy. Keep the error text in a log, show a short message to the player.
The run file was truncated by an interrupted writeThe parse fails and the recovery path runsWrite the copy first and the run file from the completion of the copy, so the copy always holds the state of the brazier.
The catalogue is missingThe lookups return the fallback value and the hero appears at the originTreat the catalogue as part of the application. Ship it with the build and check it in the exported folder.
The catalogue holds an identifier the build does not knowThe lookup selects nothingThe search of Step 4 still works, but the level is unknown. Add the identifier to the catalogue of the new build.
The hero stands on a brazier for many framesThe search runs on every frameThe search finds the identifier after the first activation, so no file is written. Move the brazier if the overlap is unintended.
The player opens a second brazier while the first copy is still being writtenThe browser runtime rejects concurrent file workWait for On JSON Saved to File before writing again. The guide writes the copy and the run file in two different events, so only one file operation is ever in flight.
The write of the copy failsThe error branch of the copy instance runsThe run file is still written. The player keeps the state of the run, and the next brazier writes a new copy.
The write of the run file failsThe error branch of the run instance runsThe copy from the last brazier is still on disk, and the message says the file was unavailable.
The autosave timer fires while a write is in flightThe group finds the busy flag at 1 and does not runThe busy flag is raised before a write and lowered in the completion event, as Step 5 does.
The health of the hero is 0 when the defeat screen appearsThe counters hold 0The defeat event restores the health of the checkpoint before the counters read it.
A path contains a slash in a keyThe path is split at the slashEncode the slash as ~1 and the tilde as ~0 inside a path.
The game runs on HTML5Apppath$ has no meaningUse a browser reference such as storage://emberfall_save and read the platform-specific file guide.
The game runs on Android or iOSThe files land in the sandbox of the applicationUse the path documented for that target and test the export, because a sandbox path differs from the one of a desktop export.

Two rules deserve emphasis. First, a save that was not confirmed is not a save: every message that claims progress was written belongs inside On JSON Saved to File. Second, the copy of the checkpoint is written before the run file, so the file that survives a failure is the one that holds less progress.

K. Runtime Compatibility​

The system relies on three groups of features: file operations, searches, and the change of nested members.

TargetFile workSearchesValue changesNotes
WindowsImplemented and testedImplemented and testedImplemented and testedApppath$ resolves to the folder of the exported application.
AndroidImplemented, not verified by an automated checkImplemented, not verified by an automated checkImplemented, not verified by an automated checkWrites inside the sandbox of the application. Test the export.
HTML5Implemented and testedImplemented and testedImplemented and testedUse a browser reference. Concurrent file work is rejected, so the two writes are never simultaneous.
macOSUnknownUnknownUnknownNo separate build was verified.
iOSImplemented, not verified by an automated checkImplemented, not verified by an automated checkImplemented, not verified by an automated checkWrites inside the sandbox of the application. Test the export.

One difference matters for the guard of Step 4. A search collects results and the two result events are emitted by the instance that ran the search, but the result collection belongs to that instance. The guide never runs a second search on Save Data between the search and its branch, because a new search replaces the previous collection. The full matrix is on the runtime compatibility page.

A second difference matters for the members of the state section. On the native runtime the exists condition accepts a member whose value is null, while the browser runtime reports such a member as absent. The run file never stores null, so both targets agree.

M. Next Steps​

  • Give every checkpoint its own message. The CheckpointID alterable carries the identifier; a second alterable with the text of the message would let the brazier say Checkpoint reached or The bridge is safe without a new event.
  • Store the health of the hero at the brazier. The catalogue holds the health the checkpoint restores. A member in the run file that records the health the hero had at that moment makes the return to the checkpoint exact.
  • Save when the level changes. The event that opens a level marks the run as changed, so a run never ends in a level the file does not know about.
  • Keep several checkpoints in one copy. The copy of the checkpoint is written on every brazier. A file per brazier would let the player choose the checkpoint they return to.
  • Encrypt the run file. The extension can encrypt the file it writes and validate it against a JSON schema. See Enable Encryption and Enable JSON Schema Validation.
  • Follow the world state. The chests, the doors and the switches of the run file are described in Persistent World State.
