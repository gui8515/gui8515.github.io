Persistent World State

A. Overview​

Emberfall is a game about a world that notices what the hero does. The chest in the forest stays open. The gate of the cavern stays unlocked. The warden stays dead. The lever at the ford stays pulled. The hero never finds the same unique item twice, and the people of the village remember the state they were left in.

This guide builds that memory. Every object of the world carries a stable identifier, and the run file records which identifiers have been changed. When the hero comes back to a level, the game asks the document which objects are already in their new state and restores them. The guide also draws the line between what must survive a restart and what must not: the permanent state lives in the run file, the temporary state lives in a second document that is never written to disk.

DifficultyIntermediate
ComplexityMedium — one run document, one catalogue of world objects, one session document
Fusion skillsFrame events, Active objects and collisions, the is clicked condition, alterable values and strings, expressions
JSON++ skillsAbsolute paths built from an identifier, searching for a key, writing nested members, separating two documents, error handling

Gameplay scenario​

The hero opens the chest at the edge of the forest and finds a mana potion. He walks to the cavern, unlocks the gate with the key and defeats the warden. He saves the game and closes the application.

Two hours later he comes back. The title screen offers the run, and the game restores the forest. The chest is open and empty. The lever is still pulled. The gate of the cavern is still open. The warden is still lying on the floor of its arena, and the quest that counted on its defeat still counts it. The hero walks back to the chest and finds nothing there, because the chest has already given its reward.

The village is different too. Elder Rook still stands in the middle of the square with the quest in his hands, because the game recorded the state of the meeting. The merchant still has her stall open. Nothing of this depends on the level the hero is standing in; the state belongs to the world.

Learning objectives​

By the end of this guide you will be able to:

  • give every object of the world a stable identifier and keep that identifier in the object itself;
  • record a change in the world with one write, whatever the kind of object that changed;
  • decide with a single search whether an object was already changed, and act on both answers;
  • restore the objects of a level from the document when the level is entered again;
  • keep the state of the people of the village apart from the state of the objects;
  • separate the state that must survive a restart from the state that must not.

What you will build​

A world section inside the run file, a catalogue of the world objects (world_catalog.json), a session document that never reaches the disk, and the events that record a change, restore a level and keep the temporary state out of the save.

B. Prerequisites​

Fusion knowledge you need

  • Frame events such as Start of Frame and how an event with a condition runs only when that condition is true.
  • The order in which Fusion runs an event, the groups under it and the events that follow it.
  • Active objects, the Collision between Active and Active condition and the is clicked condition.
  • Alterable values and alterable strings of an Active, and the actions that set them.
  • Reading an alterable of an Active by its name, for example WorldID("Forest Chest").
  • The difference between a state condition and a trigger, and why a trigger that belongs to one object instance only fires for that instance.

JSON++ concepts you need

  • JSON paths: the guide builds a path from an identifier, for example /world/objects/ followed by chest_forest_01. The identifier is a stable string, so the path always selects the same node.
  • Missing, null and empty: an object that was never changed has no member in the document, which is different from a member holding a false value.
  • Conditions and triggers: On Results Found and On Not Results Found are the two answers of a search.
  • Search results and their lifetime: the result collection belongs to the instance that ran the search, and the next search replaces it.
  • JSON instance state: two instances keep two documents, two sets of results and two positions in the navigation.

Runtime limitations to keep in mind

  • JSON++ Object has no action that deletes a file. A state that must be forgotten is removed from the document with Delete item, or replaced with a fresh template.
  • File paths follow the host. Apppath$ + "emberfall_save.json" works on Windows, HTML5 needs a browser reference such as storage://emberfall_save, and the mobile targets write inside the sandbox of the application. See platform-specific file operations.
  • A save emits On JSON Saved to File when the file work completes. On some targets the completion is asynchronous, so the follow-up work belongs in that event.
  • The result collection of a search belongs to one instance. Two searches on the same instance in the same frame replace each other.

Standard objects used here

Active, String, Special and JSON++ Object. Nothing else is required.

C. Gameplay Scenario​

The world of Emberfall is built from a handful of objects that change state. A chest opens once. A door unlocks once. A lever is pulled once. The warden dies once. A unique item is picked up once. Those five situations cover every world object of the game, and all five are recorded the same way: the identifier of the object goes into a map of the run, and the map is the memory of the world.

Each of those objects exists twice in the project. It exists as an Active object placed in a level, where it is drawn, clicked and collided with. It exists as an entry of the catalogue, where it is described: which level it belongs to, where it stands, whether its change is permanent and which state it takes once it changes. The Active object holds one identifier, and that identifier is the only thing the two share.

When the hero opens the chest, the game asks the document whether chest_forest_01 is already in the map of the world. The answer decides everything: if it is there, the chest was opened before and the hero gets nothing; if it is not, the game records the change, marks the run as changed and lets the game open the chest.

When the hero enters the forest again, the game restores the world before the level is playable. For every object of the level it asks the same question with the exists condition, and the answer sets the flag of that object. A chest whose flag is set is drawn open and empty. A lever whose flag is set stays pulled. The warden whose flag is set lies still, and the game does not spawn it again.

The people of the village need a little more than a flag. Elder Rook can be idle, hold a quest or wait for the hero to return. His state is a word, and the words live in their own map, one member per person. The game reads the word and plays the matching scene.

One kind of state must not survive. The number of enemies spawned since the level opened, the progress of the tutorial, the fade of the screen: those belong to the session, not to the world. They live in a second document, in a second instance of the object, and no event ever writes that instance to a file. A save of the run can therefore never contain them.

D. Final Result​

The completed system behaves like this:

  • Opening the forest chest records chest_forest_01 in the world map, gives the reward once and never gives it again.
  • The cavern gate stays unlocked after a restart, and the warden stays defeated.
  • The lever at the ford stays pulled, and the bridge it opens stays open.
  • The unique key never appears twice; the world map says it was taken and the level does not create it again.
  • Elder Rook still holds the quest after a restart, and the merchant still has her stall open.
  • Entering a level restores every object of that level before the hero can interact with it.
  • The state of the session, such as the number of enemies spawned or the step of the tutorial, is never written to disk.

E. JSON Data Structure​

The run file​

The world is one section of the run file. The rest of the file is the run of the hero and is described in Checkpoints and Autosave:

{
  "schema_version": 3,
  "saved_at": "2026-03-08T21:12:02Z",
  "state": {
    "autosave_pending": 1,
    "pending_checkpoint": "",
    "pending_object": "",
    "save_count": 14
  },
  "player": {
    "name": "Ari",
    "level": 4,
    "hp": 62,
    "max_hp": 100,
    "gold": 310,
    "checkpoint": "cp_cavern_entrance",
    "position": {"x": 240, "y": 96},
    "inventory": [
      {"id": "potion_health", "quantity": 3},
      {"id": "potion_mana", "quantity": 1},
      {"id": "key_cavern", "quantity": 1}
    ],
    "equipment": {"weapon": "sword_iron", "armor": "armor_chain"}
  },
  "world": {
    "objects": {
      "chest_forest_01": 1,
      "door_cavern_gate": 1,
      "switch_forest_01": 1,
      "boss_warden": 1,
      "key_cavern": 1
    },
    "npc_states": {
      "npc_elder_rook": "quest_given",
      "npc_merchant_bella": "shop_open",
      "npc_warden_dorn": "idle"
    }
  }
}

world holds two maps. objects records the world objects that the hero has already changed, and npc_states records the state of the people of the village.

MemberTypeMeaning
world/objectsobjectOne member per world object that has been changed. The member name is the identifier of the object and the value is 1.
world/npc_statesobjectOne member per person. The member name is the identifier of the person and the value is the name of the state, such as quest_given or idle.
state/pending_objectstringThe identifier of the object the hero is touching right now. It carries a value from one event to the next.

Why a map and not a list. The run file written by Multiple Save Slots lists the opened chests in an array, and an array is compact. A map costs one pair of braces per entry, and it buys the question this guide asks dozens of times: is this identifier recorded? With a map the answer is a single path, /world/objects/chest_forest_01, and the exists condition answers it without a search. With an array the answer needs a search over the values, and the result collection of a search belongs to one instance and is replaced by the next search. When a level holds many objects and the game restores them one after the other, the map is the shape that keeps the code readable.

Why the value is 1 and not a state. Every object of this guide has two states: the state the player found, and the state the player left it in. A flag of 1 means the second one. The catalogue says what the second state looks like, so the run file does not have to repeat it. A game whose objects have more than two states stores the name of the state instead of the flag, and the same paths keep working.

The catalogue of world objects​

world_catalog.json describes every object of the world. It belongs to the game, not to the run, and it never changes during a session:

{
  "schema_version": 1,
  "world_objects": {
    "chest_forest_01": {
      "type": "chest",
      "level": "level_forest",
      "position": {"x": 640, "y": 300},
      "persistent": true,
      "state": "open",
      "reward": {"id": "potion_mana", "quantity": 1}
    },
    "chest_village_02": {
      "type": "chest",
      "level": "level_village",
      "position": {"x": 210, "y": 580},
      "persistent": true,
      "state": "open",
      "reward": {"id": "ore_iron", "quantity": 2}
    },
    "door_cavern_gate": {
      "type": "door",
      "level": "level_cavern",
      "position": {"x": 480, "y": 120},
      "persistent": true,
      "state": "unlocked",
      "requires": "key_cavern"
    },
    "switch_forest_01": {
      "type": "switch",
      "level": "level_forest",
      "position": {"x": 910, "y": 420},
      "persistent": true,
      "state": "pulled"
    },
    "boss_warden": {
      "type": "boss",
      "level": "level_cavern",
      "position": {"x": 640, "y": 80},
      "persistent": true,
      "state": "defeated"
    }
  }
}
MemberTypeMeaning
typestringThe kind of object: chest, door, switch, boss. The game uses it to choose the reaction.
levelstringThe level the object belongs to: level_village, level_forest or level_cavern.
positionobjectThe coordinates of the object, with x and y. The game places the object from this member.
persistentbooleanTrue when the change must survive a restart. False for the objects that belong to the session only, such as a torch that burns out.
statestringThe state the object takes once the hero has changed it: open, unlocked, pulled, defeated.
requiresstringPresent on the objects that need something: the door needs key_cavern.
rewardobjectPresent on the chests: the item and the quantity the hero receives.

The catalogue is the level data of the world. The game reads it to create the objects of a level, to know where they stand and what they give. The run file only answers a different question: which of them the hero has already changed.

The session document​

The session state lives in a document that is never written to disk:

{
  "session": {
    "current_level": "level_forest",
    "spawned_enemies": 12,
    "chest_cooldown": 0,
    "tutorial_step": 4,
    "fader": 0
  }
}

It has no schema_version, because it never reaches a file. It lives in its own JSON++ Object instance, so no save can pick it up by accident. The values are read and written with the same absolute paths as the rest of the game, and they are lost when the application closes, which is exactly what a session is.

Two JSON++ Object instances hold the permanent state, and one holds the temporary state. The separation is by instance, not by convention: the session instance has no save event attached to it anywhere in the project.

G. Step-by-Step Implementation​

Step 1 — Create the catalogue and the objects​

  1. Create the frames Village, Forest and Cavern.
  2. Place one Active per world object and name it after the object: Forest Chest, Village Chest, Cavern Gate, Forest Lever, Cavern Warden, Cavern Key.
  3. On each of them, create an alterable string named WorldID and type the identifier: chest_forest_01, chest_village_02, door_cavern_gate, switch_forest_01, boss_warden, key_cavern.
  4. On each of them, create an alterable value named Changed and leave it at 0.
  5. Create world_catalog.json next to the exported application, with the catalogue shown above.
  6. Add the two JSON++ Object instances of the world data and the one of the session data to every frame.

The identifier is the contract between the object on the screen and the data on the disk. As long as the identifier of an object never changes, the world remembers it.

Step 2 — Load the run file and the catalogue​

Add a Start of Frame event with two actions:

  • Action: World Data : Load JSON from file at Apppath$ + "emberfall_save.json".
  • Action: World Catalogue : Load JSON from file at Apppath$ + "world_catalog.json".

The catalogue never changes, so it can also be pasted into the Initial JSON property of the World Catalogue instance. The guide loads it from a file so that the objects of a level can be tuned without rebuilding the application.

Step 3 — Restore the objects of the level​

Add an event with the condition World Data: On JSON Loaded. For every world object of the level, write the default first and let the document replace it:

  • Action: Forest Chest : Set alterable value to 0.
  • Condition of the group: World Data: "/world/objects/chest_forest_01" exists.
  • Action of the group: Forest Chest : Set alterable value to 1.

Repeat the pair for every object of the level: the village chest, the cavern gate, the lever, the warden and the key. The order matters and is the reason the default is written first. The condition reads the document, and the action writes the object, so the two never fight over the same value.

For the people of the village the value is a word rather than a flag:

  • Action: Elder Rook : Set alterable string to "idle".
  • Condition of the group: World Data: "/world/npc_states/npc_elder_rook" exists.
  • Action of the group: Elder Rook : Set alterable string to GetString( "World Data", "/world/npc_states/npc_elder_rook" ).

The group of the NPC states belongs to the frame of the village, because that is where the NPC stands. The group of the chests belongs to the frame of the forest.

An object whose member is absent keeps the default. That is the whole difference between an absent member and a member holding a false value: an object that was never touched has no member, and the game leaves it in the state the player found.

Step 4 — Record a change of the world​

Add one event per world object. The chest of the forest reads:

  • Condition: Player collides with Forest Chest.
  • Action: World Data : Set string WorldID("Forest Chest") at "/state" with key "pending_object".
  • Action: World Data : Search for key WorldID("Forest Chest") at "/world/objects" (Exact: 1).

The first action records which object the hero is touching. The second asks the document whether that identifier is already a member of the map of the world.

The search is the decision point of the whole guide. It looks for a member whose name is the identifier, so an object that was already changed is found and an object that was never touched is not. The two answers arrive as two events of the same instance.

Add the branch for the object that was already changed:

  • Condition: World Data: On Results Found.
  • Action: Status Text : Set alterable string to "Already changed".

And the branch for the object that was never changed:

  • Condition: World Data: On Not Results Found.
  • Action: World Data : Set number 1 at "/world/objects" with key GetString( "World Data", "/state/pending_object" ).
  • Action: World Data : Set number 1 at "/state" with key "autosave_pending".
  • Action: Status Text : Set alterable string to "Recorded in the world".

The first action is the whole record. The path /world/objects selects the map, and the key is the identifier that the collision event stored, so one branch serves every object of the game. The write creates the member if it does not exist yet, and the value 1 says that the object is in the state the catalogue describes.

The second action marks the run as changed, so the autosave of Checkpoints and Autosave writes the world to the disk at the next tick of its timer.

Step 5 — Apply the effect of the change​

The reward of the chest and the animation of the door are the work of the game. The guide keeps them out of the shared branch, because the branch does not know the kind of the object it is handling.

For the chest, add an event of your own that reads the catalogue and gives the reward:

  • Condition: Player collides with Forest Chest.
  • Condition of the group: World Catalogue: "/world_objects/chest_forest_01/reward/id" exists.
  • Action of the group: Loot Text : Set alterable string to GetString( "World Catalogue", "/world_objects/chest_forest_01/reward/id" ).

The catalogue says what the chest gives, so the game reads the reward from the data instead of repeating it in the event. Adding the reward to the inventory is described in Stackable Inventory System.

To make sure the reward is given once, the game sets the flag of the object when the branch of Step 4 records the change, and the restore of Step 3 sets the same flag from the document when the level is entered again. Comparing the flag before and after is the work of the game, because the condition that compares it belongs to Fusion and not to the extension.

Step 6 — Unlock the door​

The gate of the cavern is a little different, because it needs something. The condition of the collision event asks the catalogue:

  • Condition: Player collides with Cavern Gate.
  • Condition of the group: World Catalogue: "/world_objects/door_cavern_gate/requires" exists.
  • Action of the group: World Data : Set string WorldID("Cavern Gate") at "/state" with key "pending_object".
  • Action of the group: World Data : Search for key WorldID("Cavern Gate") at "/world/objects" (Exact: 1).

The gate records its change in the same map as the chests, so the restore of Step 3 puts the gate back in the open state with the same two actions.

Whether the hero carries the cavern key is a question about the inventory, and the inventory guide answers it. The condition above only checks that the catalogue describes a requirement; the requirement itself is checked against the items the hero carries.

Step 7 — Change the state of a person​

The people of the village need a word rather than a flag, and each of them has its own event:

  • Condition: Elder Rook is clicked.
  • Action: World Data : Set string "quest_given" at "/world/npc_states" with key WorldID("Elder Rook").
  • Action: Elder Rook : Set alterable string to "quest_given".
  • Action: World Data : Set number 1 at "/state" with key "autosave_pending".

The first action writes the state of the person in the document, and the second writes it on the object, so the screen and the file agree. The word written in the event is a choice of the design: idle, quest_given, quest_done and shop_open are four states of four conversations, and the guide of the dialogue covers how each of them is played.

Step 8 — Keep the temporary state out of the save​

The session document lives in its own instance. The events of the game read it and write it with absolute paths:

  • Action: Session Data : Set number 12 at "/session" with key "spawned_enemies".
  • Action: Session Data : Set string "level_forest" at "/session" with key "current_level".

No event anywhere writes the Session Data instance to a file. That is the whole mechanism: the state that must not survive has no way to reach the disk.

When a member of the session must be cleared, the game resets it with a write of its default value. Removing a member from the document is also possible with the Delete item action, which takes an absolute path.

Step 9 — Save and load the world​

The world section is part of the run file, so it is written by the events of the save. The write happens when the autosave of the previous guide runs:

  • Action: World Data : Save JSON to file at Apppath$ + "emberfall_save.json".

The world is written together with the rest of the run, so the file never describes a world that does not belong to the hero it belongs to.

After the hero returns to the forest​

The restore of Step 3 runs. The flag of the chest becomes 1 because /world/objects/chest_forest_01 exists, and the chest is drawn open and empty. The lever keeps its flag, the gate keeps its flag, and nothing is added to the inventory.

The file on disk is not changed by the restore. Reading the world and writing the world are two different moments, and only the second one touches the disk.

After the session ends​

The session document is gone with the application. The run file holds no member for the number of enemies spawned, for the step of the tutorial or for the fade of the screen, because no event ever wrote that instance to a file.

J. Edge Cases & Error Handling​

SituationWhat happensHandling
The run file does not existThe load fails and On Error runsStart a new run and let the world be found in its original state. A missing file is not an empty world.
The run file holds invalid JSONThe document is not replaced and the error text describes the problemKeep the error text in a log and show a short message. The world starts in its original state.
The catalogue does not match the objects of the levelThe lookup selects nothing and the game falls back to its defaultsGive every object of a level an entry in the catalogue and test the build after adding a level.
The catalogue is missing an entry for an objectThe restore leaves the object in its default stateThe object is treated as never changed. Add the entry to the catalogue.
The hero touches an object twice in the same frameThe second search replaces the result collection of the firstKeep one search per frame on an instance. The guide runs one search per collision event.
The hero stands on the chest for several framesThe search runs on each frameThe second search finds the identifier and the branch does nothing. The flag is written once.
An identifier of the run file is not in the catalogueThe restore has no entry to readThe member stays in the file and is ignored. Prune it with Delete item when the object leaves the game.
The object was changed but the autosave never ranThe file does not know about the changeThe change is in memory and disappears with the session. The autosave of the previous guide exists to close that window.
The session state reaches the diskIt would travel with the runKeep the session in its own instance. The separation by instance is what makes it safe.
A state has more than two valuesThe flag of 1 is not enoughStore the name of the state instead of the flag. The paths and the branches stay the same.
A path contains a slash in a keyThe path is split at the slashEncode the slash as ~1 and the tilde as ~0 inside a path.
The game runs on HTML5Apppath$ has no meaningUse a browser reference such as storage://emberfall_save and read the platform-specific file guide.
The game runs on Android or iOSThe file lands in the sandbox of the applicationUse the path documented for that target and test the export, because a sandbox path differs from the one of a desktop export.

One rule deserves emphasis. The world is written only through the branch that records a change, and the branch runs only when the search finds nothing. If the search is removed, the object gives its reward every time the hero touches it, and the world quietly forgets itself.

K. Runtime Compatibility​

The system relies on three groups of features: searches, existence checks and the change of nested members.

TargetSearchesExistence checksValue changesNotes
WindowsImplemented and testedImplemented and testedImplemented and testedApppath$ resolves to the folder of the exported application.
AndroidImplemented, not verified by an automated checkImplemented, not verified by an automated checkImplemented, not verified by an automated checkWrites inside the sandbox of the application. Test the export.
HTML5Implemented and testedImplemented and testedImplemented and testedUse a browser reference for the file. The result collection belongs to the instance that ran the search.
macOSUnknownUnknownUnknownNo separate build was verified.
iOSImplemented, not verified by an automated checkImplemented, not verified by an automated checkImplemented, not verified by an automated checkWrites inside the sandbox of the application. Test the export.

One difference matters for the restore of Step 3. On the native runtime the exists condition accepts a member whose value is null, while the browser runtime reports such a member as absent. The world map never stores null, so both targets agree. A second difference matters for the search: the native runtime matches member names without regard to case, and the browser runtime compares them with the case they were written in. The identifiers of this guide are written in lower case, so a search finds them on every target. The full matrix is on the runtime compatibility page.

M. Next Steps​

  • Give the world a log. A list of the changes with their date would let the game show "the warden fell three days ago" without a second document.
  • Store the state of the boss in the progression. The warden belongs to the run as much as to the world, and the progression section of the run file is the natural place for a boss that also counts towards a quest.
  • Move the rewards into the inventory events. The catalogue already describes the reward of each chest; the inventory guide shows how to add it without duplicating it.
  • Give the objects a version. A member that names the version of the layout of the level would let the game rebuild the world after a change in the catalogue. Save Versioning and Recovery shows the pattern.
  • Protect the file. The extension can encrypt the file it writes and validate it against a JSON schema. See Enable Encryption and Enable JSON Schema Validation.
