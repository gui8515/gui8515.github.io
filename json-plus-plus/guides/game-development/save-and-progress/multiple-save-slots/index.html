Multiple Save Slots

A. Overview​

Emberfall opens on a title screen with three save slots. One slot holds a run in progress and shows the hero name and level; the others are empty. The player can continue an existing run, start a new one in a free slot, overwrite a run they no longer want, or clear a slot and give it back.

DifficultyIntermediate
ComplexityMedium — two JSON documents, one slot index and one save file per slot
Fusion skillsFrame events, Active objects, Counter and String objects, global variables, expressions
JSON++ skillsLoading and saving files, absolute paths, reading nested members, writing values, error handling

Gameplay scenario​

The player launches Emberfall and reaches the title screen. The three slot panels are already drawn, but their labels are empty until the game knows what each slot contains. Clicking a free slot starts a new game. Clicking an occupied slot loads that run, restores the hero to the village square, refills the health bar from the saved value and shows the gold the hero was carrying. Saving again replaces the file of the slot that was loaded. Clearing a slot frees it without touching the other two.

Learning objectives​

By the end of this guide you will be able to:

  • keep a separate index document that describes the state of each slot without loading every save file;
  • read nested values such as /slots/0/player_name with absolute paths;
  • write gameplay values back into a save document and persist that document to a file;
  • distinguish an empty slot from a slot that failed to load, and recover from both;
  • apply the rule that JSON++ Object stores data while Fusion events move it into the game world.

What you will build​

A title screen with three slot panels, a slot index file (slots.json), one save file per slot (slot_1.json, slot_2.json, slot_3.json) and the events that load, save, overwrite and clear a run.

B. Prerequisites​

Fusion knowledge you need

  • Frame events such as Start of Frame and how an event with a condition runs only when that condition is true.
  • The difference between a frame condition and a group condition under an event.
  • Active objects and the is clicked condition.
  • The String object and the Set alterable string action.
  • The Counter object and its Set counter action, or a global variable on the Special object.
  • Reading an object's position with the expressions X("Player") and Y("Player").

JSON++ concepts you need

  • JSON paths and why an absolute path such as /player/hp always selects the same node.
  • Missing, null and empty, because an empty slot and a slot that could not be read are different situations.
  • Conditions and triggers, in particular the difference between On JSON Loaded and On Error.
  • JSON instance state: every JSON++ Object keeps its own document, its own navigation position and its own search results.

Runtime limitations to keep in mind

  • JSON++ Object has no action that deletes a file. Clearing a slot therefore means marking it free in the index and writing a fresh template over the save file. This guide shows that pattern.
  • File paths follow the host. Apppath$ + "slot_1.json" works on Windows. HTML5 needs a browser reference such as storage://slot_1, and the mobile targets write inside the sandbox of the application. See platform-specific file operations.
  • A save emits On JSON Saved to File when the file work completes. On some targets the completion is asynchronous, so any status message belongs in that event and not directly under the save action.

Standard objects used here

String, Counter, Special, Timer, Active and JSON++ Object. Nothing else is required.

C. Gameplay Scenario​

The title screen of Emberfall is a frame called Title. It holds three slot panels, each an Active object with a label underneath, and a status line at the bottom.

The game starts by reading slots.json. That file is small on purpose: it carries one entry per slot with an occupied flag, the hero name, the level and the play time. The title screen turns that into three labels. A slot that is free shows the word Empty; a slot that holds a run shows the name and level of the hero who owns it.

When the player clicks a panel, the game looks at the occupied flag of that slot. A free slot starts a new run with the default hero. An occupied slot loads slot_N.json, the document that holds the real run, and hands the values to the gameplay objects.

When the player saves, the game copies the live gameplay values into the save document, writes that document to slot_N.json, and only then updates the index and writes slots.json. If the save file fails, the index is not touched, so the title screen keeps showing the previous state instead of advertising a save that never happened.

D. Final Result​

The completed system behaves like this:

  • The title screen shows Empty under a slot that has never been used, and Ari — Level 3 under a slot that holds a run.
  • Clicking a free slot starts a new game with the default hero and reserves that slot.
  • Clicking an occupied slot loads the run, places the hero at the saved position and restores health, gold and the current checkpoint.
  • Saving overwrites the file of the loaded slot and refreshes the matching entry of the index.
  • Clearing a slot marks it free again and leaves the other two slots untouched.
  • A slot file that is missing, unreadable or not valid JSON produces a readable message instead of a silent empty slot.

E. JSON Data Structure​

The slot index​

{
  "schema_version": 1,
  "slots": [
    {"slot": 1, "occupied": true, "player_name": "Ari", "level": 3, "playtime_seconds": 5120},
    {"slot": 2, "occupied": false, "player_name": "", "level": 0, "playtime_seconds": 0},
    {"slot": 3, "occupied": false, "player_name": "", "level": 0, "playtime_seconds": 0}
  ]
}

The root is an object with two members. schema_version is a number that records the shape of the index; Save Versioning and Recovery shows what to do with it when the shape changes. slots is an array of three objects, one per panel.

Each entry has the same five members:

MemberTypeMeaning
slotnumberThe panel number, from 1 to 3. It matches the file name slot_N.json.
occupiednumber1 when the slot holds a run, 0 when it is free. A number is used instead of true or false so the comparison stays simple on every target.
player_namestringThe name shown on the panel. Empty when the slot is free.
levelnumberThe level of the hero, shown on the panel. Zero when the slot is free.
playtime_secondsnumberSeconds played in that run, used for a "last played" label.

The array index and the slot member always agree in this guide, but the member is the one to trust: the array position is a convenience for reading, the identifier is the contract.

The save file of one slot​

{
  "schema_version": 1,
  "saved_at": "2026-02-14T18:32:00Z",
  "player": {
    "name": "Ari",
    "level": 3,
    "hp": 80,
    "max_hp": 100,
    "gold": 250,
    "checkpoint": "cp_village_square",
    "position": {"x": 320, "y": 640},
    "inventory": [
      {"id": "potion_health", "quantity": 3},
      {"id": "herb_lotus", "quantity": 4}
    ],
    "equipment": {"weapon": "sword_iron", "armor": "armor_leather"}
  },
  "world": {
    "chests_opened": ["chest_forest_01"],
    "doors_unlocked": ["door_cavern_gate"]
  }
}

The root object holds the version, the moment of the save and two gameplay sections. player describes the hero, world describes what changed in the world; Persistent World State develops the second section.

Three rules keep this document consistent with the rest of the guides:

  • Stable identifiers. Items, checkpoints and world objects are named by identifiers such as potion_health and cp_village_square, never by their position in an array. The inventory array may be reordered without breaking a save.
  • Numbers for counts, strings for names. Quantities, levels and gold are numbers, so they can be compared and added with the JSON++ arithmetic actions.
  • The save file owns the truth. The index never duplicates the run. It holds only what the title screen needs to draw a panel.

G. Step-by-Step Implementation​

Step 1 — Create the frame and the objects​

  1. Create a frame named Title.
  2. Add the objects listed in the previous section. Rename the three panel Actives and their labels so the numbers match the slots.
  3. On the Special object, create a global variable named Slot Number and leave it at 0.

Step 2 — Load the index at the start of the frame​

Add a Start of Frame event with one action:

  • Condition: Start of Frame.
  • Action: Slot Index : Load JSON from file at Apppath$ + "slots.json".

The path expression is Apppath$ + "slots.json", the folder of the exported application. The file is read and parsed; if it cannot be read or is not valid JSON, the On Error branch of Step 8 runs instead.

Step 3 — Fill the three panel labels​

Add an event with the condition Slot Index: On JSON Loaded. The trigger belongs to the JSON++ Object, so it fires only when that instance finishes a load.

  • Action: Slot 1 Label : Set alterable string to GetString( "Slot Index", "/slots/0/player_name" ).
  • Action: Slot 2 Label : Set alterable string to GetString( "Slot Index", "/slots/1/player_name" ).
  • Action: Slot 3 Label : Set alterable string to GetString( "Slot Index", "/slots/2/player_name" ).

Each expression reads an absolute path. The array index selects the entry, the member name selects the value. Nothing depends on the navigation position of the object.

Step 4 — Replace the name of a free slot with the word Empty​

Under the same event, add a group for each slot. The group condition decides whether the label is overwritten:

  • Condition of the group: Slot Index: Is "/slots/0/occupied" equal to 0.
  • Action: Slot 1 Label : Set alterable string to "Empty".

Repeat for slots two and three with /slots/1/occupied and /slots/2/occupied. The action of the parent event runs first, so the label briefly receives the stored name and then the group replaces it with Empty when the slot is free. A free slot stores an empty name anyway, so the group is what makes the panel readable.

Step 5 — React to a click on a panel​

Add one event per panel. The first one reads:

  • Condition: Slot 1 Button is clicked.
  • Action: Special : Set Slot Number to 1.
  • Action: Save Data : Load JSON from file at Apppath$ + "slot_1.json".

The second panel uses Special : Set Slot Number to 2 and the file slot_2.json; the third uses 3 and slot_3.json.

The global variable remembers the slot for every later event, so the save and delete events do not need to know which panel was pressed.

Step 6 — Restore the run​

Add an event with the condition Save Data: On JSON Loaded:

  • Action: Player : Set alterable string to GetString( "Save Data", "/player/name" ).
  • Action: Player : Set X Position to GetNumber( "Save Data", "/player/position/x" ).
  • Action: Player : Set Y Position to GetNumber( "Save Data", "/player/position/y" ).
  • Action: HP Counter : Set counter to GetNumber( "Save Data", "/player/hp" ).
  • Action: Gold Counter : Set counter to GetNumber( "Save Data", "/player/gold" ).
  • Action: Status Text : Set alterable string to "Slot loaded".

This is the event that applies the data to the game world. JSON++ Object reads; the Fusion actions move. Changing a number in the JSON does not move the hero by itself — the events above are what transfer the value to the Active object and the counters.

Step 7 — Save the run​

Add an event with the condition Save Button is clicked:

  • Action: Save Data : Set number value("HP Counter") at "/player" with key "hp".
  • Action: Save Data : Set number value("Gold Counter") at "/player" with key "gold".
  • Action: Save Data : Set number X("Player") at "/player/position" with key "x".
  • Action: Save Data : Set number Y("Player") at "/player/position" with key "y".
  • Action: Save Data : Save JSON to file at Apppath$ + "slot_1.json".

The first four actions copy the live game values into the document. The last one writes the document to disk. The file name is the one of the slot that is loaded; when the game supports more than one slot at a time, build the name from the global variable instead of repeating the literal.

Step 8 — Update the index after the file is written​

Add an event with the condition Save Data: On JSON Saved. It runs only when the file work completed:

  • Action: Slot Index : Set number 1 at "/slots/0" with key "occupied".
  • Action: Slot Index : Set string "Ari" at "/slots/0" with key "player_name".
  • Action: Slot Index : Set number 3 at "/slots/0" with key "level".
  • Action: Slot Index : Save JSON to file at Apppath$ + "slots.json".

A second event with the condition Slot Index: On JSON Saved sets the status text to Game saved. Splitting the two events keeps the order honest: the index only advertises a run that already reached the disk.

Step 9 — Handle a failed load and a failed save​

Add one On Error event for each JSON++ Object:

  • Condition: Slot Index: On Error.
  • Action: Status Text : Set alterable string to "Slot list unavailable".

And a second one for the save document:

  • Condition: Save Data: On Error.
  • Action: Status Text : Set alterable string to GetError( "Save Data" ).

The error branch of the index is a friendly message because the player cannot act on the technical detail. The error branch of the save document shows the message, because it is the one that explains why a save did not happen.

Step 10 — Clear a slot​

Add an event with the condition Delete Button is clicked:

  • Action: Slot Index : Set number 0 at "/slots/0" with key "occupied".
  • Action: Slot Index : Set string "" at "/slots/0" with key "player_name".
  • Action: Slot Index : Set number 0 at "/slots/0" with key "level".
  • Action: Slot Index : Save JSON to file at Apppath$ + "slots.json".
  • Action: Save Data : Load JSON from String "{""schema_version"":1,""player"":{""name"":"""",""level"":1,""hp"":100,""max_hp"":100,""gold"":0,""checkpoint"":""cp_village_square"",""position"":{""x"":0,""y"":0},""inventory"":[],""equipment"":{}}}".

The last action loads an empty template into the save document. Add an event with the condition Save Data: On JSON Loaded that writes it to slot_1.json, so the file on disk no longer holds the old run either. JSON++ Object cannot remove a file from the host, so the file is overwritten with an empty document instead.

I. Expected Behavior​

Before the first save​

slots.json does not exist yet, or exists with three free slots:

{
  "schema_version": 1,
  "slots": [
    {"slot": 1, "occupied": false, "player_name": "", "level": 0, "playtime_seconds": 0},
    {"slot": 2, "occupied": false, "player_name": "", "level": 0, "playtime_seconds": 0},
    {"slot": 3, "occupied": false, "player_name": "", "level": 0, "playtime_seconds": 0}
  ]
}

The three labels read Empty, and the status line stays blank.

After saving a run in slot one​

slot_1.json holds the run:

{
  "schema_version": 1,
  "saved_at": "2026-02-14T18:32:00Z",
  "player": {
    "name": "Ari",
    "level": 3,
    "hp": 80,
    "max_hp": 100,
    "gold": 250,
    "checkpoint": "cp_village_square",
    "position": {"x": 320, "y": 640},
    "inventory": [
      {"id": "potion_health", "quantity": 3},
      {"id": "herb_lotus", "quantity": 4}
    ],
    "equipment": {"weapon": "sword_iron", "armor": "armor_leather"}
  },
  "world": {
    "chests_opened": ["chest_forest_01"],
    "doors_unlocked": ["door_cavern_gate"]
  }
}

slots.json now describes the first slot:

{
  "schema_version": 1,
  "slots": [
    {"slot": 1, "occupied": true, "player_name": "Ari", "level": 3, "playtime_seconds": 5120},
    {"slot": 2, "occupied": false, "player_name": "", "level": 0, "playtime_seconds": 0},
    {"slot": 3, "occupied": false, "player_name": "", "level": 0, "playtime_seconds": 0}
  ]
}

After loading that run​

The gameplay objects hold the values again: the hero is at 320, 640, the health counter reads 80, the gold counter reads 250, and the status line reads Slot loaded. The JSON documents on disk are unchanged by the load.

After clearing the slot​

The entry of the index returns to occupied 0 with an empty name, and slot_1.json is overwritten with the empty template. The other two entries of the index are untouched.

J. Edge Cases & Error Handling​

SituationWhat happensHandling
slots.json does not existThe load fails and On Error runsShow a friendly message and offer a new game. Create the file on the first run instead of assuming it exists.
slots.json contains invalid JSONThe document is not replaced, the error text describes the problemKeep the error text for a log, show a short message to the player.
The index has fewer than three entriesA path such as /slots/2/player_name selects nothingCheck the length of the array before reading, and write the missing entries.
The save file of the clicked slot is missingThe load fails and the error branch of the save document runsMark the slot free in the index and start a new run instead of leaving a panel that always fails.
The save file has no player memberGetNumber returns a fallback instead of a real valueCheck /player with the exists condition before reading the members below it.
The save file is written but the index write failsThe run is safe on disk, the panel still looks freeRetry the index write, or rebuild the index from the slot files at the next start.
The index is written but the save file failedThe panel advertises a run that does not existUpdate the index only inside On JSON Saved to File, as this guide does.
Two files hold the same slotThe last write winsGive every slot its own file name and never write to a file of a slot that is not loaded.
A path contains a slash in a keyThe path is split at the slashEncode the slash as ~1 and the tilde as ~0 inside a path.
The game runs on HTML5Apppath$ has no meaningUse a browser reference such as storage://slot_1 and read the platform-specific file guide.
The game runs on Android or iOSThe file lands in the sandbox of the applicationUse the path documented for that target and test the export, because a sandbox path differs from the one of a desktop export.

Two rules deserve emphasis. First, never treat a missing file as an empty slot: a missing file means the game cannot read the state it expected, and the player deserves to know. Second, keep the index and the run in separate documents, so a failure in one does not destroy the other.

K. Runtime Compatibility​

The system relies on three groups of features: file operations, insertion and change of values, and error reporting.

TargetFile workValue changesNotes
WindowsImplemented and testedImplemented and testedApppath$ resolves to the folder of the exported application.
AndroidImplemented, not verified by an automated checkImplemented, not verified by an automated checkWrites inside the sandbox of the application. Test the export.
HTML5Implemented and testedImplemented and testedUse a browser reference. storage:// uses the origin storage, download:// dispatches a download, embedded:// is read-only.
macOSUnknownUnknownNo separate build was verified.
iOSImplemented, not verified by an automated checkImplemented, not verified by an automated checkWrites inside the sandbox of the application. Test the export.

A second difference matters for the labels: on the native runtime the exists condition accepts a member whose value is null, while the HTML5 runtime reports such a member as absent. The index written by this guide never stores null, so both targets agree. The full matrix is on the runtime compatibility page.

M. Next Steps​

  • Name the slot file from the global variable. Build Apppath$ + "slot_" + Str$(Slot Number) + ".json" so one event replaces three.
  • Store the play time. A Timer object that counts seconds while the game runs gives the playtime_seconds member of the index.
  • Add a confirmation dialog. The delete event should require a second click before it writes anything.
  • Keep the run in one document. Move inventory, equipment and world into the same save file as the player so a run is a single document, and read them with the stackable inventory guide.
  • Protect the file. The extension can encrypt the file it writes and validate it against a JSON schema. See Enable Encryption and Enable JSON Schema Validation.
