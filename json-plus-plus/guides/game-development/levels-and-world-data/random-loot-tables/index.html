Random Loot Tables

A. Overview​

Every enemy of Emberfall drops something, and what it drops is decided by a table instead of by a chain of events. A file called loot.json describes the tables: which items can fall, how likely each one is, which reward is granted for certain, and how rare it is. The game reads the table of the enemy that died, draws a number, walks the entries and gives the player what the draw selected.

DifficultyAdvanced
ComplexityHigh — one table document, one state document and a weighted draw spread over several events
Fusion skillsFrame events, Active objects, Counters, Timers, the random expression, expressions
JSON++ skillsLoading files, absolute paths, reading arrays in a loop, accumulating values, writing numbers and strings at runtime

Gameplay scenario​

The hero kills a marsh slime and always receives a bone shard. Beyond that guaranteed part, the slime may also leave a health potion, a lotus herb, an iron sword or nothing at all. A wolf is more generous with herbs and less generous with potions. A forest bandit drops two random rewards and always leaves iron ore, and the cavern warden always leaves the key of the cavern. The player learns which enemy is worth chasing, and the designer can change that without touching a single event.

Learning objectives​

By the end of this guide you will be able to:

  • describe a loot table entirely in a document, with its entries, its weights and its rarities;
  • turn the weights of a table into the probability of each entry;
  • compute the total weight of a table with a loop over its entries;
  • draw a number with the random expression of Fusion and walk the entries of the table until the draw is covered;
  • grant a reward that is guaranteed, refuse a reward that is empty, and write every reward into the state of the game;
  • attach a table to an enemy without changing the events of the fight.

What you will build​

A loot table file (loot.json), a state document that records the rolls and the rewards, and the events that pick the table of the dead enemy, compute the total weight, draw the number, walk the entries and grant the result.

B. Prerequisites​

Fusion knowledge you need

  • The random expression Random(<n>) and the integer conversion Floor(<n>).
  • The Counter object, the actions Set counter to, Add to counter and Subtract from counter, and the expression value("Object").
  • Active objects, Timers and the On timer trigger.
  • Reading the alterable of an Active by name, for example EnemyType("Enemy").
  • The action Stop loop, which ends a named loop of the extension before it visits every item.

JSON++ concepts you need

  • JSON paths: the table of an enemy is reached through a path that the game builds at runtime.
  • JSON objects and arrays: the entries of a table are an array, and the order of the array is the order of the walk.
  • Understanding JSON Loops: a loop enumerates the immediate children of a container.
  • Reading Loop Values: the current item of a loop is read with the loop expressions.
  • Loop Lifecycle: the start, the item events and the end of a loop.

Runtime limitations to keep in mind

  • JSON++ Object stores the tables and provides their content. The draw itself, the comparison that walks the entries and the decision to grant a reward are the work of the events of Fusion.
  • The state document lives in the memory of the game. The rewards it holds are handed to the inventory of the hero by the game, and the inventory guide shows how.
  • A write that has to create a missing branch is refused by the browser runtime, so the state document is loaded complete at the start of the frame.

Standard objects used here

JSON++ Object, Active, Counter, Timer, String, Special and Create.

C. Gameplay Scenario​

The forest frame keeps the Enemy object and a Loot Manager object with a Loot Clock that ticks several times per second. Two documents are read when the frame starts: the loot tables and the enemy database.

The loot tables are a map of table names. Each table holds the number of random draws it performs, a list of guaranteed rewards and the entries that a draw can select. An entry names an item, a weight and a rarity. The weights of a table add up to a hundred in this guide, so a weight of forty means a chance of forty in a hundred.

The rarities live in their own section of the document. A rarity carries a label and a colour, and the interface reads them when it draws the name of a reward. The two sections are independent: a designer can add a rarity without touching a table, and a table can use the rarities it wants.

When an enemy dies, the game reads the identifier of its type and asks the enemy database which table belongs to that type. The member loot_table of the definition answers that question, so the assignment of the drops lives in the enemy database and not in the events of the fight.

The guaranteed rewards are granted first. The manager walks the list of guaranteed rewards with a loop and writes each of them into the state document. Then the table performs its random draws. The manager computes the total weight of the entries with a second loop, draws a number between zero and that total, and walks the entries one by one, adding the weight of each entry to an accumulator until the accumulator covers the drawn number. The entry that covered it is the reward.

When the reward is the entry named nothing, the manager records an empty drop and the player receives nothing.

D. Final Result​

The finished system behaves like this:

  • Killing a marsh slime always grants one bone shard, plus one random entry of the table of the slime.
  • The random entry of the slime is a health potion four times out of ten, a bone shard two times out of ten, a lotus herb twice out of ten, an iron sword once out of ten, and nothing once out of twenty.
  • A forest bandit always grants one iron ore and performs two random draws, so it can give two rewards at once.
  • The cavern warden always grants the key of the cavern and performs three random draws.
  • Every reward is written into the state document with its identifier, its quantity and its rarity.
  • An empty drop grants nothing and is recorded, so the interface can say Nothing found.
  • Changing a weight in loot.json changes the distribution of every drop of that table, and nothing else in the game changes with it.

The root and the rarities​

The root holds the version, the rarities and the tables. A rarity carries two members:

MemberTypeMeaning
labelstringThe name the interface shows.
colorstringThe colour of the name. It is a text that follows the notation of colours of the interface.

The rarities are shared. The path /rarities/legendary/label always returns the same word, and every table that uses the rarity legendary shows that word.

The tables​

tables is a map of table names. The name of the table is the identifier the enemy database refers to. Each table holds:

MemberTypeMeaning
idstringThe identifier of the table. It repeats the name of the key.
namestringThe name shown in the interface.
rollsnumberThe number of random draws the table performs.
guaranteedarrayThe rewards granted whatever the draw selects.
entriesarrayThe entries a draw can select.

The guaranteed array may be empty. An empty array is a present value, and it means that the table grants nothing for certain. The wolf table of this guide uses it that way.

The entries​

Every member of the entries array has the same three members:

MemberTypeMeaning
idstringThe identifier of the item. It refers to an item of the inventory of the game.
weightnumberThe share of the table that the entry represents.
raritystringThe key of a rarity of the rarities section.

The weights of a table add up to a hundred, so a weight of forty is a chance of forty in a hundred. When the total is not a hundred, the chance of an entry is its weight divided by the total. The document never stores the total: the game computes it with a loop, because a total that is written by hand goes wrong the first time a designer changes a weight.

The entry named nothing is the empty drop. It has a weight like any other entry, so the chance of receiving nothing is a number the designer chooses. A table without such an entry never gives nothing.

The assignment of the tables to the enemies​

The tables are attached to the enemies in the enemy database, through the member loot_table:

{
  "enemies": {
    "slime": {"id": "slime", "hp": 30, "damage": 6, "loot_table": "slime"},
    "wolf": {"id": "wolf", "hp": 45, "damage": 9, "loot_table": "wolf"},
    "bandit": {"id": "bandit", "hp": 60, "damage": 12, "loot_table": "bandit"},
    "boss_warden": {"id": "boss_warden", "hp": 320, "damage": 20, "loot_table": "boss_warden"}
  }
}

The events of the fight never name a table. They read the member loot_table of the definition of the dead enemy and use its value as the name of the table. Moving a table from a wolf to a bandit is a change of one line in this document.

The state document​

The state document records the roll in progress and the rewards that were granted:

{
  "state": {"granted": 0},
  "roll": {
    "table": "slime",
    "total": 0,
    "drawn": 0,
    "walked": 0,
    "index": 0,
    "walking": 0,
    "ready": 0,
    "reward": "",
    "rarity": "",
    "empty": 0
  },
  "rewards": {
    "reward_1": {"id": "bone_shard", "quantity": 1, "rarity": "common"}
  }
}
MemberTypeMeaning
state.grantednumberThe number of rewards that were granted.
roll.tablestringThe table being rolled.
roll.totalnumberThe sum of the weights of the entries.
roll.drawnnumberThe number drawn by the random expression.
roll.walkednumberThe sum of the weights of the entries already visited by the walk.
roll.indexnumberThe entry of the table that the walk is on.
roll.walkingnumber1 while the walk is running.
roll.readynumber1 when a reward was selected and waits to be granted.
roll.rewardstringThe identifier of the entry the draw selected.
roll.raritystringThe rarity of the selected entry.
roll.emptynumber1 when the selected entry was the empty drop.
rewardsobjectThe rewards that were granted, one member per reward.

The name of a reward is built from the number of granted rewards, so the first reward is reward_1, the second is reward_2, and the manager never writes over a reward it already granted.

F. Clickteam Fusion Object Setup​

ObjectTypeRole in the system
Loot TableJSON++ ObjectHolds the content of loot.json. It is read and never written.
Enemy DatabaseJSON++ ObjectHolds the content of enemies.json. It supplies the member loot_table of the dead enemy.
Loot StateJSON++ ObjectHolds the state document. The roll and the rewards are written into it.
Loot ManagerActiveThe object that owns the events of the roll.
Loot ClockTimerThe tick of the manager. It fires several times per second.
EnemyActiveThe enemy that died. Its alterable string carries the identifier of its type.
Total WeightCounterThe sum of the weights of the entries of the table.
Drawn NumberCounterThe number drawn by the random expression.
Reward LabelStringThe line that announces the reward the player received.
CreateCreateThe Fusion object that places the new enemies of the world. It takes no part in the roll.

Three JSON++ Object instances are used because they hold three different documents. Each instance keeps its own document and its own state.

G. Step-by-Step Implementation​

Step 1 — Create the frame and the objects​

  1. Create a frame named Forest, or add the objects to the frame that already holds the enemies.
  2. Add the objects listed in the previous section.
  3. Give the Enemy object an alterable string named EnemyType.
  4. Set the Loot Clock to fire several times per second.

Step 2 — Load the documents​

Add a Start of Frame event with three actions:

  • Action: Loot Table : Load JSON from file at Apppath$ + "loot.json".
  • Action: Enemy Database : Load JSON from file at Apppath$ + "enemies.json".
  • Action: Loot State : Load JSON from string "{""state"":{""granted"":0},""roll"":{""table"":"""",""total"":0,""drawn"":0,""walked"":0,""index"":0,""walking"":0,""ready"":0,""reward"":"""",""rarity"":"""",""empty"":0},""rewards"":{}}".

The state document is loaded from a string so that every member the events read already exists.

Step 3 — Read the rarities for the interface​

Add an event with the condition Loot Table: On JSON Loaded:

  • Action: Reward Label : Set alterable string to GetString( "Loot Table", "/rarities/common/label" ).

The interface needs the label and the colour of the rarities. The game reads them once per rarity it displays, and it never writes to this document.

Step 4 — Choose the table of the dead enemy​

Add an event with the condition Enemy Clock: On timer, which runs when the enemy has been defeated:

  • Action: Loot State : Set string GetString( "Enemy Database", "/enemies/" + EnemyType("Enemy") + "/loot_table" ) at "/roll" with key "table".
  • Action: Loot State : Set number 0 at "/roll" with key "total".
  • Action: Loot State : Set number 0 at "/roll" with key "walked".
  • Action: Loot State : Set number 0 at "/roll" with key "index".
  • Action: Loot State : Set number 0 at "/roll" with key "walking".
  • Action: Loot State : Set number 0 at "/roll" with key "ready".
  • Action: Loot State : Set number 0 at "/roll" with key "empty".
  • Action: Loot State : Set string "" at "/roll" with key "reward".
  • Action: Total Weight : Set counter to 0.
  • Action: Loot Table : Start loop "Entries" at "/tables/" + GetString( "Loot State", "/roll/table" ) + "/entries".

The first action is the whole assignment mechanism. The events never name a table: they read the name from the definition of the enemy.

Step 5 — Grant the guaranteed rewards​

Add a second action to the event of Step 4:

  • Action: Loot Table : Start loop "Guaranteed" at "/tables/" + GetString( "Loot State", "/roll/table" ) + "/guaranteed".

Then add an event with the condition Loot Table: On Loop "Guaranteed":

  • Action: Loot State : Insert object "{}" at "/rewards" with key "reward_" + Str$(GetNumber( "Loot State", "/state/granted" ) + 1).
  • Action: Loot State : Set string GetString( "Loot Table", GetLoopPath( "Loot Table", "Guaranteed" ) + "/id" ) at "/rewards/reward_" + Str$(GetNumber( "Loot State", "/state/granted" ) + 1) with key "id".
  • Action: Loot State : Set number GetNumber( "Loot Table", GetLoopPath( "Loot Table", "Guaranteed" ) + "/quantity" ) at "/rewards/reward_" + Str$(GetNumber( "Loot State", "/state/granted" ) + 1) with key "quantity".
  • Action: Loot State : Set string GetString( "Loot Table", GetLoopPath( "Loot Table", "Guaranteed" ) + "/rarity" ) at "/rewards/reward_" + Str$(GetNumber( "Loot State", "/state/granted" ) + 1) with key "rarity".
  • Action: Loot State : Add number 1 at "/state" with key "granted".

The first action creates the member of the reward and the three that follow fill it. GetLoopPath returns the path of the current item of the loop, so the members of the current guaranteed reward are read through it.

When the table has no guaranteed reward, the loop has no item and the event never runs. The array exists and it is empty; nothing else happens.

Step 6 — Compute the total weight​

Add an event with the condition Loot Table: On Loop "Entries":

  • Action: Total Weight : Add to counter GetNumber( "Loot Table", GetLoopPath( "Loot Table", "Entries" ) + "/weight" ).
  • Action: Loot State : Set number value("Total Weight") at "/roll" with key "total".

The counter is the sum of the weights of the entries the loop has visited. The state document receives the running total, so the draw can use it.

Step 7 — Draw the number​

Add an event with the condition Loot Table: On End Loop "Entries":

  • Action: Drawn Number : Set counter to Floor(Random(value("Total Weight"))).
  • Action: Loot State : Set number value("Drawn Number") at "/roll" with key "drawn".
  • Action: Loot State : Set number 0 at "/roll" with key "walked".
  • Action: Loot State : Set number 0 at "/roll" with key "index".
  • Action: Loot State : Set number 1 at "/roll" with key "walking".

The random expression of Fusion produces the number. The extension takes no part in the draw: it stores the number in the document so that the rest of the roll can read it.

Step 8 — Walk the entries until the draw is covered​

Add an event with the condition Loot Clock: On timer and one group:

  • Condition of the group: Loot State : Is "/roll/walking" equal to 1?.
  • Action: Loot State : Add number GetNumber( "Loot Table", "/tables/" + GetString( "Loot State", "/roll/table" ) + "/entries/" + Str$(GetNumber( "Loot State", "/roll/index" )) + "/weight" ) at "/roll" with key "walked".

After the addition, the game compares the accumulated weight with the drawn number. That comparison is between two values of the game, and it belongs to Fusion.

When the accumulated weight covers the drawn number, the entry that was just visited is the reward. The group carries that comparison as a second condition, and its actions write the identifier and the rarity of the entry into the state document:

  • Action: Loot State : Set string GetString( "Loot Table", "/tables/" + GetString( "Loot State", "/roll/table" ) + "/entries/" + Str$(GetNumber( "Loot State", "/roll/index" )) + "/id" ) at "/roll" with key "reward".
  • Action: Loot State : Set string GetString( "Loot Table", "/tables/" + GetString( "Loot State", "/roll/table" ) + "/entries/" + Str$(GetNumber( "Loot State", "/roll/index" )) + "/rarity" ) at "/roll" with key "rarity".
  • Action: Loot State : Set number 1 at "/roll" with key "ready".
  • Action: Loot State : Set number 0 at "/roll" with key "walking".

When the identifier of the entry is nothing, the game writes 1 into /roll/empty with the action Loot State : Set number 1 at "/roll" with key "empty", leaves /roll/ready at zero and stops the walk. The player receives nothing.

When the accumulated weight does not cover the drawn number yet, the game moves to the next entry by writing one more into /roll/index with the action Loot State : Add number 1 at "/roll" with key "index", and the next tick continues the walk.

Step 9 — Grant the reward of the draw​

Add a second event with the condition Loot Clock: On timer and one group:

  • Condition of the group: Loot State : Is "/roll/ready" equal to 1?.
  • Action: Loot State : Insert object "{}" at "/rewards" with key "reward_" + Str$(GetNumber( "Loot State", "/state/granted" ) + 1).
  • Action: Loot State : Set string GetString( "Loot State", "/roll/reward" ) at "/rewards/reward_" + Str$(GetNumber( "Loot State", "/state/granted" ) + 1) with key "id".
  • Action: Loot State : Set number 1 at "/rewards/reward_" + Str$(GetNumber( "Loot State", "/state/granted" ) + 1) with key "quantity".
  • Action: Loot State : Set string GetString( "Loot State", "/roll/rarity" ) at "/rewards/reward_" + Str$(GetNumber( "Loot State", "/state/granted" ) + 1) with key "rarity".
  • Action: Loot State : Add number 1 at "/state" with key "granted".
  • Action: Loot State : Set number 0 at "/roll" with key "ready".

The quantity of a random reward is one in this guide. A table that hands out two of an item stores the quantity in the entry and the manager reads it from there.

The grant runs in an event of its own because only the first group that matches runs inside an event. The walk sets the flag /roll/ready and clears /roll/walking, and the tick that follows grants the reward.

Step 10 — Announce the result​

Add an event with the condition Loot Clock: On timer and one group:

  • Condition of the group: Loot State : Is "/roll/empty" equal to 1?.
  • Action: Reward Label : Set alterable string to GetString( "Loot Table", "/rarities/none/label" ).

A second group reads the rarity of the reward that was granted and shows its label:

  • Condition of the group: Loot State : Is "/roll/rarity" equal to "legendary"?.
  • Action: Reward Label : Set alterable string to GetString( "Loot Table", "/rarities/legendary/label" ).

The groups are tested in order and the first one that matches runs, so the interface shows a single line for the roll that just happened.

Step 11 — Repeat the draw as many times as the table asks​

The member rolls of the table says how many random draws it performs. The manager counts the draws it has made and compares that count with /tables/<table>/rolls, which is a comparison between two values of the game. When the count is lower, the manager runs the procedure of Steps 6 and 7 again: it sums the weights, draws a number and walks the entries a second time.

Step 12 — Hand the rewards to the inventory​

The state document holds the rewards of the fight. The game reads them with a loop over /rewards and gives each of them to the inventory of the hero, which the stackable inventory guide builds. The loot tables do not touch the inventory themselves.

Step 13 — Handle a failed load​

Add one event for each JSON++ Object that reads a file:

  • Condition: Loot Table: On Error.
  • Action: Reward Label : Set alterable string to GetError( "Loot Table" ).

The same pair of actions belongs to the enemy database.

I. Expected Behavior​

Before the roll​

The state document is empty and no reward was granted:

{
  "state": {"granted": 0},
  "roll": {
    "table": "",
    "total": 0,
    "drawn": 0,
    "walked": 0,
    "index": 0,
    "walking": 0,
    "ready": 0,
    "reward": "",
    "rarity": "",
    "empty": 0
  },
  "rewards": {}
}

After a slime that dropped a health potion​

{
  "state": {"granted": 2},
  "roll": {
    "table": "slime",
    "total": 100,
    "drawn": 17,
    "walked": 40,
    "index": 0,
    "walking": 0,
    "ready": 0,
    "reward": "potion_health",
    "rarity": "common",
    "empty": 0
  },
  "rewards": {
    "reward_1": {"id": "bone_shard", "quantity": 1, "rarity": "common"},
    "reward_2": {"id": "potion_health", "quantity": 1, "rarity": "common"}
  }
}

The drawn number was seventeen. The walk added the weight of the first entry, forty, and the accumulator covered the draw, so the first entry was selected. The first reward is the guaranteed bone shard and the second one is the health potion.

A slime that draws a number between eighty-five and ninety-nine gives an empty drop: the state document records nothing as the reward, 1 in /roll/empty, and the list of rewards holds only the guaranteed bone shard.

J. Edge Cases & Error Handling​

SituationWhat happensHandling
loot.json does not existThe load fails and On Error runsShow the message and return to the menu. Ship the file with the game.
loot.json contains invalid JSONThe document is not replaced and the error text describes the problemKeep the technical text for a log and show a short message to the player.
The table of the enemy does not existThe path of the table selects nothing and the loop has no itemGive every enemy a loot_table that names a table of the document.
The table has no entriesThe total weight stays at zero and the draw is meaninglessRefuse a table without entries when the file is written, and always keep one entry in the guide.
The weights do not add up to a hundredThe probability of each entry is its weight divided by the totalThe total is computed by the game, so the distribution stays correct. A table with weights that add up to a hundred is easier to read.
Every entry is nothingThe player never receives anythingKeep a real entry in every table, even with a weight of one.
The random expression returns the total itselfThe walk reaches the last entryThe weight of the last entry covers the draw, so the walk always ends with an entry.
The walk visits every entry without covering the drawThe last entry is usedGive the last entry a weight of at least one and keep the drawn number below the total.
A reward is granted twiceThe state document holds two members with the same nameThe name of a reward is built from the number of granted rewards, so every reward gets its own member.
The enemy database has no loot_table memberThe name of the table is empty and no reward is producedGive every definition the member, and check it with the exists condition before the roll.
The state document is not loaded before the rollThe write has to create the missing branch and the browser runtime refuses itLoad the state document from a string at the start of the frame, as this guide does.
The game runs on HTML5Apppath$ has no meaningUse a browser reference such as storage://loot and read the platform-specific file guide.

Two rules deserve emphasis. First, the distribution lives in the weights and nowhere else: the total is always computed, never written. Second, the empty drop is an entry like any other. The chance of receiving nothing is a number the designer chooses, and it should be chosen on purpose.

K. Runtime Compatibility​

The system relies on four groups of features: reading a file, reading an array in a loop, writing values into a document and comparing values.

TargetFile workLoop, read and writeNotes
WindowsImplemented and testedImplemented and testedApppath$ resolves to the folder of the exported application.
AndroidImplemented, not verified by an automated checkImplemented, not verified by an automated checkReads inside the sandbox of the application. Test the export.
HTML5Implemented and testedImplemented and testedUse a browser reference. A write that has to create a missing branch is refused, so the state document is loaded complete.
macOSUnknownUnknownNo separate build was verified.
iOSImplemented, not verified by an automated checkImplemented, not verified by an automated checkReads inside the sandbox of the application. Test the export.

One difference touches the conditions. The native runtime recognizes a member whose value is null when the exists condition asks whether a path is there, while the browser runtime reports such a member as absent. The tables of this guide never store null, so both targets answer the same way. The full matrix is on the runtime compatibility page.

M. Next Steps​

  • Give a reward a quantity. The entries of a table can carry a quantity of their own, and the manager reads it from the entry instead of writing one.
  • Roll several tables. A boss can roll two tables, and the manager appends the rewards of the second roll to the same list.
  • Show the chances to the player. The interface can read the weight of an entry and display it as a percentage, using the total the manager already computed.
  • Add a pity rule. The manager can count the rolls that returned nothing and raise the weight of the rare entries after a long streak.
  • Move the rewards into the inventory. The loop over /rewards is the bridge to the inventory of the hero, and the inventory guide shows the other half of it.
