Data-Driven Enemy Database

A. Overview​

Emberfall keeps the numbers of its enemies in a single document called enemies.json. The document holds one definition per enemy type: the slime, the wolf, the bandit and the cavern warden. Every number that decides how an enemy fights — its health, its damage, its speed, its experience reward — lives in that document and nowhere else. The events of the game read the definition of the type they are about to spawn and hand the values to the object that appears on screen.

DifficultyIntermediate
ComplexityMedium — one JSON document, one lookup by identifier and one initialization step per spawned enemy
Fusion skillsFrame events, Active objects, Counters, Timers, global variables, expressions
JSON++ skillsLoading a file, absolute paths, searching for a value, reading members, writing a number at runtime

Gameplay scenario​

The hero walks into the Whispering Forest and a marsh slime crawls out of the grass. It is slow, it hits for six damage and it gives twelve experience when it dies. The next slime behaves the same way. Three wolves follow, faster and tougher. The player has no way to know that these values come from a file, and that is exactly the point: the designer who wants the wolves to hit harder changes one number in enemies.json and the next build of the forest is different.

Learning objectives​

By the end of this guide you will be able to:

  • separate an enemy definition, which is data, from an enemy instance, which is an object in the running game;
  • read the attributes of a definition through absolute paths such as /enemies/wolf/damage;
  • look up a definition by its identifier and fail cleanly when the identifier does not exist;
  • initialise a spawned enemy from the definition without hard-coding a single number in the event editor;
  • change the balance of the whole game by editing one document, and apply a change to a running game without touching the events.

What you will build​

An enemy database file (enemies.json), a frame with a spawn point and an enemy object, and the events that load the database, look up a type, initialise the new instance and report a type that the database does not know.

B. Prerequisites​

Fusion knowledge you need

  • Frame events such as Start of Frame and how an event with a condition runs only when that condition is true.
  • Active objects, the is clicked condition and the alterable string of an Active.
  • The Counter object and the actions Set counter to and Add to counter.
  • The Timer object and the On timer trigger.
  • Global variables on the Special object, written as Special : Set <name> to <value>.
  • Reading the alterable of an Active by name, for example EnemyType("Spawn Point").

JSON++ concepts you need

  • JSON paths: every read uses an absolute path that always selects the same member.
  • JSON objects and arrays: a member named by a key is not the same as an item of an array.
  • Missing, null and empty: an identifier that is absent is not an identifier that holds an empty text.
  • Search results and their lifetime: a search stores its own collection, separate from the document.
  • Conditions and triggers: the difference between On JSON Loaded and On Error.

Runtime limitations to keep in mind

  • The document is read from a file, and every target resolves a file path differently. Apppath$ + "enemies.json" works on a desktop export; the browser runtime needs a browser reference such as storage://enemies, and the mobile targets write inside the sandbox of the application. See platform-specific file operations.
  • The runtime of the game creates the enemies. JSON++ Object reads the definition and writes the values; it never places an object on the screen.
  • A search compares values, and a member whose value is null is not the same as an absent member. The document of this guide never stores null, so every target agrees.

Standard objects used here

JSON++ Object, Active, Counter, Timer, String, Special and Create. Nothing else is required.

C. Gameplay Scenario​

The forest frame holds a Spawn Point, an Enemy object and a Status Text. The designer places three spawn points and gives each of them a different alterable string: the first one says slime, the second one says wolf, the third one says bandit.

At the start of the frame the game reads enemies.json. The document is a map of enemy types. Each key is the identifier of a type, and the value of the key is the definition of that type: the display name, the category, the health, the damage, the speed, the experience reward, the attack range and the name of the loot table.

When the hero walks over a spawn point, the game looks up the identifier written on it. The lookup answers one question: does the database know this type? When the answer is yes, the game prepares the enemy object with the identifier and creates the instance. When the answer is no, the status line reports an unknown type and nothing appears on the screen.

The new instance is not ready the moment it exists. It initialises itself on the first tick of its own timer: it reads the health, the damage, the speed and the experience reward of its own definition and writes them into its counters. From that moment on, the behaviour of the enemy uses those counters, and the events of the game never mention a number again.

The cave fight works the same way. The cavern warden is a definition in the same document with a much larger health, and the game treats it like any other type. The bandit is the one enemy that carries something worth taking: an ember axe, the axe_ember of the equipment guide. Its member loot_table names the table that the random loot tables describe, so the fight and the reward of a bandit live in two different documents.

D. Final Result​

The finished system behaves like this:

  • The game reads the four definitions of enemies.json when the frame starts and reports how many types it found.
  • A spawn point marked slime produces a slime with thirty health, six damage, a speed of forty and twelve experience.
  • A spawn point marked wolf produces a wolf with the values of the wolf definition, and nothing in the event editor has to change.
  • A spawn point marked dragon produces nothing and reports Unknown enemy type, because the database has no such definition.
  • The four counters of a new enemy are empty for a fraction of a second and then hold the values of its definition.
  • Changing the number hp of the slime in the document and restarting the frame changes the balance of the forest.
  • Writing a new value into the document while the game runs changes the values used by the next spawn, without reloading the file.

E. JSON Data Structure​

The root​

The root is an object with three members. schema_version is a number that records the shape of the document; Save Versioning and Recovery explains what to do with it when the shape changes. categories describes the families of enemy. enemies holds the definitions.

The definitions​

enemies is an object, not an array. Every key is the identifier of a type, and the value of the key is the definition of that type. The choice matters:

  • an identifier is a stable string. The game can hold it in an alterable and compare it with anything;
  • a path built from an identifier always selects the same definition, whichever order the entries have in the file;
  • a designer can insert a new type in the middle of the file without breaking anything.

The four definitions of this guide share the same members:

MemberTypeMeaning
idstringThe identifier of the type. It repeats the key of the definition, so a reader of the file sees the name of the type next to its numbers.
namestringThe name shown in the interface.
categorystringThe key of a category in categories. It tells the game which family the type belongs to.
hpnumberThe health of a new instance.
damagenumberThe health removed from the hero by one hit.
speednumberThe movement speed of the instance, in the unit the game uses.
xp_rewardnumberThe experience granted when the instance dies.
attack_rangenumberThe distance at which the instance decides to strike.
loot_tablestringThe name of the loot table used when the instance dies.

The numbers are numbers and the names are strings, so every value of this document can be compared and added with the arithmetic actions of the extension.

The categories​

categories maps four families to a small object each:

CategoryLabelAggressive
beastBeast1
humanoidHumanoid1
undeadUndead0
bossBoss1

A category is reusable. The path /categories/beast/label always returns the same word, no matter how many enemies use it. A category answers questions about a family of enemies, while a definition answers questions about one type.

Definition and instance​

A definition is the data of a type. It exists once in the document, it never moves and it never dies.

An instance is the enemy in the running game. It has its own health that goes down, its own position and its own life. Several instances of the same type share one definition: ten wolves in the forest read the same /enemies/wolf definition and still have ten separate sets of counters.

The separation is what makes the system safe to change. Rebalancing a definition changes every future instance of that type and touches no instance that already exists.

G. Step-by-Step Implementation​

Step 1 — Create the frame and the objects​

  1. Create a frame named Forest.
  2. Add the objects listed in the previous section.
  3. Give the Enemy object an alterable string named EnemyType and give the Spawn Point an alterable string with the same name.
  4. Make the counters children of the Enemy object, so a new instance receives its own counters.
  5. Add the Enemy Clock as a child of the Enemy object too, set to fire once and to repeat never.

Step 2 — Load the database at the start of the frame​

Add a Start of Frame event with one action:

  • Condition: Start of Frame.
  • Action: Enemy Database : Load JSON from file at Apppath$ + "enemies.json".

The path expression is Apppath$ + "enemies.json", the folder of the exported application. The file is read and parsed. If it cannot be read or is not valid JSON, the On Error branch of Step 10 runs instead.

Step 3 — Count the definitions​

Add an event with the condition Enemy Database: On JSON Loaded:

  • Action: Enemy Count : Set counter to 0.
  • Action: Enemy Database : Start loop "Definitions" at "/enemies".

The loop enumerates the four members of the enemies object. The name of the loop, Definitions, is used again in every condition and every expression that reads the current item.

Step 4 — List the identifiers of the definitions​

Add an event with the condition Enemy Database: On Loop "Definitions":

  • Action: Enemy Count : Add to counter 1.
  • Action: Status Text : Set alterable string to GetLoopKey( "Enemy Database", "Definitions" ).

GetLoopKey returns each current member name, including slime, wolf, bandit and boss_warden. The order follows the loaded document, whose member order may change when a file is saved with key sorting. The loop visits the immediate children of the object; it does not walk the whole document.

Step 5 — Report the result of the count​

Add an event with the condition Enemy Database: On End Loop "Definitions":

  • Action: Status Text : Set alterable string to Str$(value("Enemy Count")) + " enemy types loaded".

The completion event is the right place for a summary. Reading the count right after the Start loop action can happen before the loop has visited anything.

Step 6 — Look up the type of a spawn point​

Add an event with the condition Spawn Point is clicked:

  • Action: Enemy Database : Search for value """" + EnemyType("Spawn Point") + """" at "/enemies" (Exact: 1).

The identifier is passed between JSON quotes so exact Search by Value uses the same string representation on Windows and HTML5. The id member of every definition holds that identifier, so a known type produces at least one result and an unknown type produces none.

Step 7 — Prepare the instance when the type exists​

Add an event with the condition Enemy Database: On Results Found:

  • Action: Enemy : Set alterable string to EnemyType("Spawn Point").
  • Action: Status Text : Set alterable string to "Spawning " + EnemyType("Spawn Point").

The Enemy object on the frame is the template of the enemy. In Fusion, a new instance receives a copy of the alterables of the template, so writing the identifier on the template before the creation is what gives the instance its type.

The creation itself belongs to the game: the Create object of the frame places a new Enemy at the position of the spawn point. The extension takes no part in it.

Step 8 — Report an unknown type​

Add an event with the condition Enemy Database: On Not Results Found:

  • Action: Status Text : Set alterable string to "Unknown enemy type".

The branch is as important as the successful one. A designer who writes wlf instead of wolf sees the mistake instead of an empty forest.

Step 9 — Initialise the new instance​

Add an event with the condition Enemy Clock: On timer:

  • Action: Enemy HP : Set counter to GetNumber( "Enemy Database", "/enemies/" + EnemyType("Enemy") + "/hp" ).
  • Action: Enemy Damage : Set counter to GetNumber( "Enemy Database", "/enemies/" + EnemyType("Enemy") + "/damage" ).
  • Action: Enemy Speed : Set counter to GetNumber( "Enemy Database", "/enemies/" + EnemyType("Enemy") + "/speed" ).
  • Action: Enemy XP : Set counter to GetNumber( "Enemy Database", "/enemies/" + EnemyType("Enemy") + "/xp_reward" ).

The path is built at runtime from the identifier the instance carries. It always begins with /, and it always selects the definition of the instance's own type.

This event belongs to the enemy, so each instance runs it for itself and writes into its own counters. The timer gives the instance one tick to exist before the values are applied; the counters are empty for that fraction of a second.

Step 10 — Handle a failed load​

Add an event with the condition Enemy Database: On Error:

  • Action: Status Text : Set alterable string to GetError( "Enemy Database" ).

The error text names the file that could not be read. The message reaches the player through the status line, and the details stay available in the same line for whoever plays the game in a debug build.

Step 11 — Change the balance without touching the events​

Add an event with the condition Spawn Point is clicked and, before the search, one action:

  • Action: Enemy Database : Set number 45 at "/enemies/slime" with key "hp".

The write changes the document that is already loaded. The next slime that appears reads forty-five health instead of thirty, and no event of the game has been edited.

The same action with a different key and value adjusts the damage, the speed or the experience reward. To change a value for the whole session, write it once when the frame starts.

J. Edge Cases & Error Handling​

SituationWhat happensHandling
enemies.json does not existThe load fails and On Error runsKeep the message in the status line and ship the file with the game. On a browser target the file has to be part of the resources of the page.
enemies.json contains invalid JSONThe document is not replaced and the error text describes the problemShow a short message to the player and keep the technical text for a log.
The spawn point carries an identifier the database does not knowThe search returns no result and On Not Results Found runsThe branch already reports the mistake. Nothing is created, so a typo never leaves a nameless enemy on the screen.
A definition is missing the hp memberGetNumber returns a fallback instead of a real valueCheck the member with the exists condition before reading it, or give every definition the same members in the file.
A definition holds null instead of a numberThe native runtime accepts the member in the exists condition, the browser runtime reports it as absentKeep the numbers as numbers. The runtime difference is described on the runtime compatibility page.
The definition is removed while the game runsThe path of the next spawn selects nothingReload the document after a change of the file, or write the change into the document instead of removing the member.
The document is edited while a loop is runningThe loop continues over the snapshot it capturedApply the edit when no loop is active, or start the loop again after the change.
Two spawn points carry the same identifierBoth produce the same typeThe identifier describes a type, not an individual. Use a different identifier for a different type of enemy.
The player fights the warden in a level without the fileThe warden has no values and dies at onceShip the database with every level, and check the load before the level starts.
A key of the document contains a slashThe path is split at the slashEncode the slash as ~1 and the tilde as ~0 inside a path. The identifiers of this guide never contain either.
The game runs on HTML5Apppath$ has no meaningUse a browser reference such as storage://enemies and read the platform-specific file guide.
The game runs on Android or iOSThe file lands in the sandbox of the applicationUse the path documented for that target and test the export, because a sandbox path differs from the one of a desktop export.

Two rules deserve emphasis. First, the identifier is the contract: the events of the game never assume a position in the document. Second, a value that is read as zero may be missing rather than zero, so check the member before trusting it when a definition can be edited by hand.

K. Runtime Compatibility​

The system relies on three groups of features: reading a file, searching a document and reading a member by path.

TargetFile workSearch and readNotes
WindowsImplemented and testedImplemented and testedApppath$ resolves to the folder of the exported application.
AndroidImplemented, not verified by an automated checkImplemented, not verified by an automated checkReads inside the sandbox of the application. Test the export.
HTML5Implemented and testedImplemented and testedUse a browser reference. storage:// uses the origin storage and embedded:// is read-only.
macOSUnknownUnknownNo separate build was verified.
iOSImplemented, not verified by an automated checkImplemented, not verified by an automated checkReads inside the sandbox of the application. Test the export.

One difference touches the lookup. The native runtime recognizes a member whose value is null when the exists condition asks whether a path is there, while the browser runtime reports such a member as absent. The definitions of this guide never store null, so both targets answer the same way. The full matrix is on the runtime compatibility page.

M. Next Steps​

  • Add a bestiary screen. The loop over /enemies already visits every definition; add the display name and the category to the list and the player gets a codex.
  • Scale the definitions by level. The difficulty presets guide multiplies the health and the damage of a definition by a factor, and the enemy reads both values.
  • Store the enemies in an array. A list of definitions is the better shape when the game must display them in a fixed order, such as a shop or a catalogue; the identifiers stay inside each entry.
  • Protect the document. The extension can encrypt the file it writes and validate it against a JSON schema. See Enable Encryption and Enable JSON Schema Validation.
  • Give every type a preview. Read the display name with GetString and show it next to the spawn point while the hero walks over it.
