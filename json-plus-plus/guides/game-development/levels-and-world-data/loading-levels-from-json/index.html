Loading Levels from JSON

A. Overview​

The Whispering Forest of Emberfall is not drawn by hand. A file called level_forest.json describes the level: where the hero appears, which platforms exist, where the enemies wait, which collectibles lie on the ground and which checkpoints save the run. The game reads that file when the frame starts and builds the level from it, one section at a time, so a long level never freezes the screen.

DifficultyAdvanced
ComplexityHigh — one level document, one build state document and a dispatcher that reads the type of every entry
Fusion skillsFrame events, Active objects, Counters, Timers, expressions, the Create object of the frame
JSON++ skillsLoading files, absolute paths, reading an array in a loop, reading the type of an entry, writing values at runtime

Gameplay scenario​

The hero enters the forest and stands on the stone path that leads from the village. Grass platforms carry the path over the low ground, a stone platform raises it towards the bridge, and a checkpoint stands where the bridge begins. A slime waits under the first platform, a wolf patrols the bridge and a bandit camps in the clearing at the far end. A lotus herb grows on the way and an iron ore lies in the grass of the clearing. Every one of these things comes from the file of the level, and the designer moves them by editing numbers.

Learning objectives​

By the end of this guide you will be able to:

  • describe a level with a document that holds its identity, its spawn point and its objects;
  • read the type of an object and dispatch the work that each type needs;
  • place the hero with the coordinates that the document gives;
  • create the Fusion objects of the level from the values that were read;
  • report an object whose type the game does not know instead of ignoring it in silence;
  • split a long level into sections and build it over several frames.

What you will build​

A level file (level_forest.json), a build state document that holds the values of the entry being processed, and the events that read the level, walk the entries of a section, dispatch each type and place the hero.

B. Prerequisites​

Fusion knowledge you need

  • Frame events and the On timer trigger of a Timer object.
  • Active objects, the Set X Position and Set Y Position actions, and the actions that change the size of an object.
  • The Counter object, the actions Set counter to and Add to counter, and the expression value("Object").
  • The Create object of the frame, which places the objects of the level in the world.
  • Reading the alterable of an Active by name, for example EnemyType("Enemy").

JSON++ concepts you need

  • JSON paths: every read uses an absolute path.
  • JSON objects and arrays: a level holds an array of sections, and a section holds an array of objects.
  • Understanding JSON Loops: a loop enumerates the immediate children of a container.
  • Reading Loop Values: the path of the current item of a loop is read with the loop expressions.
  • Missing, null and empty: an entry without a width is not an entry with a width of zero.

Runtime limitations to keep in mind

  • JSON++ Object reads the level and hands the values to the game. It never creates an object, never moves the hero and never sets the size of a platform.
  • The level is read once, when the frame starts. A change in the file is visible after the frame restarts.
  • The loop of a section visits the entries of that section. The loop is scheduled by the runtime, and the entries of the next section are not read until the next section starts.

Standard objects used here

JSON++ Object, Active, Counter, Timer, String, Special and Create.

C. Gameplay Scenario​

The forest frame holds the Hero, the object types the level uses and a Level Loader object with a Build Clock. The clock ticks once, and each tick builds one section of the level.

The file of the level has two parts. The level member describes the level itself: its identifier, its name, its size, the point where the hero appears and the music that plays. The sections member is an array, and each section holds an array of objects.

An entry of a section always has a type, and the type decides what the rest of the entry means. A platform has a width and a height. An enemy names a type of enemy instead. A collectible names an item. A checkpoint carries the identifier of a checkpoint, and a prop names a decoration. An entry whose type the game does not know is counted and reported, because a silent omission is the hardest kind of mistake to find in a level file.

The loader keeps the values of the entry it is processing in a small state document. It writes the type first, then the coordinates, and then the groups of the event look at the type and read the members that belong to it. The state document is the bridge between the description of the level and the work of the game.

The creation of the objects is the work of Fusion. Each group of the dispatcher ends with the creation of the object of that type, at the coordinates that were read, with the size that was read. The extension never takes part in it.

D. Final Result​

The finished system behaves like this:

  • The hero appears on the stone path of the village side of the forest, at the coordinates of the file.
  • The platforms of the level appear at the right place and with the right size.
  • The slime, the wolf and the bandit appear where the file places them, and they read their health and their damage from the enemy database.
  • The lotus herb and the iron ore appear on the ground and can be collected.
  • The checkpoint of the bridge appears with its identifier, and the checkpoint guide shows how it saves the run.
  • An entry with a type the game does not know is counted, and the status line reports the type instead of leaving a gap in the level.
  • A long level appears over several frames, and the game never freezes while the level is built.

E. JSON Data Structure​

The complete document​

{
  "schema_version": 1,
  "level": {
    "id": "level_forest",
    "name": "Whispering Forest",
    "width": 3200,
    "height": 1800,
    "background": "forest",
    "music": "forest_theme",
    "spawn": {"x": 160, "y": 1520}
  },
  "sections": [
    {
      "name": "entrance",
      "objects": [
        {"type": "platform", "x": 0, "y": 1600, "width": 640, "height": 64, "surface": "grass"},
        {"type": "platform", "x": 640, "y": 1520, "width": 320, "height": 64, "surface": "grass"},
        {"type": "prop", "prop": "tree", "x": 300, "y": 1450},
        {"type": "collectible", "item": "herb_lotus", "x": 1300, "y": 1280}
      ]
    },
    {
      "name": "bridge",
      "objects": [
        {"type": "platform", "x": 1200, "y": 1400, "width": 480, "height": 64, "surface": "stone"},
        {"type": "checkpoint", "id": "cp_forest_bridge", "x": 1900, "y": 1440},
        {"type": "enemy", "enemy": "slime", "x": 900, "y": 1440},
        {"type": "enemy", "enemy": "wolf", "x": 2000, "y": 1320}
      ]
    },
    {
      "name": "clearing",
      "objects": [
        {"type": "platform", "x": 2400, "y": 1440, "width": 800, "height": 64, "surface": "stone"},
        {"type": "enemy", "enemy": "bandit", "x": 2700, "y": 1360},
        {"type": "collectible", "item": "ore_iron", "x": 2600, "y": 1300},
        {"type": "mystery", "x": 100, "y": 100}
      ]
    }
  ]
}

The level​

The level member describes the level as a whole:

MemberTypeMeaning
idstringThe identifier of the level. It is level_forest, the same identifier the checkpoints and the saves use.
namestringThe name the interface shows.
widthnumberThe width of the level in pixels.
heightnumberThe height of the level in pixels.
backgroundstringThe name of the background of the frame.
musicstringThe name of the music of the level.
spawnobjectThe point where the hero appears, with an x and a y.

The spawn point is an object of its own, because a position always carries two numbers. The path /level/spawn/x always selects the same value.

The sections​

sections is an array. Each section has a name and an objects array. The sections are built in the order of the array, and the names are for the person who reads the file.

Splitting a level into sections is what keeps a long level responsive. The builder of this guide builds one section per tick of the clock, so a level with three hundred objects takes three ticks of work spread over three frames instead of one long stall.

The objects​

Every entry of an objects array has a type, an x and a y. The type decides the other members:

TypeExtra membersMeaning
platformwidth, height, surfaceA solid piece of ground. The surface names the animation or the image the platform uses.
enemyenemyAn enemy of the world. The member names the type, and the enemy reads its values from the enemy database.
collectibleitemAn item lying on the ground. The member names the item of the inventory.
checkpointidA checkpoint. The member is the identifier of the checkpoint, and it is the same identifier the save system uses.
proppropA decoration with no behaviour of its own.
any other value—An unknown type. The builder counts it and reports it.

The coordinates are the position of the object in the level. The position of the hero is read from /level/spawn, and the positions of the objects are read from the entries themselves.

The entry of type mystery at the end of the clearing is deliberate. It shows what the builder does with a type it does not know, and it shows the report that appears in the status line.

The build state​

The build state holds the values of the entry being processed:

{
  "build": {
    "type": "",
    "known": 0,
    "unknown": 0,
    "x": 0,
    "y": 0,
    "width": 0,
    "height": 0,
    "enemy": "",
    "item": "",
    "id": "",
    "prop": "",
    "section": 0,
    "sections": 0,
    "loading": 0,
    "done": 0
  }
}
MemberTypeMeaning
build.typestringThe type of the entry being processed.
build.knownnumber1 once a group of the dispatcher matched the type.
build.unknownnumberThe number of entries with a type the game does not know.
build.x, build.ynumberThe position of the entry.
build.width, build.heightnumberThe size of the entry, when it has one.
build.enemystringThe type of enemy of the entry.
build.itemstringThe item of the entry.
build.idstringThe identifier of the entry, when it has one.
build.propstringThe decoration of the entry.
build.sectionnumberThe section being built.
build.sectionsnumberThe number of sections of the level.
build.loadingnumber1 while a section is still being built.
build.donenumber1 when the whole level was built.

The state document is a working area, not a description of the level. It can be emptied and filled again for every entry.

F. Clickteam Fusion Object Setup​

ObjectTypeRole in the system
Level DataJSON++ ObjectHolds the content of level_forest.json. It is read and never written.
Build StateJSON++ ObjectHolds the build state. The dispatcher reads the type from it and writes the values of the entry into it.
HeroActiveThe player. It is placed at the spawn point of the level.
Platform, Enemy, Collectible, Checkpoint, PropActiveThe object types the level uses. The game creates them from the values that were read.
Build X, Build YCounterThe position of the object being built.
Build W, Build HCounterThe size of the object being built.
Build ClockTimerThe tick of the builder. It fires once per section.
Status TextStringThe line that reports the name of the level and the unknown types.
CreateCreateThe Fusion object that creates the objects of the level.

Two JSON++ Object instances are used because they hold two different documents. The level is never written, and the build state is rewritten for every entry.

G. Step-by-Step Implementation​

Step 1 — Create the frame and the objects​

  1. Create a frame named Forest and give it the size of the level.
  2. Add the objects listed in the previous section.
  3. Add the five object types to the frame, outside the visible area of the level.
  4. Set the Build Clock to fire once, with a delay that gives the game a moment to draw the frame.

Step 2 — Load the level and the build state​

Add a Start of Frame event with two actions:

  • Action: Level Data : Load JSON from file at Apppath$ + "level_forest.json".
  • Action: Build State : Load JSON from string "{""build"":{""type"":"""",""known"":0,""unknown"":0,""x"":0,""y"":0,""width"":0,""height"":0,""enemy"":"""",""item"":"""",""id"":"""",""prop"":"""",""section"":0,""sections"":0,""loading"":0,""done"":0}}".

The build state is loaded from a string so that every member the events read already exists. A write that has to create a missing branch is refused by the browser runtime.

Step 3 — Place the hero and open the first section​

Add an event with the condition Level Data: On JSON Loaded:

  • Action: Hero : Set X Position to GetNumber( "Level Data", "/level/spawn/x" ).
  • Action: Hero : Set Y Position to GetNumber( "Level Data", "/level/spawn/y" ).
  • Action: Status Text : Set alterable string to GetString( "Level Data", "/level/name" ).
  • Action: Build State : Set number GetNumItems( "Level Data", "/sections" ) at "/build" with key "sections".
  • Action: Build State : Set number 0 at "/build" with key "section".
  • Action: Build State : Set number 1 at "/build" with key "loading".

The hero is placed by Fusion with the two values that were read. The extension provides the numbers and the movement belongs to the game.

Step 4 — Build one section per tick​

Add an event with the condition Build Clock: On timer and one group:

  • Condition of the group: Build State : Is "/build/loading" equal to 1?.
  • Action: Level Data : Start loop "Objects" at "/sections/" + Str$(GetNumber( "Build State", "/build/section" )) + "/objects".

The path of the loop is built from the number of the current section. The loop visits the entries of that section and nothing else.

Step 5 — Read the entry that the loop is on​

Add an event with the condition Level Data: On Loop "Objects":

  • Action: Build State : Set string GetString( "Level Data", GetLoopPath( "Level Data", "Objects" ) + "/type" ) at "/build" with key "type".
  • Action: Build State : Set number GetNumber( "Level Data", GetLoopPath( "Level Data", "Objects" ) + "/x" ) at "/build" with key "x".
  • Action: Build State : Set number GetNumber( "Level Data", GetLoopPath( "Level Data", "Objects" ) + "/y" ) at "/build" with key "y".
  • Action: Build State : Set number 0 at "/build" with key "known".

GetLoopPath returns the path of the current entry, so the members of that entry are read through it. The three actions run before the groups of the event, and the groups read what they need from the build state.

Step 6 — Build a platform​

Add a group to the event of Step 5:

  • Condition of the group: Build State : Is "/build/type" equal to "platform"?.
  • Action: Build State : Set number GetNumber( "Level Data", GetLoopPath( "Level Data", "Objects" ) + "/width" ) at "/build" with key "width".
  • Action: Build State : Set number GetNumber( "Level Data", GetLoopPath( "Level Data", "Objects" ) + "/height" ) at "/build" with key "height".
  • Action: Build State : Set number 1 at "/build" with key "known".
  • Action: Build X : Set counter to GetNumber( "Build State", "/build/x" ).
  • Action: Build Y : Set counter to GetNumber( "Build State", "/build/y" ).
  • Action: Build W : Set counter to GetNumber( "Build State", "/build/width" ).
  • Action: Build H : Set counter to GetNumber( "Build State", "/build/height" ).

The group ends with the creation of the platform: the Create object of the frame places a Platform Active at the coordinates of the two counters and gives it the size of the other two. That creation is a Fusion action.

Step 7 — Build an enemy​

Add a second group to the event of Step 5:

  • Condition of the group: Build State : Is "/build/type" equal to "enemy"?.
  • Action: Build State : Set string GetString( "Level Data", GetLoopPath( "Level Data", "Objects" ) + "/enemy" ) at "/build" with key "enemy".
  • Action: Build State : Set number 1 at "/build" with key "known".
  • Action: Build X : Set counter to GetNumber( "Build State", "/build/x" ).
  • Action: Build Y : Set counter to GetNumber( "Build State", "/build/y" ).

The group ends with the creation of the enemy at the coordinates of the two counters, and the identifier of the type is written on the template before the creation so that the new instance inherits it. The new enemy then reads its health and its damage from the enemy database, as the Data-Driven Enemy Database shows.

Step 8 — Build a collectible​

Add a third group to the event of Step 5:

  • Condition of the group: Build State : Is "/build/type" equal to "collectible"?.
  • Action: Build State : Set string GetString( "Level Data", GetLoopPath( "Level Data", "Objects" ) + "/item" ) at "/build" with key "item".
  • Action: Build State : Set number 1 at "/build" with key "known".
  • Action: Build X : Set counter to GetNumber( "Build State", "/build/x" ).
  • Action: Build Y : Set counter to GetNumber( "Build State", "/build/y" ).

The group ends with the creation of the collectible at the coordinates of the two counters. The item the collectible gives is read by the inventory of the game when the hero touches it.

Step 9 — Build a checkpoint​

Add a fourth group to the event of Step 5:

  • Condition of the group: Build State : Is "/build/type" equal to "checkpoint"?.
  • Action: Build State : Set string GetString( "Level Data", GetLoopPath( "Level Data", "Objects" ) + "/id" ) at "/build" with key "id".
  • Action: Build State : Set number 1 at "/build" with key "known".
  • Action: Build X : Set counter to GetNumber( "Build State", "/build/x" ).
  • Action: Build Y : Set counter to GetNumber( "Build State", "/build/y" ).

The identifier of the checkpoint is cp_forest_bridge, the same identifier the save system stores. The checkpoints and autosave guide shows the other half of it.

Step 10 — Build a decoration​

Add a fifth group to the event of Step 5:

  • Condition of the group: Build State : Is "/build/type" equal to "prop"?.
  • Action: Build State : Set string GetString( "Level Data", GetLoopPath( "Level Data", "Objects" ) + "/prop" ) at "/build" with key "prop".
  • Action: Build State : Set number 1 at "/build" with key "known".
  • Action: Build X : Set counter to GetNumber( "Build State", "/build/x" ).
  • Action: Build Y : Set counter to GetNumber( "Build State", "/build/y" ).

Step 11 — Report an unknown type​

Add a last group to the event of Step 5:

  • Condition of the group: Build State : Is "/build/known" equal to 0?.
  • Action: Build State : Add number 1 at "/build" with key "unknown".
  • Action: Status Text : Set alterable string to "Unknown object type: " + GetString( "Build State", "/build/type" ).

The groups are tested in the order they appear in the event. The first group whose type matches runs and sets /build/known to one, so the last group only runs when no other group matched.

Step 12 — Close the section and open the next one​

Add an event with the condition Level Data: On End Loop "Objects":

  • Action: Build State : Add number 1 at "/build" with key "section".
  • Action: Build State : Set number 0 at "/build" with key "type".

The game compares the number of the section with the number of sections of the level. When the level is finished, it writes 1 into /build/done and 0 into /build/loading, and the status line announces that the level is ready. That comparison is between two values of the game, and it belongs to Fusion.

Step 13 — Handle a failed load​

Add an event with the condition Level Data: On Error:

  • Action: Status Text : Set alterable string to GetError( "Level Data" ).

The hero stays where the last level left it and the status line explains that the level could not be read. The game should not continue with an empty forest.

I. Expected Behavior​

Before the level is built​

The build state is empty and no section has been built:

{
  "build": {
    "type": "",
    "known": 0,
    "unknown": 0,
    "x": 0,
    "y": 0,
    "width": 0,
    "height": 0,
    "enemy": "",
    "item": "",
    "id": "",
    "prop": "",
    "section": 0,
    "sections": 3,
    "loading": 1,
    "done": 0
  }
}

The hero stands at the spawn point, 160 and 1520, and the status line reads Whispering Forest.

After the level is built​

The build state records that the three sections were built and that one entry was not understood:

{
  "build": {
    "type": "",
    "known": 0,
    "unknown": 1,
    "x": 0,
    "y": 0,
    "width": 0,
    "height": 0,
    "enemy": "",
    "item": "",
    "id": "",
    "prop": "",
    "section": 3,
    "sections": 3,
    "loading": 0,
    "done": 1
  }
}

The file of the level is unchanged by the build. Only the build state records the work, and the status line reports the type that the game did not know: Unknown object type: mystery.

J. Edge Cases & Error Handling​

SituationWhat happensHandling
level_forest.json does not existThe load fails and On Error runsShow the message and return to the map. Ship the file with the game.
level_forest.json contains invalid JSONThe document is not replaced and the error text describes the problemKeep the technical text for a log and show a short message to the player.
The level has no sections arrayThe loop has no item and nothing is builtCheck /sections with the exists condition before the first tick.
An entry has no x or no yThe position reads as a fallback and the object appears at the originGive every entry a position, and check the member with the exists condition before the build.
A platform has no widthThe size reads as a fallback and the platform has no sizeGive every platform a width and a height, and reject the file with a schema when it is written.
An entry has a type the game does not knowNo group matches and the entry is countedThe last group reports the type in the status line and adds it to /build/unknown.
A type has a typo, such as platfromThe entry is reported as unknownThe report names the type, so the typo is visible in one glance.
An enemy names a type the enemy database does not knowThe instance appears with fallback valuesKeep the two files in step, and let the enemy check its own definition.
A section holds hundreds of objectsThe frame is busy while the section is builtSplit the section further, or build one section over several ticks.
The same level is built twiceEvery object appears twiceGuard the build with the flag /build/loading, and start the builder only once.
The hero appears inside a platformThe hero falls or is pushed outKeep the spawn point on a platform of the first section.
A checkpoint names an identifier the save system does not knowThe checkpoint saves nothingUse the identifiers of the checkpoints of the game, such as cp_forest_bridge.
The level is loaded again after the hero movedThe hero returns to the spawn pointLoad the level when the frame starts and never again, or save the position before a reload.
The game runs on HTML5Apppath$ has no meaningUse a browser reference such as storage://level_forest and read the platform-specific file guide.

Two rules deserve emphasis. First, an unknown type is a mistake in the file and it must be visible: a level that quietly loses an enemy is worse than a level that refuses to load. Second, the level file describes the world and the build state describes the work: keep them apart and a rebuild starts from nothing every time.

K. Runtime Compatibility​

The system relies on four groups of features: reading a file, reading an array in a loop, reading the members of an entry and writing values into a document.

TargetFile workLoop, read and writeNotes
WindowsImplemented and testedImplemented and testedApppath$ resolves to the folder of the exported application.
AndroidImplemented, not verified by an automated checkImplemented, not verified by an automated checkReads inside the sandbox of the application. Test the export.
HTML5Implemented and testedImplemented and testedUse a browser reference. A write that has to create a missing branch is refused, so the build state is loaded complete.
macOSUnknownUnknownNo separate build was verified.
iOSImplemented, not verified by an automated checkImplemented, not verified by an automated checkReads inside the sandbox of the application. Test the export.

One difference touches the conditions. The native runtime recognizes a member whose value is null when the exists condition asks whether a path is there, while the browser runtime reports such a member as absent. The level file of this guide never stores null, so both targets answer the same way. The full matrix is on the runtime compatibility page.

M. Next Steps​

  • Build the level in the background. The builder can keep working while the player moves, and the objects of the next section appear as the hero walks towards them.
  • Add a trigger volume. An entry of type trigger can carry the name of a script the game runs when the hero enters a region, and the dispatcher gives it a group of its own.
  • Store the collected items in the level. The level file can hold the collectibles that were already taken, and the world state guide shows how to keep them.
  • Validate the file before the build. A JSON schema rejects a platform without a width and an entry without a position, and the error names the member that is missing.
  • Build the other levels with the same events. The file level_village.json and the file level_cavern.json follow the same shape, and the builder changes only the name of the file it reads.
