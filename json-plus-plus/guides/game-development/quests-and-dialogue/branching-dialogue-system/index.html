Branching Dialogue System

A. Overview​

Emberfall talks to its heroes. Elder Rook asks for help with the slimes, the player may ask questions before answering, and the answer changes what the village remembers. A dialogue of that kind is data: a set of nodes, a set of answers for each node, and the conditions that decide whether an answer is offered at all.

DifficultyAdvanced
ComplexityHigh — two documents, one walk over the answers, one conversation state machine
Fusion skillsFrame events, Active objects, String objects, global variables, group conditions, an event that runs every frame
JSON++ skillsAbsolute paths, reading nested members, comparing a value with a value read from the document, iterating an array, the exists condition, saving a file

Gameplay scenario​

The hero walks into Elder Rook in the village square of level_village. A panel opens in the middle of the screen. Rook says that three slimes are eating the lotus crop, and three answers appear below his words: I will cull them, What do they look like and That is not my fight. The middle answer opens another node that explains the slimes and leads back. The first answer sets the quest under way and closes the conversation. The third one closes it with a different memory.

A day later, when the quest is ready to be reported, the same click on Rook opens a different dialogue, because the state of the quest has changed.

Learning objectives​

By the end of this guide you will be able to:

  • describe a conversation as a graph of nodes, each with its own text and its own answers;
  • fill a dialogue interface from the data instead of from a hardcoded list of buttons;
  • hide an answer whose condition is not met and offer it again later when the condition changes;
  • move from one node to the next and end a conversation without leaving the panel on screen;
  • store the decisions of the player and the variables of a conversation in a document that survives a restart;
  • make a whole dialogue depend on the state of a quest.

What you will build​

A dialogue panel with a text area and three answer buttons, a dialogue definition file (dialogues.json), a player state file (player_state.json) and the events that open a conversation, list the answers, apply a choice and close the conversation.

B. Prerequisites​

Fusion knowledge you need

  • Frame events such as Start of Frame, and events with the condition Always, which are evaluated again in every frame.
  • Group conditions under an event, and the order in which the actions of an event run before its groups are evaluated.
  • Active objects, the is clicked condition, and the Set visible and Set invisible actions.
  • The String object and the Set alterable string action.
  • Global variables on the Special object, written as Special : Set <name> to <value>, and comparisons of two values such as a global variable and a number.

JSON++ concepts you need

  • JSON Paths, because every read of a dialogue is addressed by an absolute path.
  • Missing, Null and Empty, because a member that is absent and a member that holds an empty text are different, and this guide uses the difference to know whether an answer ends the conversation.
  • Conditions and Triggers, in particular the difference between a state condition and a trigger such as On JSON Loaded.
  • Understanding JSON Loops and Reading Loop Values, because the answers of a node are an array that the interface walks.
  • JSON Instance State: the dialogue definitions and the player state are two separate instances, each with its own document.

Runtime limitations to keep in mind

  • JSON++ Object stores the dialogue and the state of the player. It never draws a panel, never shows a button and never moves the hero. The Fusion events of this guide copy the text out of the document and into the interface.
  • A JSON++ Object cannot wait for a click. The event that reacts to a click is a Fusion event, and it reads the document that the dialogue left open.
  • File paths follow the host. Apppath$ + "player_state.json" works on Windows. HTML5 needs a browser reference such as storage://player_state. See platform-specific file operations.
  • The walk of the answers prepares its work from a snapshot. An edit made while the walk is running does not change what the walk visits.

Standard objects used here

JSON++ Object, Active, String and Special. Nothing else is required.

C. Gameplay Scenario​

The village square of Emberfall holds two characters that speak: Elder Rook, who gives the quests, and Bella, the merchant. Each of them has one or more dialogues, and each dialogue belongs to an NPC.

A dialogue is a map of nodes. Every node holds the line the NPC says and the list of answers the player may choose. One answer leads to another node, another one ends the conversation, and a third one changes the state of the world.

The panel is a group of Fusion objects that the game shows and hides. The dialogue does not draw the panel and it does not write a single letter of the text of an answer. It only holds the text. The interface reads that text from the document and copies it into the String objects of the panel, one answer at a time, while the walk over the answers is running.

The player state document holds three things: the state of the quests, the decisions of the player and the variables of the conversations. The decisions are the answers that were actually chosen, kept as one flag per answer. The variables are the facts that the conversations establish, such as Elder Rook trusts the hero.

When the hero comes back after the quest is ready, Rook greets the hero with another dialogue. The dialogue that opens is chosen by the state of the quest, and the answers that are offered inside it are chosen by the same state.

D. Final Result​

The completed system behaves like this:

  • Clicking an NPC opens a panel with the text of the NPC and the answers of the current node.
  • An answer that is not offered is not drawn. Rook stops offering I will cull them as soon as the quest is under way.
  • The panel keeps the position of the conversation: the answers of a node lead to the next node, and the text of the panel follows.
  • The last answer of a branch closes the panel and leaves the conversation empty.
  • Every answer that is chosen is written to the player state document, together with the variables it sets.
  • A dialogue can depend on the state of a quest. Rook pays the hero in one dialogue and asks for help in another.

E. JSON Data Structure​

The dialogue definitions​

The root holds the version of the document and one member, dialogues. The dialogues member is an object whose keys are the identifiers of the dialogues.

Each dialogue holds four members:

MemberTypeMeaning
npcstringThe identifier of the NPC who speaks this dialogue.
startstringThe identifier of the node the conversation opens with.
nodesobjectOne entry per node, keyed by the identifier of the node.
descriptionstringOptional text for the debug log of the game.

Each node holds a text and a list of options. The list is an array because the order of the answers matters: the first answer is the one the player reads first.

Each answer holds these members:

MemberTypeMeaning
idstringThe identifier of the answer, used to record the decision.
textstringThe words shown on the button.
endsnumber1 when choosing this answer closes the conversation.
nextstringThe identifier of the node that follows, present when ends is 0.
conditionalnumber1 when the answer is only offered while a condition holds.
requires_queststringThe identifier of the quest the condition refers to, present when conditional is 1.
requires_statestringThe state that quest must be in, present when conditional is 1.
sets_variablestringThe variable this answer sets, present only when the answer sets one.

Two members are left out on purpose. The answer opt_ask has no sets_variable, because it does not change anything. The answer opt_farewell has no next, because it ends the conversation. The interface tells them apart with the exists condition, and the two states are not the same: a missing member and a member that holds an empty text.

The state of the player​

{
  "schema_version": 1,
  "quests": {
    "quest_slime_cull": {"state": "ready", "reward_claimed": 0}
  },
  "decisions": {
    "dlg_rook_intro": {"opt_accept": 0, "opt_ask": 0, "opt_refuse": 0},
    "dlg_rook_report": {"opt_pay": 0, "opt_thanks": 0},
    "dlg_bella_greet": {"opt_farewell": 0},
    "dlg_bella_stock": {"opt_trade": 0}
  },
  "variables": {
    "rook_trusts_hero": 0,
    "rook_refused": 0
  }
}

This document is written to disk. It holds three sections:

MemberTypeMeaning
questsobjectThe state of each quest, with the same shape as the quest state document of the quest tracking guide.
decisionsobjectOne entry per dialogue, holding one flag per answer. A flag of 1 means the answer was chosen.
variablesobjectThe facts that the conversations establish. Every member is a number.

The decisions are kept as one flag per answer rather than as the text of the last answer. A flag answers a question that a single text cannot: has the player already refused to help. The member last_option is added by the events of this guide and holds the identifier of the answer that was chosen last.

The variables are the memory of the conversations. rook_trusts_hero becomes 1 when the hero accepts the quest, and rook_refused becomes 1 when the hero says no. Other systems read them: the reputation guide turns them into a score, and a shop may refuse a discount to a hero who refused to help.

Two documents, two jobs​

The dialogue definitions belong to the game and never change while it runs. The state of the player belongs to the run and changes with every answer. A new game only has to reset the small document.

Six global variables on the Special object carry the state of the running conversation:

Global variableTypeMeaning
Current DialoguetextThe identifier of the dialogue that is running, such as dlg_rook_intro.
Current NodetextThe identifier of the node that is on screen.
Option PathtextThe path of the answer that is being examined.
Option Opennumber1 when the answer that is being examined may be shown.
Choice Readynumber1 when an answer has just been chosen and still has to be applied.
Choice Acceptednumber1 when that answer passes the conditions of its dialogue.

A seventh global, Refresh Ready, asks the interface to redraw itself. The running conversation is transient and stays in these globals; only the decisions and the variables are written to the document.

G. Step-by-Step Implementation​

Step 1 — Create the objects and the globals​

  1. Add the objects listed in the previous section to the frame that holds the village square.
  2. Create the seven global variables on the Special object: Current Dialogue, Current Node, Option Path, Option Open, Choice Ready, Choice Accepted and Refresh Ready. Leave every one of them at zero or empty.
  3. Set the Dialogue Panel and its three Option Buttons to invisible, so that the panel is closed when the frame starts.

Step 2 — Load the two documents​

Add a Start of Frame event with two actions:

  • Action: Dialogue Data : Load JSON from file at Apppath$ + "dialogues.json".
  • Action: Player State : Load JSON from file at Apppath$ + "player_state.json".

Step 3 — Open a conversation with Elder Rook​

Add an event with the condition Elder Rook is clicked.

  • Action: Dialogue Panel : Set visible.
  • Action: Speaker Label : Set alterable string to "Elder Rook".
  • Action: Special : Set Current Dialogue to "dlg_rook_intro".
  • Action: Special : Set Current Node to GetString( "Dialogue Data", "/dialogues/dlg_rook_intro/start" ).
  • Action: Special : Set Refresh Ready to 1.

Under that event, add a group:

  • Condition of the group: Player State: Is "/quests/quest_slime_cull/state" equal to "ready".
  • Action: Special : Set Current Dialogue to "dlg_rook_report".
  • Action: Special : Set Current Node to GetString( "Dialogue Data", "/dialogues/dlg_rook_report/start" ).

The actions of the event run first and open the conversation that asks for help. The group runs after and replaces it with the dialogue that pays the hero, when the quest is ready. That is the whole rule for choosing a dialogue: the state of the quest decides.

Add the same event for Bella, with dlg_bella_greet as the first dialogue and dlg_bella_stock in the group, whose condition is Player State: Is "/quests/quest_slime_cull/state" equal to "completed".

Step 4 — Redraw the panel​

Add an event with the condition Always. The events that run every frame are placed below the events that set the flags, so that a flag set in this frame is seen in the same frame.

  • Condition of the group: Special : Refresh Ready = 1.
  • Action: Special : Set Refresh Ready to 0.
  • Action: Dialogue Text : Set alterable string to GetString( "Dialogue Data", "/dialogues/" + Current Dialogue + "/nodes/" + Current Node + "/text" ).
  • Action: Option Button 1 : Set invisible.
  • Action: Option Button 2 : Set invisible.
  • Action: Option Button 3 : Set invisible.
  • Action: Dialogue Data : Start loop "Options" at "/dialogues/" + Current Dialogue + "/nodes/" + Current Node + "/options".

The walk of the answers starts here. The three buttons are hidden first, because the number of answers of a node is not known before the walk.

Step 5 — Walk the answers and fill the buttons​

Add an event with the condition Dialogue Data: On Loop "Options".

  • Action: Special : Set Option Path to GetLoopPath( "Dialogue Data", "Options" ).
  • Action: Special : Set Option Open to 1.

Under that event, add a group that applies the condition of the answer:

  • Condition of the group: Dialogue Data: Is Option Path + "/conditional" equal to 1.
  • Action: Special : Set Option Open to 0.

Under that group, add a second group:

  • Condition of the group: Player State: Is "/quests/" + GetString( "Dialogue Data", Option Path + "/requires_quest" ) + "/state" equal to GetString( "Dialogue Data", Option Path + "/requires_state" ).
  • Action: Special : Set Option Open to 1.

The order of the two actions matters. The answer is closed first and opened again when its condition holds, so an answer with a condition that is not met stays closed.

Under the first event, add one group per button:

  • Condition of the group: GetLoopIndex( "Dialogue Data", "Options" ) = 0.
  • Action: Option Label 1 : Set alterable string to GetString( "Dialogue Data", Option Path + "/text" ).

Under that group, add one more group:

  • Condition of the group: Special : Option Open = 1.
  • Action: Option Button 1 : Set visible.

Repeat for the second button with the condition GetLoopIndex( "Dialogue Data", "Options" ) = 1 and the third button with GetLoopIndex( "Dialogue Data", "Options" ) = 2.

The loop path is the path of the answer that is being examined, so every read inside the walk uses the same base. The loop index is the position of the answer in the array, which is what decides which button receives it.

Step 6 — React to a click on an answer​

Add one event per button. The first one reads:

  • Condition: Option Button 1 is clicked.
  • Action: Special : Set Option Path to "/dialogues/" + Current Dialogue + "/nodes/" + Current Node + "/options/0".
  • Action: Special : Set Choice Ready to 1.

The second button uses /options/1 and the third one /options/2.

The buttons keep their position in the array even when an answer is hidden, so a hidden answer leaves an empty place in the panel instead of moving the other answers.

Step 7 — Apply the choice​

Add a second group to the Always event, placed above the group of Step 4 so that a choice is applied before the panel is redrawn.

  • Condition of the group: Special : Choice Ready = 1.
  • Action: Special : Set Choice Ready to 0.
  • Action: Special : Set Choice Accepted to 0.

Under that group, add a group for an answer without a condition:

  • Condition of the group: Dialogue Data: Is Option Path + "/conditional" equal to 0.
  • Action: Special : Set Choice Accepted to 1.

Under the first group, add another group for an answer with a condition:

  • Condition of the group: Dialogue Data: Is Option Path + "/conditional" equal to 1.
  • Action: Special : Set Choice Accepted to 0.

Under that group, add a third group:

  • Condition of the group: Player State: Is "/quests/" + GetString( "Dialogue Data", Option Path + "/requires_quest" ) + "/state" equal to GetString( "Dialogue Data", Option Path + "/requires_state" ).
  • Action: Special : Set Choice Accepted to 1.

The answer is refused when its condition does not hold. The flag Choice Accepted is what the last group of this step looks at.

Step 8 — Record the decision and move to the next node​

Under the group Special : Choice Accepted = 1, add these actions:

  • Action: Player State : Set number 1 at "/decisions/" + Current Dialogue + with key GetString( "Dialogue Data", Option Path + "/id" ).
  • Action: Player State : Set string GetString( "Dialogue Data", Option Path + "/id" ) at "/decisions/" + Current Dialogue + with key "last_option".

Under that group, add a group for the variable that the answer sets:

  • Condition of the group: Dialogue Data: Option Path + "/sets_variable" exists.
  • Action: Player State : Set number 1 at "/variables" with key GetString( "Dialogue Data", Option Path + "/sets_variable" ).

And a group for the end of the conversation:

  • Condition of the group: Dialogue Data: Is Option Path + "/ends" equal to 1.
  • Action: Dialogue Panel : Set invisible.
  • Action: Special : Set Current Dialogue to "".
  • Action: Special : Set Refresh Ready to 0.

And the group for the move to the next node:

  • Condition of the group: Dialogue Data: Is Option Path + "/ends" equal to 0.
  • Action: Special : Set Current Node to GetString( "Dialogue Data", Option Path + "/next" ).
  • Action: Special : Set Refresh Ready to 1.

The flag Refresh Ready is what makes the panel follow the conversation: the next node is written into Current Node, and the group of Step 4 redraws the text and walks the answers of that node.

Step 9 — Write the state to disk​

Add an event with the condition Player State: On JSON Saved to File.

  • Action: Status Label : Set alterable string to "Decisions saved".

And the action that writes the file, at the end of the group that accepts a choice:

  • Action: Player State : Save JSON to file at Apppath$ + "player_state.json".

The file is written once the answer has been applied, not when the answer was clicked. A conversation that is interrupted in the middle therefore keeps the answers that were already given.

Step 10 — Report a failure to the player​

Add one event for each JSON++ Object.

  • Condition: Player State: On Error.
  • Action: Status Label : Set alterable string to GetError( "Player State" ).

And a second one:

  • Condition: Dialogue Data: On Error.
  • Action: Status Label : Set alterable string to "Dialogues unavailable".

I. Expected Behavior​

Before the hero speaks to Rook​

player_state.json holds the state of the quests and the empty memory of the conversations:

{
  "schema_version": 1,
  "quests": {
    "quest_slime_cull": {"state": "ready", "reward_claimed": 0}
  },
  "decisions": {
    "dlg_rook_intro": {"opt_accept": 0, "opt_ask": 0, "opt_refuse": 0},
    "dlg_rook_report": {"opt_pay": 0, "opt_thanks": 0},
    "dlg_bella_greet": {"opt_farewell": 0},
    "dlg_bella_stock": {"opt_trade": 0}
  },
  "variables": {
    "rook_trusts_hero": 0,
    "rook_refused": 0
  }
}

Every flag of the decisions is at zero and every variable is at zero. The quest is ready, so a click on Rook opens the dialogue that pays the hero and not the one that asks for help.

After the hero accepts the quest and refuses another offer​

{
  "schema_version": 1,
  "quests": {
    "quest_slime_cull": {"state": "ready", "reward_claimed": 0}
  },
  "decisions": {
    "dlg_rook_intro": {"opt_accept": 1, "opt_ask": 0, "opt_refuse": 1},
    "dlg_rook_report": {"opt_pay": 0, "opt_thanks": 0},
    "dlg_bella_greet": {"opt_farewell": 0},
    "dlg_bella_stock": {"opt_trade": 0}
  },
  "variables": {
    "rook_trusts_hero": 1,
    "rook_refused": 1
  }
}

The flag opt_accept is at one, the flag opt_refuse is at one, and the two variables record what the hero said. The member last_option has been added to dlg_rook_intro by the event that applies a choice, and holds opt_refuse.

J. Edge Cases & Error Handling​

SituationWhat happensHandling
dialogues.json does not existThe load fails and On Error runsShow a short message and let the game run without conversations. Ship the file with the game.
A node holds no answerThe walk visits nothing and the panel shows the text with no buttonGive every node at least one answer, and keep the buttons hidden until the walk opens them.
An answer points to a node that does not existThe text of the next node reads as an empty textCheck the identifiers of the nodes when the definitions are written, and keep the node map complete.
The condition of an answer never holdsThe answer stays hiddenThat is the intended result. Make sure the quest state that the condition reads is the one the game writes.
The player clicks a hidden answerThe choice is refused by the check of the conditionThe same check protects the panel and the document.
The player clicks twice in the same frameThe second click overwrites the path of the firstClear the flag Choice Ready as soon as the choice is taken, as this guide does.
The conversation is closed while a choice is pendingThe flag Refresh Ready is cleared when the conversation endsClear the flag in the branch that ends the conversation.
A quest state member is missingThe condition of the answer never holdsKeep the quests section of the player state document complete.
The player state file cannot be writtenThe save fails and On Error runsKeep the decisions in memory for the rest of the run and tell the player that the conversation was not remembered.
An answer sets a variable that does not existThe write creates the member with the value oneDeclare the variables of a conversation in the document before the game writes them.
The panel is still open when the level endsThe panel stays on screen in the next frameHide the panel in the event that leaves the level.
The game runs on HTML5Apppath$ has no meaningUse a browser reference such as storage://player_state. See the platform-specific file guide.

Two rules deserve emphasis. First, a missing member and an empty text are different, and this guide relies on that: the answer opt_farewell has no next member, and that absence is what ends the conversation. Second, the choice is applied before the panel is redrawn. Reversing the two groups shows the previous node for one frame, which reads as a stutter.

K. Runtime Compatibility​

The system relies on four groups of features: file operations, reading and writing values, comparison of values and iteration over an array.

One difference matters for the condition of an answer. On the native runtime the exists condition accepts a member whose value is null, while the HTML5 runtime reports such a member as absent. The dialogue definitions never store null, so both targets agree. The full matrix is on the runtime compatibility page.

A second difference matters for the walk. The loop prepares its work from a snapshot and the item notifications are scheduled, so the answers that are offered are the answers of the node at the moment the walk started. A node that changes while the walk runs is drawn by the next walk.

M. Next Steps​

  • Choose the dialogue with a walk. Instead of testing two dialogues by hand, walk the map of dialogues and keep the first one whose npc matches and whose condition holds.
  • Draw the panel with a Create object. A node with more than three answers then needs no extra buttons, because the interface can create one row per answer.
  • Speak the lines of the NPC. Add a voice member to every node and play it with a Sound object when the node appears.
  • Translate the text. The text of the nodes and the answers is a good candidate for the dictionaries of the localization guide.
  • Add a portrait. Give every NPC a portrait and read the identifier of the NPC from the dialogue to show it.
  • Protect the file. The extension can encrypt the file it writes and validate it against a JSON schema. See Enable Encryption and Enable JSON Schema Validation.
