Quest and Objective Tracking

A. Overview​

Emberfall keeps track of what the hero has been asked to do. A quest lives in two places: a definition that belongs to the game, and a progress record that belongs to the player. This guide builds both, plus the events that carry the hero from one state of a quest to the next.

DifficultyIntermediate
ComplexityMedium — two documents, one state machine per quest, one loop over the objectives
Fusion skillsFrame events, Active objects, Counter and String objects, global variables, group conditions
JSON++ skillsAbsolute paths, reading nested members, arithmetic on numbers, comparing a value with a number read from the document, iterating an object, saving a file

Gameplay scenario​

Elder Rook stops the hero in the village square of Emberfall. Three slimes have been eating the lotus crop near the old bridge, and he wants three of them dead. He also wants proof, and proof means two lotus herbs taken from the nests the slimes used. When both demands are met, he wants the hero back in front of him, because the payment waits at the end. A tracker in the corner of the screen shows the quest from the moment it is accepted until the moment the reward is in the hero's purse.

Learning objectives​

By the end of this guide you will be able to:

  • keep the definition of a quest apart from the progress of the player, so that a new game starts with a clean record;
  • model the states of a quest as data: available, active, ready and completed;
  • advance the right objective of the right quest without relying on the position of an entry in an array;
  • mark a quest as ready only when every one of its objectives is complete;
  • pay a reward once and refuse to pay it a second time;
  • write the progress of the quests to a file and restore it when the level starts.

What you will build​

A quest tracker panel, a quest definition file (quests.json), a quest progress file (quest_state.json), and the events that accept a quest, count a defeated slime, collect an herb, close a quest and pay the reward.

B. Prerequisites​

Fusion knowledge you need

  • Frame events such as Start of Frame and Start of Level.
  • Group conditions under an event, and the order in which the actions of an event run before its groups are evaluated.
  • Active objects, the is clicked condition and the is overlapping Active condition.
  • The String object and the Set alterable string action.
  • The Counter object and its Set counter and Add to counter actions.
  • Global variables on the Special object, written as Special : Set <name> to <value>.
  • The alterable string of an Active object, used here to carry the identifier of an enemy.

JSON++ concepts you need

  • JSON Paths, because every read in this guide uses an absolute path that begins with /.
  • Missing, Null and Empty, because a quest that has no progress record is a different situation from a quest whose progress is zero.
  • Conditions and Triggers, in particular the difference between a state condition such as Is a path equal to a value and a trigger such as On JSON Loaded.
  • Understanding JSON Loops and Loop Lifecycle, because the tracker walks the objectives of the active quest.
  • Reading Loop Values, for the loop key and the loop index used to address the current objective.
  • JSON Instance State: the definition document and the progress document are two separate JSON++ Object instances, each with its own document.

Runtime limitations to keep in mind

  • JSON++ Object stores and transforms data. It never destroys a slime, never opens a chest and never draws the tracker. Each of those is a Fusion action placed in the event that reads or writes the data.
  • JSON++ Object has no action that deletes a file. A quest log that must be erased is overwritten with a fresh document.
  • File paths follow the host. Apppath$ + "quest_state.json" works on Windows. HTML5 needs a browser reference such as storage://quest_state, and the mobile targets write inside the sandbox of the application. See platform-specific file operations.
  • A save emits On JSON Saved to File when the file work completes. On some targets the completion is asynchronous, so the message that confirms a save belongs in that event.

Standard objects used here

JSON++ Object, Active, String, Counter and Special. Nothing else is required.

C. Gameplay Scenario​

Emberfall opens in the village square of level_village. Elder Rook stands next to the well. When the hero walks into him and clicks, the game looks at the quest log and asks two questions: is the slime cull still available, and has it already been accepted?

If the quest is available, Rook hands it over. The tracker appears in the corner of the screen and reads Slime Cull. Under the title, two lines describe the objectives: Slay three slimes: 0 / 3 and Gather two lotus herbs: 0 / 2.

The forest of level_forest holds slimes and lotus herbs. Each time the hero defeats a slime, the first objective advances by one. Each herb that the hero picks up advances the second one. When the third slime falls and the second herb is gathered, both objectives are complete and the quest is ready to be reported.

The hero walks back to Rook in the village square. The reward of sixty gold and two health potions is paid once, the quest state becomes completed, and the tracker folds away.

If the player closes the game and starts it again, the quest log comes back exactly as it was left: the slimes already killed stay killed, and the reward is never paid twice.

D. Final Result​

The completed system behaves like this:

  • The tracker stays hidden until a quest is accepted, and it shows the title, both objectives with their progress, and the reward.
  • Defeating a slime advances the objective that counts slimes, and gathering a herb advances the objective that counts herbs. Neither event touches the other.
  • A quest only reaches the state ready when every objective of that quest is complete. A quest with one open objective never reaches it.
  • The hero can talk to Rook as often as he likes: the reward is paid on the first visit that closes the quest, and never again.
  • Restarting the game restores the quests, the progress of every objective and the flag that records a paid reward.

E. JSON Data Structure​

The quest definitions​

{
  "schema_version": 1,
  "quests": {
    "quest_slime_cull": {
      "title": "Slime Cull",
      "giver": "npc_elder_rook",
      "turn_in": "npc_elder_rook",
      "objectives": {
        "defeat_slime": {
          "title": "Slay three slimes",
          "type": "defeat",
          "target": "slime",
          "required": 3
        },
        "collect_herb_lotus": {
          "title": "Gather two lotus herbs",
          "type": "collect",
          "target": "herb_lotus",
          "required": 2
        }
      },
      "reward": {
        "gold": 60,
        "item": "potion_health",
        "quantity": 2
      }
    },
    "quest_cavern_key": {
      "title": "The Cavern Key",
      "giver": "npc_warden_dorn",
      "turn_in": "npc_warden_dorn",
      "objectives": {
        "find_key_cavern": {
          "title": "Find the cavern key",
          "type": "collect",
          "target": "key_cavern",
          "required": 1
        }
      },
      "reward": {
        "gold": 40,
        "item": "potion_mana",
        "quantity": 1
      }
    }
  }
}

The root holds the version of the document and a single member, quests. The quests member is an object whose keys are the identifiers of the quests: quest_slime_cull and quest_cavern_key. A key is the identifier, never the position of the entry, so the file can be reordered without breaking a save.

Each quest holds these members:

MemberTypeMeaning
titlestringThe name shown by the tracker.
giverstringThe identifier of the NPC who offers the quest.
turn_instringThe identifier of the NPC who receives the report and pays the reward.
objectivesobjectOne entry per objective, keyed by the identifier of the objective.
rewardobjectWhat the player receives when the quest is closed.

Each objective holds a title for the interface, a type that tells the events what kind of progress they are counting, a target that names the enemy or the item involved, and a required number that says how much progress completes the objective.

The reward object holds a gold number, an item identifier and a quantity number. The reward of the slime cull is sixty gold and two health potions.

The progress of the player​

{
  "schema_version": 1,
  "quests": {
    "quest_slime_cull": {
      "state": "active",
      "reward_claimed": 0,
      "objectives": {
        "defeat_slime": {"progress": 2, "required": 3, "complete": 0},
        "collect_herb_lotus": {"progress": 1, "required": 2, "complete": 0}
      }
    },
    "quest_cavern_key": {
      "state": "available",
      "reward_claimed": 0,
      "objectives": {
        "find_key_cavern": {"progress": 0, "required": 1, "complete": 0}
      }
    }
  }
}

The progress document carries the same identifiers as the definitions. Every quest that exists in the game has an entry here from the first run, with the state available and a progress of zero for each objective. That is what makes an accept simple: the entry exists, so accepting a quest writes one member instead of creating a tree.

The state member is a string with one of four values:

StateMeaning
availableThe quest can be taken but has not been taken yet.
activeThe quest has been taken and at least one objective is still open.
readyEvery objective is complete and the report is still owed.
completedThe quest was closed and the reward was paid.

The reward_claimed member is a number that acts as a latch. It stays at 0 while the reward has not been paid and becomes 1 as soon as it has been. The state completed and this latch answer different questions: the state tells the interface what to draw, and the latch tells the events what may still be paid.

Each objective of the progress document holds three numbers:

MemberMeaning
progressHow much has been counted so far.
requiredA copy of the amount that completes the objective, taken when the quest was defined.
complete1 when the objective has been satisfied, 0 otherwise.

The copy of required inside the progress document is deliberate. It is the requirement that was in force when the quest was accepted, so a later change to the definition never rewrites a run that is already in progress.

Two documents, two jobs​

The definitions belong to the game and never change while it runs. The progress belongs to the player and changes constantly. Keeping them apart means a new game only has to reset the small document, and a designer can add a quest without touching a single saved file.

G. Step-by-Step Implementation​

Step 1 — Create the objects and the globals​

  1. Add the objects listed in the previous section to the frame that holds the gameplay.
  2. On the Special object, create a global variable named Current Quest and a global variable named Current Objective. Leave both empty.
  3. Give the Slime Active an alterable string named enemy_id and give the frame the value slime in it.
  4. Add a second Active to the hero as the hitbox and name it Attack. It follows the hero and is not drawn.

Step 2 — Load the two documents when the level starts​

Add a Start of Frame event with two actions:

  • Action: Quest Log : Load JSON from file at Apppath$ + "quests.json".
  • Action: Quest State : Load JSON from file at Apppath$ + "quest_state.json".

Both instances load independently. Each one reports its own On JSON Loaded and its own On Error, so a broken definition file never prevents the progress file from loading.

Step 3 — Clear the tracker when the level starts​

Add an event with the condition Quest State: On JSON Loaded. The tracker is empty until a quest is under way.

  • Action: Quest Title Label : Set alterable string to "".
  • Action: Reward Label : Set alterable string to "".

The two labels are filled again at the end of the walk of Step 7, with the quest that the walk belongs to. Nothing is drawn before the hero has taken a quest.

Step 4 — Accept the quest at Elder Rook​

Add an event with the condition Elder Rook is clicked.

  • Action: Special : Set Current Quest to "quest_slime_cull".

Under that event, add a group:

  • Condition of the group: Quest State: Is "/quests/quest_slime_cull/state" equal to "available".
  • Action: Quest State : Set string "active" at "/quests/quest_slime_cull" with key "state".
  • Action: Status Label : Set alterable string to "Quest accepted".
  • Action: Open Objectives : Set counter to 0.
  • Action: Quest State : Start loop "Objectives" at "/quests/" + Current Quest + "/objectives".

The group condition is what stops the quest from being accepted twice. If the state is already active, the group does not run and the tracker simply refreshes.

The loop started at the end of the group walks the objectives and fills the two objective lines of the tracker. It is described in Steps 6 and 7.

Step 5 — Count a defeated slime​

Add an event with the condition Attack is overlapping Slime.

  • Action: Slime : Destroy.

Under that event, add a group for the quest that is being worked on:

  • Condition of the group: Quest State: Is "/quests/" + Current Quest + "/state" equal to "active".
  • Action: Quest State : Add number 1 at "/quests/" + Current Quest + "/objectives/defeat_slime" with key "progress".
  • Action: Open Objectives : Set counter to 0.
  • Action: Quest State : Start loop "Objectives" at "/quests/" + Current Quest + "/objectives".

The group checks that the quest is active, so that a slime killed before the quest is accepted does not advance anything.

The action Add number 1 at "<path>" with key "progress" writes inside the objective selected by the path. The path ends with the identifier defeat_slime, and the key names the member inside it.

The last two actions prepare the walk of Step 6. The counter is emptied before the walk starts, because the walk counts the objectives that are still open. The count is raised before the walk begins, so the tracker always shows the number that includes the slime that has just fallen.

Step 6 — Walk the objectives, complete them and refresh the tracker​

Add an event with the condition Quest State: On Loop "Objectives".

  • Action: Special : Set Current Objective to GetLoopKey( "Quest State", "Objectives" ).

Under that event, add a group for the first line of the tracker:

  • Condition of the group: GetLoopIndex( "Quest State", "Objectives" ) = 0.
  • Action: Objective 1 Label : Set alterable string to GetString( "Quest Log", "/quests/" + Current Quest + "/objectives/" + Current Objective + "/title" ) + ": " + Str$(GetNumber( "Quest State", "/quests/" + Current Quest + "/objectives/" + Current Objective + "/progress" )) + " / " + Str$(GetNumber( "Quest State", "/quests/" + Current Quest + "/objectives/" + Current Objective + "/required" )).

Add a second group with the condition GetLoopIndex( "Quest State", "Objectives" ) = 1 and the same action on Objective 2 Label.

Add a third group that completes the objective once the count has reached the requirement:

  • Condition of the group: GetNumber( "Quest State", "/quests/" + Current Quest + "/objectives/" + Current Objective + "/progress" ) >= GetNumber( "Quest State", "/quests/" + Current Quest + "/objectives/" + Current Objective + "/required" ).
  • Action: Quest State : Set number GetNumber( "Quest State", "/quests/" + Current Quest + "/objectives/" + Current Objective + "/required" ) at "/quests/" + Current Quest + "/objectives/" + Current Objective + with key "progress".
  • Action: Quest State : Set number 1 at "/quests/" + Current Quest + "/objectives/" + Current Objective + with key "complete".

Both numbers of the comparison are read from the document, so a change of the requirement is followed without a change to the event. The first action of the group brings the progress back to the requirement when the count has gone past it, which keeps the tracker honest: an objective that needs three slimes shows three, not five.

Add a fourth group that counts the objectives that are still open:

  • Condition of the group: Quest State: Is "/quests/" + Current Quest + "/objectives/" + Current Objective + "/complete" equal to 0.
  • Action: Open Objectives : Add to counter 1.

The order of the groups matters. The third group writes the flag of completion and the fourth group reads it, so an objective that has just reached its requirement is not counted as open.

The loop key is the identifier of the objective, because the objectives are stored as an object keyed by that identifier. The loop index is the position in the walk, which is what decides which line of the tracker receives the text.

Step 7 — Decide the state of the quest at the end of the walk​

Add an event with the condition Quest State: On End Loop "Objectives". It runs when the walk is over.

  • Action: Quest Title Label : Set alterable string to GetString( "Quest Log", "/quests/" + Current Quest + "/title" ).
  • Action: Reward Label : Set alterable string to Str$(GetNumber( "Quest Log", "/quests/" + Current Quest + "/reward/gold" )) + " gold and " + Str$(GetNumber( "Quest Log", "/quests/" + Current Quest + "/reward/quantity" )) + " x " + GetString( "Quest Log", "/quests/" + Current Quest + "/reward/item" ).

Under that event, add a group:

  • Condition of the group: value("Open Objectives") = 0.
  • Action: Quest State : Set string "ready" at "/quests/" + Current Quest + with key "state".
  • Action: Status Label : Set alterable string to "Quest ready".
  • Action: Quest State : Save JSON to file at Apppath$ + "quest_state.json".

And a second group for the case where at least one objective is still open:

  • Condition of the group: value("Open Objectives") > 0.
  • Action: Quest State : Set string "active" at "/quests/" + Current Quest + with key "state".

The two groups are the condition of completion of a quest. The quest reaches ready only when the walk found no open objective at all.

The title and the reward are drawn here, because the walk belongs to the quest that the identifier names. Every path is absolute and built from that identifier, so the same three actions serve every quest of the game. The title of the quest is a string and is read with GetString; the gold and the quantity are numbers and are read with GetNumber.

Step 8 — Collect a lotus herb​

Add an event with the condition Herb is clicked.

  • Action: Herb : Destroy.

Under that event, add a group:

  • Condition of the group: Quest State: Is "/quests/" + Current Quest + "/state" equal to "active".
  • Action: Quest State : Add number 1 at "/quests/" + Current Quest + "/objectives/collect_herb_lotus" with key "progress".
  • Action: Open Objectives : Set counter to 0.
  • Action: Quest State : Start loop "Objectives" at "/quests/" + Current Quest + "/objectives".

The shape of this event is the shape of Step 5. The objective identifier changes, and so does the type of the objective, but the events do not. A new collecting objective is a new identifier in the documents and nothing else.

The event advances the quest that is being followed, so the tracker of a project with several quests at once shows one of them. A game that shows every quest at once gives each quest its own walk, with a name of its own.

Step 9 — Return to Elder Rook and take the reward​

Add a second event with the condition Elder Rook is clicked. This one runs when the quest is ready to be closed.

  • Action: Special : Set Current Quest to "quest_slime_cull".

Under that event, add a group:

  • Condition of the group: Quest State: Is "/quests/quest_slime_cull/state" equal to "ready".

Under that group, add a second group:

  • Condition of the group: Quest State: Is "/quests/quest_slime_cull/reward_claimed" equal to 0.
  • Action: Quest State : Set number 1 at "/quests/quest_slime_cull" with key "reward_claimed".
  • Action: Quest State : Set string "completed" at "/quests/quest_slime_cull" with key "state".
  • Action: Gold Counter : Add to counter GetNumber( "Quest Log", "/quests/quest_slime_cull/reward/gold" ).
  • Action: Status Label : Set alterable string to "Reward claimed".
  • Action: Quest State : Save JSON to file at Apppath$ + "quest_state.json".

The latch is what prevents a duplicated reward. The state ready would already be enough to block a second payment, but a player who saves the game, reloads it and talks to Rook again would meet a document where the state was rolled back and the latch was not. The latch is a separate member, so it survives on its own.

The gold is read from the definition document and added to the counter of the hero. The two health potions of the reward are added to the inventory by the inventory system, which is described in the stackable inventory guide.

The return to the giver is the moment the quest ends. The state ready says that every objective is complete and that the hero has not reported yet, and the state completed says that the reward was paid.

Step 10 — Report a failure to the player​

Add one event for each JSON++ Object.

  • Condition: Quest State: On Error.
  • Action: Status Label : Set alterable string to GetError( "Quest State" ).

And a second one:

  • Condition: Quest Log: On Error.
  • Action: Status Label : Set alterable string to "Quest definitions unavailable".

The technical message is shown for the progress file, because the player needs to know that the quests will not be remembered. The definitions are read-only, so a failure there only affects the wording of the interface and a short message is enough.

I. Expected Behavior​

Before the quest is accepted​

{
  "schema_version": 1,

    "quest_slime_cull": {

      "reward_claimed": 0,

      "objectives": {
        "find_key_cavern": {"progress": 0, "required": 1, "complete": 0}
      }

}

The tracker is empty, because the state of the quest is still available and the events that fill the tracker only run for a quest under way.

      }
    }
  }
}

The tracker reads Slime Cull, Slay three slimes: 2 / 3 and Gather two lotus herbs: 1 / 2. The state of the quest is still active, because the walk found two objectives that are not complete.

      }
    },
    "quest_cavern_key": {
      "state": "available",
      "reward_claimed": 0,
      "objectives": {
        "find_key_cavern": {"progress": 0, "required": 1, "complete": 0}
      }

The gold counter of the hero reads sixty, the status line reads Reward claimed, and a second visit to Elder Rook leaves the counter alone because reward_claimed is already 1.

J. Edge Cases & Error Handling​

SituationWhat happensHandling
quest_state.json does not existThe load fails and On Error runsCreate the file with the template of Section E the first time the game starts, or ship it with the game.
quest_state.json contains invalid JSONThe document is not replaced and the error text describes the problemShow the message to the player and keep the quest log out of the way.
A quest has no entry in the progress documentThe path selects nothing and the state reads as emptyShip a progress document that carries every quest, as in Section E.
A quest has no entry in the definitionsThe title and the reward read as empty textCompare the identifiers of the two documents when the game starts, and report the mismatch.
The player defeats a slime before accepting the questThe group that checks the state does not runNothing is counted, which is what the state available means.
The player defeats more slimes than the quest needsThe walk brings the progress back to the requirementKeep the normalisation inside the walk, as this guide does, so the tracker never shows a count above the requirement.
The player talks to Elder Rook before the objectives are completeThe state is active and the reward group does not runThe reward group only accepts the state ready.
The player talks to Elder Rook after the reward was paidThe state is completed and no group runsThe latch reward_claimed is the second line of defence.
The game is closed before the quest is reportedThe state on disk is still active and the report is lostSave the progress document at the end of the walk, as this guide does.
The objective walk is started twice in the same frameThe second start replaces the work of the firstStart the walk from one place, or give the two walks different names.
The objective walk finds no objective at allThe counter stays at zero and the quest is marked readyCheck the state of the quest before starting the walk.
A path contains a slash in a keyThe path is split at the slashEncode the slash as ~1 and the tilde as ~0 inside a path.
The game runs on HTML5Apppath$ has no meaningUse a browser reference such as storage://quest_state and read the platform-specific file guide.
The game runs on Android or iOSThe file lands in the sandbox of the applicationUse the path documented for that target and test the export.

Two rules deserve emphasis. First, a counter that is read as zero does not prove that an objective is missing: use the exists condition before reading a member that may be absent. Second, never rely on the order of the objectives in the document. The loop key is the identifier, and the events address an objective by that identifier.

The system relies on four groups of features: file operations, reading and writing values, comparison of values and iteration over an object.

One difference matters for the completion of a quest. On the native runtime the exists condition accepts a member whose value is null, while the HTML5 runtime reports such a member as absent. The documents of this guide never store null, so both targets agree. The full matrix is on the runtime compatibility page.

A second difference matters for the walk. The loop prepares its work from a snapshot, so an edit made while the walk is running does not change what the walk visits. The events of this guide change the progress before the walk starts, and the walk only reads, so the two never collide.

M. Next Steps​

  • Show every objective, not only two. The tracker of this guide has two lines because the quest has two objectives. Add one group per line, or draw the tracker with a Create object and the loop that fills it.
  • Add a marker on the map. Write the identifier of the active quest into a world marker so that the compass can point at Rook while the quest is under way.
  • Let the quest guide the dialogue. Store the identifier of the active quest in the state document and let the dialogue system of the next guide read it, so Rook greets the hero differently once the slimes are dead.
  • Track a timer. Add a time_limit member to the definition and compare it in the same way the requirement is compared, to give the player a deadline.
  • Protect the file. The extension can encrypt the file it writes and validate it against a JSON schema. See Enable Encryption and Enable JSON Schema Validation.
  • Add a chapter. Several chapters can hold several quests each, and the tracker can show the quest of the current chapter only.
